# 🧹 git restore

> [!ABSTRACT] **Определение**
> 
> **git restore** — это специализированная команда для восстановления файлов в рабочем каталоге или индексе до состояния из определенного источника (по умолчанию это Индекс или HEAD). Она пришла на смену «файловой» части команды `git checkout`.

---
### 🛠️ Флаги и команды в таблице

| **Команда / Флаг**    | **Описание**                                                          | **Пример**                       |
| --------------------- | --------------------------------------------------------------------- | -------------------------------- |
| `--source` (`-s`)     | Указывает «откуда» брать версию файла (коммит, ветка или тег).        | `git restore -s HEAD~2 file.txt` |
| `--staged` (`-S`)     | Восстанавливает файл в **Индексе**. Аналог «unstage».                 | `git restore --staged file.txt`  |
| `--worktree` (`-W`)   | Восстанавливает файл в **Рабочем дереве**. (Флаг по умолчанию).       | `git restore file.txt`           |
| `-p` (`--patch`)      | Интерактивный режим: выбор конкретных фрагментов (ханков) для отката. | `git restore -p app.js`          |
| `--staged --worktree` | Одновременный откат файла и в индексе, и на диске.                    | `git restore -S -W file.txt`     |

### 🔍 Ответы на технические вопросы

> [!QUESTION] **1. В чем главное отличие от **`git checkout`?
> 
> До 2019 года `checkout` делал всё: переключал ветки и восстанавливал файлы. Это путало.
> 
> - `git switch` теперь только для веток.
>     
> - `git restore` теперь только для **содержимого файлов**.
>     
>     Это повышает безопасность: вы не переключите ветку случайно, когда просто хотели откатить опечатку в конфиге.
>     

> [!QUESTION] **2. Что является источником (Source) по умолчанию?**
> 
> Это зависит от того, что вы восстанавливаете:
> 
> - Если вы восстанавливаете **Рабочий каталог** (`--worktree`), источником будет **Индекс**.
>     
> - Если вы восстанавливаете **Индекс** (`--staged`), источником будет **HEAD**.
>     
> - Если вы восстанавливаете **оба сразу**, источником будет **HEAD**.
>     

> [!QUESTION] **3. Как это реализовано под капотом?**
> 
> Git находит в указанном источнике (коммите или индексе) нужный объект типа **blob** (снимок файла), вычисляет его содержимое и просто перезаписывает файл в целевой области (диск или файл индекса).
> 
> - **Важно:** В отличие от `stash`, `restore` не создает временных коммитов. Это прямая операция записи поверх существующих данных.
>     

> [!QUESTION] **4. Можно ли восстановить удаленный файл?**
> 
> Да. Если вы случайно удалили файл через `rm`, но он есть в коммите или индексе:
> 
> `git restore deleted_file.txt` — Git увидит, что файла нет в рабочей директории, найдет его в индексе и «воскресит» его.

---
### 🏗️ Архитектурная логика (Source -> Destination)

Команда `restore` работает как насос, перекачивающий данные между тремя деревьями:

1. **Коммит (Source)** -> **Индекс (Destination)**: `git restore --staged --source=HEAD~1 file.txt`
2. **Индекс (Source)** -> **Рабочий каталог (Destination)**: `git restore file.txt`
3. **Коммит (Source)** -> **Рабочий каталог (Destination)**: `git restore --source=master file.txt`

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про Restore**
> 
> **1. Как отменить** `git add .`**, используя** `restore`**?**
> 
> - _Ответ:_ `git restore --staged .`. Это сбросит файлы из индекса, вернув их в состояние последнего коммита (HEAD), но оставит все правки в самих файлах на диске.
>     
> 
> ---
> 
> **2. Как полностью сбросить файл до состояния из другой ветки?**
> 
> - _Ответ:_ `git restore --source=other-branch --staged --worktree path/to/file.js`. Это сделает файл идентичным версии в `other-branch` и в индексе, и в рабочей папке.
>     
> 
> ---
> 
> **3. Что будет с новыми (untracked) файлами при вызове** `git restore .`**?**
> 
> - _Ответ:_ Ничего. `restore` работает только с **отслеживаемыми** путями. Новые файлы останутся на диске. Чтобы удалить их, нужно использовать `git clean`.
>     
> 
> ---
> 
> **4. Можно ли «откатить» изменения внутри файла, которые еще не были добавлены в индекс?**
> 
> - _Ответ:_ Да, это самая частая операция: `git restore <file>`. Она просто затирает текущие изменения на диске версией из индекса.
>     
> 
> ---
> 
> **5. В чем разница между** `git reset HEAD <file>` **и** `git restore --staged <file>`**?**
> 
> - _Ответ:_ Технически — ни в чем. `restore` просто делает это более явно и читаемо. В новых версиях Git именно `restore` является рекомендуемым способом.
>

### 💡 Резюме для конспекта:

> [!SUCCESS] **Главный инсайт**
> 
> `git restore` — это ваш предохранитель.
> 
> - Нужно убрать файл из `git add`? -> `--staged`.
>     
> - Нужно стереть плохой код в файле? -> просто `restore`.
>     
> - Нужно достать версию файла из вчерашнего коммита? -> `--source`.
>     
>     Она гораздо безопаснее, чем `reset --hard`, потому что позволяет работать **точечно** с файлами, не ломая всю историю ветки.
>
