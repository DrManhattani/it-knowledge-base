# 📦 git subtree

> [!ABSTRACT] **Техническая суть**
> 
> **git subtree** — инструмент в Git, позволяющий включать и управлять репозиториями внутри другого репозитория, не используя submodule. Это полезно, если нужно включить код из другого репозитория и при этом управлять его обновлениями и изменениями без сложностей, связанных с git submodule.

---

### 🧠 Главное отличие: Механика хранения

В `git subtree` нет никаких файлов `.gitmodules` и режима `160000`.

- Все файлы «внедренного» проекта становятся **обычными файлами** твоего репозитория.
- Любой человек, склонировавший твой проект, сразу видит все файлы, ему не нужно делать `init` или `update`.
- История коммитов внедренного проекта подклеивается к твоей истории (обычно в сжатом виде).

## 🛠️🛠🛠 Разбор синтаксиса и процессов

### 🛠🛠 Пункт №1: Добавление (Add)

Эта команда инициализирует связь и физически копирует файлы из чужого репозитория в твой.
#### Синтаксис

```bash
git subtree add --prefix <путь_внутри_проекта> <url_репозитория> <ветка> --squash
```

- **`--prefix <путь>`**: Это обязательный флаг, который задает «точку монтирования». Git subtree — команда специфическая, она не понимает относительные пути просто так, поэтому ей нужно явно сказать: «Возьми всё содержимое удаленного репозитория и положи его вот в эту конкретную папку (например, `vendor/logger`)». Если папки нет, Гит создаст её сам.
    
- **`<url_репозитория>`**: Адрес проекта, который мы внедряем.
    
- **`<ветка>`**: Здесь ты указываешь, **какую именно ветку** из удаленного репозитория ты хочешь забрать. Это критически важно: ты не скачиваешь весь репозиторий целиком со всеми потрохами, ты берешь «слепок» конкретной ветки (например, `main` или `v2.0`) на текущий момент.
    
- **`--squash`**: Флаг, который превращает всю многолетнюю историю внешнего проекта в **один единственный коммит** в твоем дереве.
#### ⚙️ Что происходит «под капотом» (Step-by-Step)

Когда ты запускаешь эту команду, Гит выполняет сложную последовательность низкоуровневых действий:

1. **Fetch**: Гит идет по указанному URL и скачивает объекты указанной `<ветки>` во временное хранилище твоего репозитория.
    
2. **Synthesize (если есть --squash)**: Гит создает один «синтетический» коммит, который содержит в себе всё состояние файлов внешней ветки, но отрезает всю её предыдущую историю.
    
3. **Read-Tree**: Это магия слияния. Гит считывает дерево этого коммита и «маппит» (сопоставляет) его на твой рабочий каталог, добавляя указанный тобой `--prefix` ко всем путям файлов. То есть файл `README.md` из чужого репо превращается в `vendor/logger/README.md` в твоем.
    
4. **Commit**: Гит создает **Merge Commit** в твоем основном репозитории. Этот коммит имеет двух «родителей» (твой последний коммит и тот самый синтетический коммит из сабтри).

#### 💡 Важные нюансы

> [!TIP] **Почему** `--squash` **— это стандарт индустрии?**
> 
> Без этого флага ты вливаешь в свой проект **всю историю** чужого репозитория. Если в библиотеке было 10 000 коммитов, твоя команда `git log` превратится в бесконечный список чужих правок, в которых твои собственные коммиты просто потеряются. `--squash` делает историю чистой: «Один коммит — внедрение одной библиотеки».

> [!WARNING] **Засада с путями**
> 
> `--prefix` всегда считается от корня твоего текущего репозитория. Не пытайся использовать `../` или абсолютные пути — Гит работает строго внутри своего «песочного» дерева.

### 🛠🛠 Пункт №2: Обновление (Pull)

Эта команда забирает свежие изменения из удаленного репозитория и вливает их в твою подпапку.

#### Синтаксис

```bash
git subtree pull --prefix <путь> <url_репозитория> <ветка> --squash
```

#### ❓ Куда и как ложатся коммиты?

Новые коммиты из удаленного репозитория ложатся **поверх твоей текущей ветки** в основном репозитории.

**Нарушается ли история?**

- **В основном репозитории:** Да, история становится «смешанной». Между твоим прошлым обновлением библиотеки и текущим могут лежать десятки твоих собственных коммитов, которые вообще не относятся к этой библиотеке. Для основного проекта это нормально — это просто хронология твоей работы.
- **В удаленном репозитории (оригинале):** Его история **никак не страдает**. Когда ты делаешь `pull`, ты не меняешь ничего «там», ты только забираешь данные «себе».
- **Как Гит не путается?** Гит использует алгоритм слияния (merge strategy), который знает: «Из всех изменений в этом огромном коммите обновления меня интересуют только те, что касаются папки `--prefix`».

>[!warning]  Как Гит «не путается»? (Механика стратегии)
>Когда ты делаешь обычный `merge`, Гит ищет общего предка двух веток. Но у основного репозитория и сабтри-репозитория **разные структуры папок** (в одном файлы в корне, в другом — в подпапке).
>
>Гит использует **Subtree Merge Strategy**. Её магия в том, что перед началом сравнения файлов она «виртуально» сдвигает путь до корневого дерева удаленного репозитория, добавляя к нему твой `--prefix`. Только после этого выравнивания Гит начинает искать отличия. 

>[!info] **Сценарий А: С флагом** `--squash` **(Чистая история)**
> 
Это когда ты хочешь забрать обновления одним коммитом.
**Процесс по шагам:**
>1. **Fetch:** Гит качает новые коммиты из удаленной ветки.
>    
>2. **Squash (Сжатие):** Гит берет все новые коммиты и «схлопывает» их в один временный коммит (назовем его **Commit-S**). 
>	- В этом коммите файлы лежат в корне. Этот один «сжатый» коммит становится для Гита якорем. При следующем обновлении Гит посмотрит на этот якорь и поймет: «Ага, с прошлого раза в библиотеке изменились вот эти 5 файлов, давай я их обновлю».
>	- Гит создает коммит «в воздухе» (как висячий узел в графе), а потом делает слияние с основной веткой.
>    
>3. **Tree Alignment:** Гит берет содержимое **Commit-S** и «перекладывает» его в дерево, где все пути начинаются с твоего `--prefix`.
>    
>4. **Merge:** Гит создает в твоей ветке новый **Merge Commit**.
>    
>    - **Первый родитель:** Твой текущий `HEAD`.
>        
>    - **Второй родитель:** Тот самый **Commit-S**.
>        
>    - **Результат:** Твоя история остается линейной, ты видишь только один коммит: _"Squashed 'path/' changes from [hash]"_.
   >     
>> [!IMPORTANT] **Где берется точка отсчета?**
> Гит ищет в твоей истории последний коммит, созданный командой `subtree add/pull --squash` для этого префикса. Он сравнивает «тогда» и «сейчас» в удаленном репо, и только разницу (diff) вливает в твой префикс.

> [!INFO] **Сценарий B: БЕЗ флага** `--squash`
> 
> При использовании команды без сжатия происходит полноценное слияние двух независимых историй (графов) коммитов. Весь процесс делится на следующие технические этапы:
> 
> 1. **Fetch (Скачивание объектов):** Git загружает из удаленного репозитория все новые объекты коммитов, деревьев и блобов. В этих объектах файлы по-прежнему расположены в корне (`/`), так как физически коммиты автора не изменяются.
>     
> 2. **Поиск общего предка (Common Ancestor):** Алгоритм ищет последнюю точку слияния между вашей текущей веткой и удаленной веткой. Это необходимо для вычисления диффа (разницы), который нужно применить.
>     
> 3. **Стратегия слияния (Subtree Strategy):** Активируется специфический алгоритм `recursive` со стратегией `subtree`. Его задача — сопоставить (map) корневое дерево (`tree object`) удаленного коммита с конкретным путем (`--prefix`) в вашем рабочем дереве.
>     
> 4. **Виртуальное выравнивание:** В процессе вычисления слияния Git «на лету» сопоставляет пути: изменение файла `file.txt` в удаленном репо Гит интерпретирует как изменение `prefix/file.txt` в вашем проекте.
>     
> 5. **Создание Merge-коммита:** В вашей ветке создается новый коммит слияния, который имеет **двух родителей**:
>     
>     - **Первый родитель:** Ваш последний локальный коммит.
>         
>     - **Второй родитель:** Последний оригинальный коммит автора из удаленного репозитория.
>         
> 6. **Результат в истории:** > * В лог вашего репозитория (`git log`) попадает **вся цепочка оригинальных коммитов** автора со всей их метаинформацией.
>     
>     - Если выполнить `git checkout` на любой из этих «пришедших» коммитов, файлы будут находиться в корне, так как их объекты `tree` не перезаписывались.
>         
>     - Только в итоговом **Merge-коммите** (и во всех ваших последующих коммитах) файлы будут зафиксированы в подпапке, согласно логике слияния деревьев.
>

#### 📊 Сравнение сценариев

|**Характеристика**|**С флагом --squash**|**БЕЗ флага --squash**|
|---|---|---|
|**Вид истории**|Чистая (один Merge-коммит на обновление).|Запутанная (десятки чужих коммитов в логе).|
|**Конфликты**|Проще решать, так как работаешь с одним «слепком».|Сложнее, если конфликты возникли в середине чужой истории.|
|**Поиск ошибок**|Тяжело понять, какой именно мелкий коммит автора всё сломал.|Легко использовать `git bisect`, чтобы найти виновный коммит автора.|
|**Использование в DevOps**|**Стандарт.** Нам важна чистота истории проекта.|Редко. Только если нужно очень глубоко дебажить чужой код.|
#### 💡 Важные нюансы

> [!CAUTION] **Золотое правило** `--squash`
> 
> Если ты добавил (`add`) сабтри с флагом `--squash`, ты **обязан** использовать `--squash` при каждом последующем `pull`. Если ты забудешь флаг хотя бы один раз, Git попытается влить всю детальную историю удаленного репозитория в твою ветку, что приведет к мешанине из сотен чужих коммитов и огромному количеству конфликтов слияния.

> [!IMPORTANT] **Локальные изменения**
> 
> Если ты правил файлы внутри папки сабтри у себя локально и при этом делаешь `pull`, Git попытается выполнить обычное слияние (merge). Если изменения пересекаются, возникнут классические **конфликты**, которые придется править руками, как при обычном `git merge`.
#### 🎙️ На собеседовании:

> «При выполнении `git subtree pull` происходит интеграция внешних изменений в текущую рабочую ветку основного проекта. Механизм основан на стратегии слияния `subtree`, которая сопоставляет дерево внешнего репозитория с конкретным префиксом в нашем проекте. Использование `--squash` позволяет сохранять линейную и чистую историю основного репозитория, представляя каждое обновление внешней библиотеки как один атомарный merge-коммит. При этом история самого внешнего репозитория остается нетронутой».

### ❓ Вопросы к теме слияния при git subtree pull:
#### 1. БЕЗ флага `--squash` (Поиск через Общего Предка)

В этом режиме Гит работает как классический `merge`.
- **Как он вычисляет разницу?** Гит ищет в графе **Merge Base** — это самый последний общий коммит, который есть и в твоей ветке, и в ветке автора.
- **Что с чем сравнивается?** Гит берет **последний коммит автора** и сравнивает его с этим **общим предком**.
- **Результат:** Полученный «дифф» (разница) накладывается на твою папку с префиксом.

> [!NOTE] **Суть без squash**
> 
> Гит сравнивает **[Последний коммит автора]** vs **[Общий предок]**. Твой текущий Merge-коммит здесь не является точкой отсчета для диффа, он лишь место, где этот дифф сохранится.
#### 2. С флагом `--squash` (Сравнение Состояний)

Здесь магия хитрее, потому что общего предка в графе нет (мы же отрезали историю в прошлый раз).
- **Как он вычисляет разницу?** Гит смотрит в историю твоего репозитория и ищет последний «синтетический» коммит, который был создан командой `subtree pull/add --squash` для этого префикса.
- **Что с чем сравнивается?** Гит берет хэш того коммита удаленного репозитория, на котором ты остановился в прошлый раз (он записан в комментарии к твоему прошлому скваш-коммиту), и сравнивает его с **новым последним коммитом автора**.
- **Результат:** Гит понимает: «С прошлого раза в удаленном репо добавилось 5 новых коммитов. Я возьму их суммарный дифф, сделаю из него один новый "синтетический" коммит и приклею его к проекту».

> [!IMPORTANT] **Суть со squash**
> 
> Ты попал в точку: Гит вычисляет разницу между **[Новым состоянием автора]** и **[Старым состоянием автора]** (на котором ты «засинхронился» в прошлый раз).
#### 3. Кто является «Общим предком» (pull без `--squash`)?

Когда ты делаешь `git subtree pull` во второй раз, Гиту нужно найти точку, от которой он будет считать разницу.

**Общим предком** будет являться **тот самый коммит автора**, который ты вливал в прошлый раз (при `add` или прошлом `pull`).

**Как Гит его находит?**

Он смотрит на твой последний **Merge-коммит**, созданный сабтри-командой. У этого мерджа два родителя:

1. Твоя основная ветка.
2. **Коммит автора из удаленного репозитория.**

Гит заглядывает во «второго родителя», видит его хэш и понимает: «Ага, в прошлый раз мы остановились на коммите `A`. Сейчас в удаленном репозитории последний коммит — `D`. Значит, мне нужно вычислить разницу между `D` и `A` и применить её к моей папке».

> [!IMPORTANT] **Точный ответ**
> 
> Общим предком является **последний коммит из удаленного репозитория**, который уже был успешно объединен с твоей веткой ранее.
#### 4. Совпадает ли хэш Скваш-коммита с хэшем автора?

**Нет, никогда не совпадает.** Это технически невозможно в архитектуре Git.
Давай вспомним, из чего вычисляется хэш коммита (SHA-1):
1. **Tree (Дерево):** Список файлов и путей.
2. **Parents (Родители):** Хэши предыдущих коммитов.
3. **Author/Committer:** Имя и дата.
4. **Message:** Текст сообщения.
##### Почему хэши разные (3 причины):

- **Структура (Tree):** Это главная причина. У автора в коммите файлы лежат в корне (`/`). В твоем скваш-коммите файлы лежат в подпапке (`vendor/lib/`). Поскольку пути разные, объект `tree` имеет другой хэш. А раз дерево другое — хэш коммита тоже другой.
- **Родители (Parents):** У коммита автора в родителях — его собственная история. У твоего скваш-коммита (синтетического) либо **вообще нет родителей** (если это первый `add`), либо они ведут в твою историю.
- **Метаданные:** В скваш-коммите Гит обычно дописывает техническую информацию (например, хэш оригинала), чтобы при следующем пулле знать, на чем он остановился.
##### 🔍 Что же тогда общего у этих коммитов?

Единственное, что у них идентично — это **содержимое файлов (blobs)**.

Если ты сравнишь хэш файла `api.py` в репозитории автора и хэш того же файла в твоем скваш-коммите — **они будут одинаковыми**. Гит не копирует данные, он просто ссылается на тот же «блоб», но под другим путем в дереве.

##### 🎙️ Резюме для конспекта:

1. **При обычном Pull (без скваша):** Гит находит общего предка через граф связей (предыдущий мердж). Разница считается между «старым» и «новым» коммитами автора.
2. **При Squash Pull:** Хэш твоего локального скваш-коммита **отличается** от оригинального коммита автора из-за наличия префикса в путях и другой структуры родителей. Гит использует комментарии в скваш-коммите, чтобы хранить ссылку на оригинальный хэш автора для будущих обновлений.

### 🛠🛠 3. Отправка изменений (Push)

Это сложнее. Если ты поправил файлы внутри папки subtree и хочешь отдать их назад в оригинал:

```bash
git subtree push --prefix <папка> <url_репозитория> <ветка>
```

**Процесс:** `git subtree push` — это самая ресурсозатратная и технически сложная операция в механике Subtree. Если при `pull` Гит просто «вклеивал» чужое дерево в твое, то здесь ему приходится проводить обратную «хирургическую операцию»: вычленять твои правки из общего потока и воссоздавать из них чистую историю для оригинального репозитория.

Вот подробный разбор того, что происходит под капотом.

> [!INFO] **Механика git subtree push: Процесс синтеза истории**
> 
> Команда `git subtree push --prefix=<путь> <url_репозитория> <ветка>` запускает процесс, состоящий из трех ключевых фаз: **Split (Разделение)**, **Reconstruction (Воссоздание)** и **Transport (Передача)**.
> 
> ### 1. Фаза Split (Фильтрация истории)
> 
> Поскольку в твоем репозитории изменения библиотеки перемешаны с изменениями основного проекта, Гит не может просто отправить твои коммиты «как есть».
> 
> - **Сканирование:** Гит проходит по всей истории текущей ветки от момента последнего слияния с сабтри.
>     
> - **Идентификация:** Алгоритм ищет каждый коммит, в котором были затронуты файлы внутри директории `--prefix`.
>     
> 
> ### 2. Фаза Reconstruction (Синтез новых объектов)
> 
> Для каждого найденного коммита Гит создает **совершенно новый объект коммита** в твоей локальной базе данных. Это и есть процесс «расщепления» истории:
> 
> - **Отсечение префикса:** Гит берет дерево (`tree`) этого коммита и «вырезает» из него только то поддерево, которое находится по пути `--prefix`. Теперь это поддерево становится **корневым деревом** нового коммита.
>     
> - **Сохранение метаданных:** Новый коммит наследует автора, дату и сообщение оригинального коммита, но получает **новый хэш** (так как структура дерева и родители изменились).
>     
> - **Связывание родителей:** Гит выстраивает эти новые синтетические коммиты в цепочку, которая соответствует хронологии твоих правок. В итоге получается временная «чистая» ветка, где нет файлов основного проекта, а файлы библиотеки лежат в корне.
>     
> 
> ### 3. Фаза Transport (Отправка)
> 
> Как только «чистая» цепочка коммитов построена:
> 
> - Гит сравнивает верхушку этой временной ветки с верхушкой удаленной ветки.
>     
> - Если конфликтов нет, он выполняет обычный `push` этой синтезированной истории в удаленный репозиторий.
>     
> 
> ### ⚠️ Важные технические нюансы:
> 
> - **Cache (Кэширование):** Чтобы не пересчитывать всю историю при каждом пуше, Гит сохраняет соответствие между твоими оригинальными коммитами и синтезированными в папке `.git/subtree-cache`. Это значительно ускоряет повторные операции.
>     
> - **Ресурсоемкость:** Процесс `split` может быть очень долгим, если в основном проекте тысячи коммитов, так как Гит должен проверить каждый на наличие изменений в подпапке.
>     
> - **Идентичность:** Если два человека сделают `subtree push` одних и тех же изменений, Гит создаст идентичные хэши синтетических коммитов (если сообщения и даты совпадают), что позволяет избежать дубликатов в удаленном репозитории.
>     

### 🛠🛠 4. Разделение (Split) — для профи

Если ты вдруг понял, что папка в твоем проекте выросла в нечто крутое и должна стать отдельным репозиторием:

```bash
git subtree split --prefix=<папка> -b <новая_ветка>
```

**Процесс:** Команда `split` — это «двигатель» всей магии `subtree`. Именно она отвечает за выделение (экстракцию) части истории в отдельную ветку. Несмотря на то, что `split` часто работает «под капотом» команды `push`, её можно использовать самостоятельно, что крайне полезно для DevOps-задач (например, при распиле монорепозитория на микросервисы).

Вот подробный разбор того, как Git проводит эту «археологическую» работу.

> [!INFO] **Механика git subtree split: Экстракция поддерева**
> 
> Команда `git subtree split --prefix=<путь> -b <новая_ветка>` выполняет глубокое сканирование и реконструкцию истории. Процесс происходит по следующему алгоритму:
> 
> ### 1. Обход графа (History Traversal)
> 
> Git берет текущую ветку и начинает просматривать каждый коммит, начиная с самого первого. Это линейный процесс: алгоритм должен проверить каждое состояние проекта.
> 
> ### 2. Фильтрация и сравнение (Filtering)
> 
> Для каждого коммита Git задает вопрос: «Изменилось ли в этом коммите что-нибудь внутри папки `<префикс>` по сравнению с его родителем?».
> 
> - **Если изменений нет:** Этот коммит полностью игнорируется.
>     
> - **Если изменения есть:** Git переходит к фазе синтеза.
>     
> 
> ### 3. Синтез нового коммита (Rewriting)
> 
> Это самая важная часть. Для коммита, прошедшего фильтр, Git создает **новый объект коммита**:
> 
> - **Маппинг дерева (Tree Mapping):** Гит берет объект `tree` исходного коммита, находит в нем запись для папки `<префикс>` и делает это поддерево **корневым деревом** нового коммита. Таким образом, префикс пути физически «отрезается».
>     
> - **Сохранение контекста:** Новый коммит получает того же автора, ту же дату и то же сообщение, что и оригинал.
>     
> - **Пересчет хэша:** Поскольку дерево теперь другое (файлы в корне, а не в папке) и родители другие, коммит получает новый уникальный SHA-1 хэш.
>     
> 
> ### 4. Склеивание истории (Linking)
> 
> Новые синтезированные коммиты связываются друг с другом. Родителем нового коммита `N` становится новый коммит `N-1`, созданный на предыдущем шаге. В итоге формируется абсолютно новая ветка, которая существует параллельно основной, но содержит только «очищенную» историю одной папки.
> 
> ### ⚠️ Технические особенности:
> 
> - **Кэширование:** Git сохраняет таблицу соответствий (Mapping) между старыми и новыми хэшами в папке `.git/subtree-cache`. Если ты запустишь `split` повторно, он не будет пересчитывать всю историю с нуля, а просто достроит недостающее звено.
>     
> - **Идентичность результата:** Если два разных человека запустят `split` на одной и той же истории с одним и тем же префиксом, они получат **одинаковые хэши** новых коммитов. Это позволяет синхронизировать работу разных участников.
>     
> - **Игнорирование Merge-коммитов:** По умолчанию `split` пытается игнорировать мерджи, которые не относятся к подпапке, чтобы сделать историю максимально линейной и чистой для будущего использования в качестве отдельной библиотеки.
>

### 🚀 Реальный пример работы

Представь, ты работаешь над основным проектом и хочешь вставить туда библиотеку `logger`.

1. **Добавляем:**
    `git subtree add --prefix lib/logger https://github.com/user/logger.git main --squash`
    _Результат:_ Папка `lib/logger` появилась. Файлы внутри — обычные. В истории один коммит: "Merge branch 'main' of...".
    
2. **Меняем код:** Ты прямо в основном проекте правишь `lib/logger/core.py`. Делаешь обычный `git commit`.
	
3. **Отдаем назад:**
    `git subtree push --prefix lib/logger https://github.com/user/logger.git main`
    _Результат:_ Твои правки улетели в оригинальный репозиторий логгера.

### 📊 Сравнение: Subtree vs Submodule

|**Характеристика**|**Git Submodule**|**Git Subtree**|
|---|---|---|
|**Хранение**|Ссылка (gitlink)|Реальные файлы|
|**Сложность для коллег**|Высокая (нужен `update`)|**Нулевая** (просто `clone`)|
|**Размер репозитория**|Почти не растет|Растет на объем файлов|
|**История**|Раздельная|Смешанная|
|**Изменение кода**|Сложно (нужен checkout в подпапке)|**Легко** (как обычные файлы)|

### 🎙️ Роль в DevOps и частота использования

В 2026 году на российском и мировом рынке ситуация такая:

1. **Популярность:** `subtree` используется реже, чем `submodule`, но его популярность растет в **Monorepo** подходах.
2. **Где встретишь:**
    - **Общие конфиги:** Если у тебя 10 проектов и им нужны одинаковые Bash-скрипты или CI-шаблоны.
    - **Библиотеки внутри компании:** Когда разработчики не хотят мучиться с зависимостями, они просто «втаскивают» код через subtree.
3. **В DevOps:** Мы используем subtree, когда нужно внедрить общие **Terraform модули** или **Ansible роли** в разные проекты так, чтобы это было прозрачно для всей команды.

> [!TIP] **Мнение инженера**
> 
> Если твоя команда — это «суровые» программисты, они выберут **Submodule**, потому что это чище архитектурно.
> 
> Если в команде много новичков или нужно, чтобы «просто работало после клонирования» — выбирай **Subtree**.
