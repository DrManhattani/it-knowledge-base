# ⏪ git reset

> [!ABSTRACT] **Техническое определение**
> 
> **git reset** — это команда **отменяет последние изменения** и возвращает репозиторий к нужному состоянию. Если точнее, то происходят манипуляции с указателем текущей ветки (`refs/heads/<branch>`). Команда перемещает этот указатель ветки на другой коммит, опционально синхронизируя с ним Индекс и Рабочую директорию. Сами объекты коммитов при этом не изменяются и не удаляются из базы `.git/objects`.

---
### 🏗️ Три стадии влияния на деревья

>[!check] Разные зоны действия команды в зависимости от флагов 
>
>```bash
>git reset [ --soft | --mixed | --hard ] [<commit>]
>```

| **Флаг**  | **Перемещение указателя ветки (и за ним HEAD)**            | **Обновление Индекса (Index / Staging)**                       | **Обновление Рабочей директории (Working Copy)**                     |
| --------- | ---------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| `--soft`  | **Да.** Указатель ветки теперь ссылается на целевой SHA-1. | **Нет.** Индекс остается в том же состоянии, что и до команды. | **Нет.** Файлы на диске не меняются.                                 |
| `--mixed` | **Да.** Указатель ветки теперь ссылается на целевой SHA-1. | **Да.** Индекс перезаписывается состоянием целевого коммита.   | **Нет.** Файлы на диске не меняются.                                 |
| `--hard`  | **Да.** Указатель ветки теперь ссылается на целевой SHA-1. | **Да.** Индекс перезаписывается состоянием целевого коммита.   | **Да.** Файлы на диске перезаписываются состоянием целевого коммита. |
>[!attention] По умолчанию используется флаг `--mixed`
>- **Если коммит указан** - то происходит смещение ветки на указанный коммит, а также изменения индекса до состояния указанного коммита.
>- **Если коммит НЕ указан** - то по умолчанию используется текущий коммит `HEAD` и индекс меняется до уровня текущего коммита.

---
### 📘 Детальный разбор механики

#### 1. `--soft`

Команда обновляет только файл ссылки ветки (например, `.git/refs/heads/main`). Поскольку индекс не тронут, разница между «новым» положением ветки и «старым» состоянием индекса воспринимается Гит как **staged changes** (подготовленные к коммиту).

#### 2. `--mixed` (Default)

Указатель ветки перемещается, а файл индекса (`.git/index`) обновляется так, чтобы соответствовать дереву (tree) целевого коммита. Разница между целевым коммитом и файлами в рабочей директории теперь видится как **unstaged changes** (изменения, не добавленные в индекс).

#### 3. `--hard`

Самый глубокий уровень синхронизации. Помимо указателя и индекса, Git выполняет операцию, аналогичную `checkout` для всех файлов, приводя рабочую директорию к состоянию целевого коммита.

**Важно:** Единственные данные, которые можно потерять безвозвратно — это изменения в рабочей директории, которые **никогда не были закоммичены** (даже если они были в индексе, их блобы останутся, но найти их без ссылок крайне сложно).

---
### 🛡️ Жизненный цикл объектов и Reflog

Любой коммит, от которого мы «отрезали» ветку с помощью `reset`, становится **висячим объектом (dangling commit)**. Он перестает быть достижимым через стандартную историю ветвей, но:

1. **Доступность:** Он всё еще существует физически в `.git/objects`.
2. **Reflog:** Git записывает каждое перемещение HEAD в журнал `reflog`. Если ты сделал `git reset --hard HEAD~3`, ты можешь найти хеш старой «верхушки» через `git reflog` и вернуть ветку обратно.
3. **Garbage Collection:** Объекты будут удалены только после запуска `git gc`, и только если на них нет ссылок (обычно через 30-90 дней, в зависимости от настроек `gc.reflogExpire`).

### 🛠️ Сценарии использования (Best Practices)

> [!EXAMPLE] **Сценарий 1: Схлопывание (Squashing) коммитов**
> 
> Ты наделал 5 мелких коммитов типа "fix", "typo", "fix again". Ты хочешь, чтобы в истории это был один красивый коммит.
> 
> ```bash
> # Откатываемся на 5 шагов назад, но оставляем весь код в Индексе
> git reset --soft HEAD~5
> # Делаем один чистый коммит
> git commit -m "Feature: full implementation of authentication"
> ```

> [!EXAMPLE] **Сценарий 2: Очистка Индекса**
> 
> Ты случайно сделал `git add .` и добавил лишние логи или конфиги.
> 
> ```bash
> # Просто убирает файлы из "зеленой зоны", не удаляя код
> git reset
> ```

### ❓ Вопросы на собеседовании

1. **В чем разница между `git reset` и `git checkout` для коммитов?**
    - _Ответ:_ `checkout` перемещает только **HEAD** (оставляя ветку на месте, создавая Detached HEAD). `reset` перемещает **саму ветку** вместе с HEAD.
2. **Как отменить `git reset --hard`, если ты понял, что откатился не туда?**
    - _Ответ:_ С помощью `git reflog`. Нужно найти хеш коммита, который был «верхушкой» до ресета, и сделать `git reset --hard <hash_from_reflog>`.
3. **Что произойдет, если сделать `git reset --soft` и сразу `git commit`?**
    - _Ответ:_ Ты создашь коммит, идентичный тому, который только что «отменил», но с новым хешем (и, возможно, новым сообщением).

# ⏪ git reset `<path>`

> [!IMPORTANT] **Использование пути к файлам в команде**
> 
> Когда вы передаете `git reset` путь к файлу или папке, команда **никогда** не перемещает указатель ветки (HEAD). Она работает исключительно с **Индексом**, копируя в него состояние файла из указанного коммита.

---

### 🏗️ Механика процесса (Step-by-Step)

Если выполнить `git reset <commit> <file>`:

1. **Поиск объекта:** Git идет в указанный `<commit>`, находит там дерево (tree) и извлекает хеш (SHA-1) для конкретного `<file>`.
2. **Обновление Индекса:** Git перезаписывает запись для этого файла в `.git/index` этим хешем.
3. **Рабочая директория:** Файлы на диске **не меняются**.
4. **Указатель ветки:** Остается на месте.

---
### 🛠️ Сценарии использования

#### 1. Сброс файла из Индекса (Unstaging)

Самый частый случай: вы сделали `git add .`, но поняли, что файл `config.json` не должен попасть в этот коммит.

- **Команда:** `git reset config.json` (эквивалентно `git reset HEAD config.json`)
- **Результат:** Файл `config.json` в Индексе теперь совпадает с тем, что было в последнем коммите (HEAD). В `git status` он превратится из «зеленого» (staged) в «красный» (modified).
#### 2. Восстановление версии файла из прошлого в Индекс

Вы хотите подготовить коммит, в котором файл `script.py` будет таким же, каким он был 3 коммита назад.

- **Команда:** `git reset HEAD~3 script.py`
- **Результат:** Индекс обновится версией файла из `HEAD~3`. Ваши текущие правки в `script.py` на диске всё еще сохранены, но теперь вы можете легко сделать `diff` между ними и старой версией в индексе или просто закоммитить старую версию (сделав потом `checkout`).

---
### 📊 Сравнение: Reset коммита vs Reset файла

| **Характеристика**          | `git reset <commit>`          | `git reset <commit> <path>`      |
| --------------------------- | ----------------------------- | -------------------------------- |
| **Указатель ветки (HEAD)**  | **Перемещается**              | **Не меняется**                  |
| **Индекс (Staging Area)**   | Обновляется (кроме `--soft`)  | **Обновляется всегда**           |
| **Рабочая директория**      | Обновляется (только `--hard`) | **Не меняется никогда**          |
| **Флаги** (`--soft/--hard`) | Применимы                     | **Недопустимы** (вызовут ошибку) |
