# 🏷️ git tag

> [!ABSTRACT] **Определение**
> 
> **git tag** — это неизменяемая ссылка (pointer), которая указывает на конкретный коммит в истории. В отличие от веток, теги не двигаются вперед при создании новых коммитов. Обычно используются для маркировки версий (v1.0, v2.1.4-beta).

---
### 🏗️ Два типа тегов: Техническое различие

Это самый частый вопрос на интервью. Git хранит их по-разному.

|**Тип**|**Что это такое?**|**Где хранится?**|**Команда**|
|---|---|---|---|
|**Lightweight** (Легковесный)|Просто "закладка". Только имя и хеш коммита.|Файл в `.git/refs/tags/`|`git tag v1.0`|
|**Annotated** (Аннотированный)|Полноценный **объект** в БД Git. Содержит имя автора, дату, e-mail и сообщение.|Объект в `.git/objects/`|`git tag -a v1.0 -m "Msg"`|
### 📦 Где хранятся ссылки и объекты?

Это важный момент для понимания архитектуры:
1. **Указатель (Reference):** Любой тег (и легкий, и аннотированный) всегда имеет файл-ссылку в папке `.git/refs/tags/<имя_тега>`.
2. **Содержимое ссылки:**
    - Для **Lightweight**: в файле лежит хеш **коммита**.
    - Для **Annotated**: в файле лежит хеш **объекта тега** (который находится в `.git/objects/`).
3. **Объект тега:** Этот объект, в свою очередь, содержит внутри себя ссылку на целевой коммит.

### 🛠️ Таблица команд и операций

| **Команда**                       | **Описание**                                                                   | **Пример**                    |
| --------------------------------- | ------------------------------------------------------------------------------ | ----------------------------- |
| `git tag`                         | **Список** всех существующих тегов.                                            | `git tag`                     |
| `git tag -l`                      | **Поиск по маске**. Флаг `-l` (list) обязателен при использовании паттернов.   | `git tag -l "v1.2.*"`         |
| `git tag -a`                      | **Создать аннотированный** тег (рекомендуется для релизов).                    | `git tag -a v1.1 -m "Stable"` |
| `git tag -d <tag>`                | **Удалить** тег - удаляет только файл в `refs/tags/`                           | `git tag -d v1.0`             |
| `git tag <tag> <hash>`            | **Тег на старый коммит**. Позволяет «повесить» тег на любое событие в прошлом. | `git tag v0.9 HEAD~1`         |
| `git tag -f <tagname> <new_hash>` | **Перезаписать** тег на другой коммит                                          | `git tag -f v1.0 HEAD~2`      |
| `git show <tag>`                  | **Посмотреть данные** тега и коммита, на который он указывает.                 | `git show v1.1`               |
| `git push origin <tag>`           | Отправить конкретный тег на сервер.                                            | `git push origin v1.0`        |
| `git push origin --tags`          | Отправить **все** локальные теги на сервер.                                    | `git push origin --tags`      |

### 🌐 Взаимодействие с удаленным сервером

Это главная ловушка для новичков.
> [!CAUTION] **Логика Push**
> 
> По умолчанию команда `git push` или `git push origin <branch>` отправляет только **коммиты и ветки**. Теги игнорируются, чтобы избежать засорения сервера вашими локальными экспериментальными метками.
- **Отправить конкретный тег:** `git push origin v1.0`
- **Отправить все теги сразу:** `git push origin --tags`
- **Удалить тег на сервере:** `git push origin --delete v1.0` (просто удалить локально недостаточно).

### 🔍 Ответы на технические вопросы

> [!QUESTION] **1. Почему теги не отправляются на сервер при обычном** `git push`?**
> 
> **Ответ:** Это историческое решение Git. Теги считаются важными вехами, и их отправка должна быть осознанным действием разработчика, чтобы не засорять удаленный репозиторий «мусорными» локальными метками.

> [!QUESTION] **2. Что произойдет, если я сделаю** `git checkout v1.0`?**
> 
> **Ответ:** Ты перейдешь в состояние **«Detached HEAD»** (отсоединенный HEAD). Поскольку тег — это не ветка, ты не можешь «растить» историю дальше. Любые коммиты, сделанные в этом состоянии, не будут принадлежать ни одной ветке и могут быть удалены сборщиком мусора.

> [!QUESTION] **3. Как «переставить» тег на другой коммит, если ошибся?**
> 
> **Ответ:** Напрямую — нельзя (теги неизменны). Но можно принудительно перезаписать его: `git tag -f <tagname> <new_hash>`. Если тег уже был на сервере, придется делать `git push -f`. **Это плохая практика**, лучше создать версию `v1.0.1`.

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про теги**
> 
> **1. В чем главное отличие тега от ветки?**
> 
> - _Ответ:_ Ветка — это **подвижная** ссылка, которая автоматически перемещается на новый коммит при его создании. Тег — это **статичная** ссылка, прибитая к конкретному хешу.
>     
> 
> ---
> 
> **2. Когда стоит использовать Lightweight, а когда Annotated?**
> 
> - _Ответ:_ Annotated — для официальных релизов (чтобы знать, кто и когда выпустил версию). Lightweight — для временных локальных пометок (например, «проверить здесь баг позже»).
>     
> 
> ---
> 
> **3. Можно ли подписать тег криптографически?**
> 
> - _Ответ:_ Да. Git поддерживает GPG-подпись для аннотированных тегов (флаг `-s`). Это гарантирует, что релиз выпустил именно доверенный разработчик, а не злоумышленник.
>     
> 
> ---
> 
> **4. Как удалить тег с сервера?**
> 
> - _Ответ:_ `git push origin --delete <tagname>`.
>     
> 
> ---
> 
> **5. Можно ли создать тег на коммит, который был месяц назад?**
> 
> - _Ответ:_ Да. Нужно просто указать хеш этого коммита в конце команды: `git tag -a v0.9 <hash>`.
> ---
> **6. Зачем нужны аннотированные теги, если есть легкие?**
>
> - _Ответ:_ Для прослеживаемости. Они хранят дату создания и имя того, кто именно сделал релиз. Это критично для аудита и автоматизации CI/CD.
> ---
> **7. Почему при** `git pull` **теги прилетают, а при** `git push` **не улетают?**
> 
> - _Ответ:_ Git исходит из того, что вы хотите иметь полную картину истории проекта (включая чужие релизы), когда скачиваете данные. Но при отправке он оберегает общий репозиторий от ваших личных меток.
> ---
> **8. Как сделать тег, который указывает не на коммит?**
> 
> - _Ответ:_ Технически аннотированный тег может указывать на любой объект (даже на другой тег или blob), но на практике 99.9% тегов указывают на коммиты.
