# 📡 git remote

> [!ABSTRACT] Суть
> Используется для управления связями между локальным репозиторием и удаленными репозиториями. По умолчанию отобразит имя удаленного репозитория. Вместо того чтобы каждый раз вводить `https://github.com/user/repo.git`, ты используешь короткое имя (алиас), например `origin`.
> 
> В принципе позволяет:
> 1. Просматривать список удаленных репозиториев: `git remote`
> 2. Добавлять новые удаленные репозитории. `git remote add <имя> <url>`
> 3. Удалять или переименовывать удаленные репозитории. `git remote rename <old_name> <new_name>`
> 4. Проверять URL удаленных репозиториев. `git remote -v`

### 🔍 1. Инспекция и проверка

Когда нужно понять, куда «смотрит» твой проект.

| Команда                         | Описание                                                                                                                                          | Результат                                                                            |
| :------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------ | :----------------------------------------------------------------------------------- |
| `git remote`                    | Список имен.                                                                                                                                      | По умолчанию увидишь просто `origin`.                                                |
| `git remote -v`                 | **Verbose.**                                                                                                                                      | Показывает имена + URL (для чтения и для записи).  Читает информацию из`.git/config` |
| `git remote get-url origin`     | Проверка адреса.                                                                                                                                  | Выводит только актуальный URL для указанного имени.                                  |
| `git remote show [-n] [<name>]` | Расширенная информация<br>`-n` - запрещает Гиту лезть в интернет (покажет только то, что уже закэшировано)<br>`name` - имя удаленного репозитория | Показывает расширенную информацию об удаленной ветке.                                |

> [!INFO] Разбор команды `git remote show origin` 
> 
> 📋 **Пример вывода**
>
>
> ```
> * remote origin
>   Fetch URL: git@github.com:user/my-obsidian-vault.git
>   Push  URL: git@github.com:user/my-obsidian-vault.git

> ### 🔍 Что означают эти строки?
> 
> |**Секция / Статус**|**Что это значит в примере?**|**Твое действие**|
> |---|---|---|
> |`Fetch/Push URL`|Адрес твоего репозитория в облаке.|Проверь, если хочешь сменить HTTPS на SSH.|
> |`HEAD branch`|`main` — главная ветка на сервере.|Информативно: это база проекта.|
> |`tracked`|Ветки `main` и `feature-logs` есть и тут, и там.|Всё ок, работай как обычно.|
> |`stale`|🚩 Ветка `old-idea` удалена на сервере, но висит у тебя.|**Почисти мусор:** `git remote prune origin`.|
> |`merges with`|Настройка автоматики для `git pull`.|Просто знай: `pull` на `main` тянет данные из `origin/main`.|
> |`up to date`|Ветка `main` полностью синхронизирована.|Пушить нечего, версия в облаке актуальна.|
> |`fast-forwardable`|У тебя есть новые коммиты в `feature-logs`.|**Зеленый свет:** можно делать `git push`.|
> 
> **💡 Важный нюанс:** Для работы этой команды Гит обязательно должен «достучаться» до сервера (нужен интернет). Если ты в офлайне, Гит не сможет узнать, не стала ли какая-то ветка `stale`.
> 
> ---
> 
> > [!WARNING] Чего не хватает в этом примере?
> > **Ситуация:** Если бы кто-то другой изменил файл на сервере, ты бы увидел статус `local out of date`.
>
> **Пример вывода:**
> ```text
>    Local refs configured for 'git push':
> 	   main pushes to main (local out of date)
> ```
> * **Что это значит**: *прямой запрет*: Если ты сейчас введешь `git push`, сервер ответит ошибкой `[rejected] (fetch first)`. *Причина:* Ветка `main` на сервере ушла вперед. В ней есть коммиты, которых нет в твоей локальной базе объектов.
> * **Как это исправить**: Сначала скачай чужие правки: `git pull origin main`.
>
>> [!WARNING]  Обнаружение новых веток (New)
> **Ситуация:** Кто-то другой создал ветку в облаке, а у тебя её еще нет.
> 
> **Пример вывода:**
> ```text
>   Remote branches:
>     main                            tracked
>     new-feature                     new (next fetch will store in remotes/origin)
> ```
> * **Что это значит:** Статус `new` сообщает, что на сервере появился объект, о котором твой локальный Git еще не слышал.
> * **Польза:** Ты видишь актуальный список веток на сервере без необходимости делать `fetch`. Это «предпросмотр» того, что появится у тебя после обновления.
>
> > [!WARNING]  Поиск «веток-призраков» (Stale)
> **Ситуация:** Ветка была удалена на сервере (например, через интерфейс GitHub), но твои локальные ссылки (`refs/remotes/origin/...`) всё еще указывают на неё.
> 
> **Пример вывода:**
> ```text
>   Remote branches:
>     main                            tracked
>     old-experiment                  stale (use 'git remote prune' to remove)
> ```
> * **Что это значит:** Статус `stale` (протухшая) означает, что локальная копия ветки ссылается на пустоту.
> * **Польза:** Это прямой сигнал к действию. Чтобы почистить этот мусор и синхронизировать списки, нужно выполнить команду `git remote prune origin`.
>
> > [!WARNING]  Проверка автоматики (Push/Pull Configuration)
> **Ситуация:** Тебе нужно понять, как связаны твои локальные ветки с удаленными (upstream).
> 
> **Пример вывода:**
> ```text
>   Local branches configured for 'git pull':
>     main merges with remote main
>
>   Local refs configured for 'git push':
>     main     pushes to main     (up to date)
>     draft    pushes to main     (local out of date)
> ```
> * **Разбор строк:**
>     * `merges with remote main`: Гит подтверждает, что при команде `git pull` он пойдет именно в ветку `main` на сервере.
>     * `pushes to main (up to date)`: Гит сообщает, что всё, что ты написал в `main`, уже отправлено в облако.
>     * `local out of date`: 🚩 **Критическая ошибка.** Означает, что ты пытаешься пушить в `main`, но там уже есть чужие изменения. Твой пуш будет отклонен, пока ты не сделаешь `pull`.
> * **Польза:** Позволяет увидеть конфликты «на берегу», до того как ты начнешь отправку данных и получишь ошибку от сервера.

### 🛰️ 2. Управление удаленными связями (git remote)

> [!INFO] **Шпаргалка: Быстрый старт**
> 
> | Команда | Синтаксис | Что делает | Пример |
> | :--- | :--- | :--- | :--- |
> | **add** | `git remote add <имя> <url>` | Привязывает новый репозиторий | `git remote add origin git@github.com:user/repo.git` |
> | **set-url** | `git remote set-url <имя> <new-url>` | Меняет адрес уже существующей связи | `git remote set-url origin https://github.com/user/repo.git` |
> | **rename** | `git remote rename <старое> <новое>` | Переименовывает алиас сервера | `git remote rename origin github-server` |
> | **remove** | `git remote remove <имя>` | Удаляет связь с сервером | `git remote remove backup` |
#### 🛠️ 2.1 Подробный разбор команд

> [!EXAMPLE] **1. git remote add — Создание связи**
> 
> Используется в двух случаях: ты инициализировал новый проект (`git init`) или хочешь добавить второй сервер для бэкапа.
> 
> - **Синтаксис:** `git remote add <name> <url>`
>     
> - **Что происходит под капотом:** Git создает новую запись в файле `.git/config` и выделяет место в `.git/refs/remotes/` для будущих веток этого сервера.
>     
> - **Пример:**
>     
> 
> ```bash
> git remote add origin git@github.com:anton/my-vault.git
> ```
> 
> - **Нюанс:** Имя `origin` — это просто традиция. Ты можешь назвать его `home`, `server` или `cloud`.
>     

> [!SETTINGS] **2. git remote set-url — Исправление адреса**
> 
> Самая частая команда, когда нужно сменить протокол (например, с HTTPS на SSH) или если репозиторий переехал на новый домен.
> 
> - **Синтаксис:** `git remote set-url <name> <new-url>`
>     
> - **Почему это важно:** Если ты просто попробуешь сделать `add origin` снова, Git выдаст ошибку `remote origin already exists`.
>     
> - **Пример:**
>     
> ```bash
> git remote set-url origin git@github.com:anton/my-vault.git
> ```
> 
> - **Совет:** После смены URL всегда делай `git remote -v`, чтобы убедиться, что адрес обновился правильно.
>     

> [!NOTE] **3. git remote rename — Наведение порядка**
> 
> Помогает, когда проект разрастается и имен вроде `origin` становится недостаточно.
> 
> - **Синтаксис:** `git remote rename <old-name> <new-name>`
>     
> - **Последствия:** Команда не просто меняет имя в конфиге, она переименовывает все твои удаленные ветки-отслеживания. Например, `origin/main` превратится в `github/main`.
>     
> - **Пример:**
>     
> ```bash
> git remote rename origin github
> ```
> 
> - **Внимание:** После переименования не забудь обновить свои локальные скрипты или настройки Obsidian, если они опирались на имя `origin`.
>     

> [!DANGER] **4. git remote remove — Разрыв связей**
> 
> Используется, если сервер больше не нужен или был добавлен по ошибке.
> 
> - **Синтаксис:** `git remote remove <name>`
>     
> - **Безопасность:** Эта команда **не удаляет** файлы на твоем диске и **не удаляет** репозиторий на сервере. Она просто заставляет твой локальный Git «забыть» адрес.
>     
> - **Пример:**
>     
> ```bash
> git remote remove temporary-backup
> ```
> 
> - **Результат:** Все удаленные ветки (вроде `temporary-backup/main`) будут удалены из твоего локального списка.
>

### 🧹 3. Гигиена и обновление (Prune & Update)
> [!ABSTRACT] Суть
> Со временем локальная копия репозитория забивается «мусором» — ссылками на ветки, которые в облаке уже удалены. Эти команды позволяют синхронизировать твое представление о сервере с реальным положением дел.
#### 📋 3.1 Сводная таблица команд

| Команда                     | Что делает?                           | Сценарий использования                                                    |
| :-------------------------- | :------------------------------------ | :------------------------------------------------------------------------ |
| `git remote prune origin`   | Удаляет «ветки-призраки»              | Когда кто-то удалил ветку на GitHub, а у тебя она всё еще висит в списке. |
| `git remote update`         | Скачивает данные со **всех** серверов | Когда у тебя несколько удаленных репозиториев (напр. GitHub и GitLab).    |
| `git remote update --prune` | Обновляет и чистит всё разом          | Универсальная команда «сделай мне всё актуально и чисто».                 |
#### 🛠️ 3.2 Подробный разбор
> [!DANGER] **1. git remote prune origin — Борьба с призраками**
> Когда ветка удаляется на сервере, твой локальный Git об этом не узнает автоматически. В списке `git branch -r` она продолжит числиться как «живая».
> 
> * **Проблема:** Накопление сотен удаленных веток, которых физически больше не существует.
> * **Что делает команда:** Проверяет список веток на сервере и удаляет из твоей папки `.git/refs/remotes/origin/` те файлы, которых на сервере больше нет.
> * **Безопасность:** Эта команда **никогда** не удаляет твои локальные ветки (`refs/heads/`). Она чистит только «слепки» удаленных веток.

> [!SETTINGS] **2. git remote update — Массовое обновление**
> Если обычный `git fetch origin` работает только с одним сервером, то `update` проходит по всему списку в твоем конфиге.
> 
> * **Синтаксис:** `git remote update [group]`
> * **Зачем это нужно:** Если ты ведешь проект, который зеркалится на два сервера (например, рабочий GitHub и личный бэкап-сервер), одна эта команда обновит информацию сразу об обоих.
> * **Под капотом:** Git заглядывает в `.git/config`, находит все секции `[remote "..."]` и запускает fetch для каждой.

> [!SUCCESS] **3. git remote update --prune — Идеальное состояние**
> Это комбинация двух предыдущих инструментов. Самая полезная команда для ежедневной рутины.
> 
> * **Логика работы:**
>   1. Идет на все удаленные серверы.
>   2. Скачивает все новые коммиты и ветки.
>   3. Сразу после этого удаляет ссылки на все ветки, которые были удалены на этих серверах.
> * **Результат:** Твой список удаленных веток (`git branch -a`) всегда идеально чист и соответствует реальности.
#### 💡 3.3 Флаг --prune в других командах

Ты можешь не запускать `remote prune` отдельно, а добавить этот флаг к обычному скачиванию данных. Это сэкономит время.
> [!TIP] **Автоматизация чистки**
> Если ты не хочешь каждый раз вспоминать про prune, используй:
> `git fetch --prune`
> Это сделает то же самое: скачает новое и удалит старое за один проход.
> 
> **Настройка «навсегда»:**
> Ты можешь заставить Git всегда делать prune при каждом fetch/pull:
> `git config --global fetch.prune true`
> После этого твой список веток всегда будет чистым сам по себе.

### 💡Глубокая логика (Internals)
