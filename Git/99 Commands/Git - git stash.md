# 📦 git stash

> [!ABSTRACT] **Определение**
> 
> **git stash** — это инструмент для временного сохранения незавершенных изменений (текущего состояния **отслеживаемых** файлов) без создания коммита в истории ветки. Это позволяет быстро получить «чистое» состояние проекта для переключения на другую задачу. Она создает набор специальных коммитов, которые не принадлежат ни одной ветке, и сохраняет их в локальном стеке.

---
### 🛠️ Флаги и команды в таблице

| **Команда / Флаг**           | **Описание**                                                              | **Пример**                             |
| ---------------------------- | ------------------------------------------------------------------------- | -------------------------------------- |
| `push`                       | Современный стандарт создания сташа. Позволяет указывать пути.            | `git stash push -m "work in progress"` |
| `list`                       | Показать весь список накопленных сташей.                                  | `git stash list`                       |
| `pop`                        | Применить последний сташ и **удалить** его из списка.                     | `git stash pop`                        |
| `apply`                      | Применить сташ, но **оставить** его в списке.                             | `git stash apply stash@{2}`            |
| `drop`                       | Безвозвратно удалить конкретный сташ из списка.                           | `git stash drop stash@{0}`             |
| `-u` (`--include-untracked`) | Сохранить вместе с изменениями еще и новые (неотслеживаемые) файлы.       | `git stash -u`                         |
| `-a` (`--all`)               | Сохранить всё: отслеживаемые, неотслеживаемые и даже игнорируемые файлы.  | `git stash -a`                         |
| `-p`                         | Интерактивный режим (выбор конкретных строк/ханков).                      | `git stash -p`                         |
| `--keep-index`               | Сохраняет изменения в сташ и не очищает изменения, которые были в индексе | `git stash --keep-index`               |

### 🔍 Ответы на технические вопросы

> [!QUESTION] **1.** `git stash push` **vs обычный** `git stash`
> Раньше использовалась команда `git stash save`. Команда `push` пришла ей на смену и стала дефолтным поведением.
>- **Главное отличие:** `push` поддерживает **pathspec**. Это значит, что ты можешь засташить не всё сразу, а конкретные файлы: `git stash push -m "fix" script.py`. Обычный `save` или просто `git stash` этого не умеют (они всегда берут всё дерево).

> [!QUESTION] **2. Что под капотом? (Index vs Working Directory)**
>Под капотом сташ — это не просто «копия папки». Git создает **специальные коммиты**, которые не принадлежат ни одной ветке.
>- **Реализация:** Когда ты делаешь сташ, Git создает **два (или три) объекта коммита**:
>    1. **Один коммит** хранит состояние Индекса (Staging Area).
>    2. **Второй коммит** хранит состояние Рабочей директории (Working Tree).
>    3. (Опционально) Третий коммит для untracked-файлов.
>- **STASH хранится только ЛОКАЛЬНО:** Ссылки на эти коммиты хранятся в файле `.git/refs/stash`, который ведет себя как лог (reflog).
>- **Ответ на твой вопрос:** Сохраняются изменения **и из индекса, и из рабочего каталога**. Но при `apply` по умолчанию Git пытается развернуть всё в рабочий каталог. Чтобы восстановить еще и состояние индекса (чтобы файлы снова стали «зелеными»), нужно использовать `git stash apply --index`.

> [!QUESTION] **3. Перенос между ветками**
>- **Как это работает:** Сташ — это глобальная сущность репозитория. Он не привязан к ветке, в которой был создан. Ты можешь сделать сташ в `feature-1`, переключиться в `master` и сделать `apply`. Изменения успешно перейдут.
>- **Удаление:** Если ты используешь `apply`, сташ **остается** в списке `stash list`. Если используешь `pop`, то после успешного применения (без конфликтов) Git автоматически вызовет `drop` и удалит его.

 > [!QUESTION] **4.** `git stash drop` **под капотом**
>- **Нужно ли указывать ID?** Если вызвать просто `git stash drop`, Git удалит самый последний сташ (`stash@{0}`). Если нужно удалить другой — ID обязателен.
>- **Под капотом:** Git просто удаляет запись из рефлога `refs/stash`. Сами объекты коммитов, из которых состоял сташ, остаются в базе данных `.git/objects` как «висячие» (dangling), пока их не удалит сборщик мусора (`git gc`).

> [!QUESTION]  **5.** `git stash branch <name>` **подробно**
>Это очень полезная команда для случаев, когда изменения в сташе слишком сильно разошлись с текущим состоянием ветки и вызывают конфликты при `apply`.
>- **Что она делает:**
>    1. Создает новую ветку `<name>` от того самого коммита, на котором ты **создавал** этот сташ.
>    2. Переключается на эту ветку.
>    3. Применяет изменения сташа (здесь конфликтов не будет, так как база совпадает).
>    4. Если всё прошло успешно — **удаляет** сташ из списка (делает `drop`).
>- **Зачем это:** Чтобы спокойно доделать задачу в отдельной ветке, если в основной ветке код ушел слишком далеко вперед.

> [!QUESTION] **6. Как работает** `git stash push` **с несколькими файлами?**
> 
> При использовании `push` ты можешь перечислить сколько угодно файлов: `git stash push file1.js file2.js path/to/folder/`.
> 
> - **Это создаст ОДИН stash**, в который попадут только эти файлы.
>     
> - Остальные измененные файлы останутся в рабочей директории нетронутыми.
>     
> - Тебе не нужно создавать отдельный сташ для каждого файла (если только ты не хочешь применять их по отдельности).
>     

> [!QUESTION] **7. Что именно сохраняется? (Tracked vs Untracked)**
> 
> Это тонкий момент. В Git файлы в рабочей директории делятся на **отслеживаемые** (modified, deleted, staged) и **нет** (untracked).
> 
> - **По умолчанию:** `stash` берет только **Tracked** файлы (те, что уже были в репозитории, или те, на которых сделали `git add`).
>     
> - **Зачем нужен флаг** `-u`? Без него Git игнорирует новые файлы (untracked), потому что они технически еще не часть проекта. Если ты создал новый файл и хочешь его спрятать — `-u` обязателен.
>     
> - **Структура под капотом:** Когда ты делаешь сташ, Git создает **мини-дерево коммитов**:
>     
>     1. **Коммит C_index:** состояние Индекса.
>         
>     2. **Коммит C_worktree:** состояние Рабочей директории (только отслеживаемые).
>         
>     3. **Коммит C_untracked:** (только если есть `-u`) состояние новых файлов.
>         
>         При `apply` Git берет данные из этих скрытых коммитов и вливает их обратно.
>         

> [!QUESTION] **8. Как добавлять сообщения?**
> 
> Чтобы потом не гадать, что лежит в `stash@{2}`, всегда используй флаг `-m`:
> 
> `git stash push -m "Рефакторинг логики авторизации"`
> 
> Теперь в `git stash list` ты увидишь понятный текст вместо стандартного "WIP on branch...".

### 🌳 git stash branch `<name>` 

> [!INFO] **Зачем это нужно?**
> 
> Бывает так: ты сделал сташ, потом в основной ветке кто-то сильно изменил код. Ты делаешь `apply`, и получаешь гору конфликтов.

**Как команда решает проблему технически:**

1. Git находит **конкретный коммит**, на котором ты стоял, когда создавал этот сташ.
2. Он создает от этого коммита **новую ветку** `<name>`.
3. Поскольку состояние кода в этой новой ветке _идентично_ тому, что было при создании сташа, изменения из сташа применяются **без конфликтов**.
4. После успешного применения сташ удаляется (`drop`).
5. Ты оказываешься в новой ветке, где твои изменения наложены на "родной" для них фундамент.

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про Stash**
> 
> **1. В чем разница между** `pop` и `apply`?
> 
> - `apply` — применяет изменения, сташ остается в списке (безопасно).
>     
> - `pop` — применяет изменения и сразу удаляет сташ из списка (удобно, но если возникнут конфликты, сташ может не удалиться сразу).
>     
> ---
> **2. Как применить изменения, сохранив их статус в Индексе?**
> 
> - По умолчанию `apply` всё вываливает в "красную" зону (Working Directory). Чтобы вернуть "зеленые" файлы (Staged), нужно использовать `git stash apply --index`.
>     
> ---
> **3. Что будет со сташем, если я удалю ветку, на которой его создал?**
> 
> - Ничего. Сташ не привязан к ветке. Он будет существовать, пока ты не сделаешь `drop` или `clear`.
>     
> ---
> **4. Как посмотреть, что именно лежит внутри конкретного сташа, не применяя его?**
> 
> - Использовать `git stash show -p stash@{0}`. Флаг `-p` (patch) покажет полный diff изменений.
>     
> ---
> **5. Что делать, если сделал** `stash pop`**, возникли конфликты, и сташ пропал из списка?**
> 
> - На самом деле при конфликтах `pop` ведет себя как `apply` и **не удаляет** сташ, пока конфликты не будут решены. Но если вы его всё же потеряли, его хеш можно найти в `git reflog`.
>---
> **6. «Можно ли сделать stash только части изменений в файле?»**
>
> - _Ответ:_ Да, через `git stash push -p` (patch mode). Ты сможешь интерактивно выбрать конкретные строки кода для сохранения.
>---
> **7. «Как восстановить сташ, который был удален по ошибке через** `drop` **или** `pop`?**»**
> - _Ответ:_ Нужно найти его хеш через `git fsck --unreachable` или `git reflog` (если это было недавно), а затем применить его напрямую через `git stash apply <hash>`.
>---
> **8. «Если я сделал** `stash apply`**, почему файлы в статусе стали все красные, хотя до сташа часть была в индексе (зеленые)?»**
> 
> - _Ответ:_ Потому что по умолчанию `apply` не восстанавливает индекс. Нужно использовать флаг `git stash apply --index`.
> ---
> **9. «Конфликтует ли stash с файлом .gitignore?»**
>   
> - _Ответ:_ По умолчанию — нет (сташ не берет игнорируемые файлы). Но если использовать `git stash -a` (`--all`), то в сташ попадут даже файлы, прописанные в `.gitignore`.
