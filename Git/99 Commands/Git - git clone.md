# 📥 git clone

> [!ABSTRACT] Суть
> Команда копирует существующий Git-репозиторий. Она автоматически создает удаленное отслеживание (remote) под именем `origin`, скачивает все данные и переключается (checkout) на основную ветку (обычно `main` или `master`).

---

> [!INFO] 🔍 1. Базовый синтаксис
> | № | Команда | Описание | Примеры |
> | :-- | :--- | :--- | :--- |
> | 1 | `git clone <url>` | Создает папку с именем репозитория и скачивает всё содержимое. | `git clone https://github.com/user/repo.git`
> | 2 | `git clone <url> <dir>` | Скачивает репозиторий в папку с выбранным именем `<dir>`. | `git clone https://... MyFolder` |
> | 3 | `git clone . <dir>` | Клонирование из локальной папки (путь `.` или путь к диску). | `git clone /D/MyRepo MyCopy` |

> [!EXAMPLE] 🌿 2. Работа с ветками и глубиной
> | № | Флаг | Описание | Примеры |
> | :-- | :--- | :--- | :--- |
> | 1 | `-b <name>` | **Branch.** Сразу после клонирования переключается на указанную ветку.<br>**Пример:** скачает всё, но **сразу переключит** тебя на ветку `develop`. | `git clone --branch develop https://github.com/user/repo.git` |
> | 2 | `--single-branch` | Скачивает историю **только** одной ветки (экономит место).<br>**Пример:** скачает **только** ветку `develop`. Историю других веток Гит даже не тронет. | `git clone -b develop --single-branch https://github.com/user/repo.git` |
> | 3 | `--depth <N>` | **Shallow clone.** Скачивает только последние `<N>` коммитов (без всей истории).<br>**Пример:** Скачает только **последнее состояние** (последний коммит). | `git clone --depth 1 https://github.com/user/repo.git` |

# 🏗️ Анатомия git clone: Что происходит «под капотом»

> [!ABSTRACT] Суть
> 
> Когда ты вводишь одну команду `git clone`, Git на самом деле запускает цепочку внутренних процессов, превращая пустую папку в полноценный репозиторий.

> [!attention]  Git «под капотом» выполняет следующие шаги: 
> 1. `git init`: Создает новую локальную директорию и инициализирует в ней пустой репозиторий. 
> 2. `git remote add origin <url>`: Настраивает связь с удаленным сервером. 
> 3. `git fetch origin`: Скачивает все объекты (коммиты, файлы) и обновляет удаленные ветки (`refs/remotes/origin/`). 
> 4. `git checkout`: Извлекает файлы из базы данных в твою рабочую директорию.
### 📂 Этап 1: Инициализация (git init)
Git создает «скелет» будущего репозитория.
> [!INFO] **Шаг 1: Создание структуры**
> 
> Создается скрытая директория `.git/`, которая станет базой данных. На этом этапе папка пуста, но в ней уже прописаны основные указатели:
> 
> Plaintext
> 
> ```
> .git/
> ├── objects/    # Будущее хранилище сжатых данных
> ├── refs/       # Указатели на ветки и теги
> └── HEAD        # Файл, указывающий на текущую ветку
> ```
### 📖 Этап 2: Адресная книга (git remote add origin)
Git фиксирует, откуда именно он будет брать данные.
> [!SETTINGS] **Шаг 2: Настройка связи**
> 
> Прописывается связь с удаленным сервером под стандартным именем `origin`. Эта настройка сохраняется в текстовом конфиге:
> 
> Bash
> 
> ```
> # Информация записывается в:
> .git/config
> ```
### 📦 Этап 3: Транспортировка (git fetch origin)
Самый тяжелый этап: физическое перемещение данных.
> [!DOWNLOAD] **Шаг 3: Наполнение базы данных**
> 
> 1. **Соединение:** Git связывается с сервером по URL.
>     
> 2. **Сравнение:** Вычисляет, какие объекты (коммиты, файлы) нужно передать.
>     
> 3. **Загрузка:** Скачивает данные в виде **pack-файлов** (сжатых бинарных пакетов).
>     
> 4. **Индексация:** Распаковывает их во внутреннее хранилище.
>     
> 
> **В итоге в** `.git/objects/pack/` **появляются:**
> - `pack-xxxx.pack` — сами данные.
> - `pack-xxxx.idx` — индекс для быстрого поиска внутри пакета.
>     
> 
> **Создается «тень» удаленной ветки:**
> 
> `refs/remotes/origin/main → <hash>`
### 🛠️ Этап 4: Материализация (git checkout main)
Превращение бинарных данных в файлы, которые ты можешь редактировать.
> [!SUCCESS] **Шаг 4: Развертывание в Worktree**
> 
> Теперь, когда база данных наполнена, Git нужно «вытащить» файлы на диск:
> 
> 1. **Связь веток:** Создает локальную ветку `main` и привязывает её к `origin/main`.
>     
> 2. **Чтение дерева:** Берет `tree` объект нужного коммита (снимок файловой структуры).
>     
> 3. **Распаковка:** Читает **blob-объекты** (содержимое файлов) из папки `.git/objects`.
>     
> 4. **Запись:** Физически записывает их в твою рабочую директорию.
>     
> 
> > [!IMPORTANT] Резюме
> > 
> > На этом этапе Git **не скачивает** данные из интернета, а **извлекает** их из локальной базы, которую наполнил `fetch`.

# 🔐 Права доступа и Push после клонирования

> [!WARNING] **Тонкий нюанс**
> Наличие кода на диске после `clone` не означает, что у тебя есть право его менять на сервере. Нужно различать техническую «связку» веток и «разрешение» на запись.

### 🛡️ 1. Как клонировать, чтобы сразу пушить?
Лучший способ — использовать **SSH**. Если твой ключ добавлен на GitHub, авторизация произойдет автоматически.
* **Команда:** `git clone git@github.com:username/repo.git`
* **Плюс:** Не нужно вводить пароль или токены.

### 🔑 2. Если клонировал через HTTPS
Гит будет запрашивать авторизацию при каждой попытке `push`.
* **Что нужно:** Вместо пароля используй **Personal Access Token (PAT)**.
* **Чтобы не вводить каждый раз:**
  `git config --global credential.helper store` (сохранит токен в системе).

### 🛠️ 3. Как исправить клон без прав (Fork Workflow)
Если ты клонировал чужой проект и `push` выдает ошибку `403 Forbidden`:
1. Сделай **Fork** проекта в свой аккаунт на сайте.
2. Переподключи локальный репозиторий к своему форку одной командой:
   `git remote set-url origin git@github.com:YOUR_NAME/repo.git`
3. Теперь ты можешь пушить в свою копию!

---
### ⚠️ Нюанс про `--branch`

Многие думают, что `git clone -b <name>` скачивает *только* одну ветку. **Это не так.** * По умолчанию Git всё равно скачает **всю историю всех веток**, но после завершения просто автоматически сделает `checkout` на ту ветку, которую ты указал.
* Чтобы действительно сэкономить трафик и время, нужно комбинировать флаги:
  `git clone -b <name> --single-branch <url>`

# 📥 git clone: Продвинутые режимы

### 🏗️ 3. Клонирование без рабочей директории

В некоторых случаях нам не нужны файлы для редактирования, а нужна только сама база данных (история, ветки, теги). Для этого существуют специальные флаги.

|**№**|**Флаг**|**Описание**|**Примеры**|
|---|---|---|---|
|1|`--bare`|**Bare repository.** Создает «голый» репозиторий. В нем нет рабочей директории (файлов), только содержимое папки `.git`.|`git clone --bare <url>`|
|2|`--mirror`|**Mirroring.** «Супер-bare» режим. Копирует абсолютно все ссылки (refs) и настраивает удаленное отслеживание так, чтобы `git remote update` полностью синхронизировал все данные.|`git clone --mirror <url>`|

---

### 🔍 Глубокий разбор: --bare vs --mirror

> [!INFO] **Зачем нужен **`--bare`**?**
> 
> «Голые» репозитории используются на серверах. Когда ты пушишь код на GitHub, он попадает именно в `bare` репозиторий.
> 
> В нем нельзя сделать `git commit` или `git status`, потому что там **нет файлов на диске** — только база объектов. Это защищает сервер от конфликтов слияния и экономит место.
#### Техническое отличие в структуре:

В обычном репозитории всё хранится в скрытой папке `.git/`. В `bare` репозитории **сама корневая папка** является тем, что обычно лежит в `.git/`. По стандарту такие папки называют с расширением `.git` (например, `my-project.git`).

#### В чем особенность `--mirror`?

1. **Все ссылки:** Клонирует не только ветки, но и скрытые ссылки (notes, дополнительные атрибуты).
2. **Настройка Remote:** В конфиге прописывается `fetch = +refs/*:refs/*`, что заставляет Git при обновлении принудительно перезаписывать локальные данные удаленными, делая репозиторий точной копией (зеркалом) сервера.
3. **Автоматический Bare:** Флаг `--mirror` автоматически включает в себя `--bare`.

# 🏗️ Анатомия git clone: Что происходит «под капотом»

> [!attention] **Как меняется процесс при использовании **`--bare`**?**
> 
> Если при обычном клонировании Git выполняет 4 этапа (Init -> Remote -> Fetch -> Checkout), то при `bare` клонировании **Этап 4 (Checkout) полностью пропускается**.
> 
> База данных наполняется объектами, но Git не «материализует» их в файлы. Указатель `HEAD` в таком репозитории указывает не на ветку в рабочем дереве, а непосредственно на текущую ветку в базе данных.

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про клонирование**
> 
> **1. Можно ли превратить обычный репозиторий в bare и наоборот?**
> 
> - **Ответ:** Да. Чтобы сделать из обычного `bare`, нужно переместить содержимое папки `.git` в корень и выполнить `git config --bool core.bare true`. Для обратного процесса — создать папку, переместить туда данные и поставить `core.bare false`, после чего сделать `git checkout`.
>     
> 
> ---
> 
> **2. Почему нельзя пушить (push) в обычный (не bare) репозиторий, в ту ветку, которая там сейчас открыта?**
> 
> - **Ответ:** Потому что Git не сможет автоматически обновить рабочую директорию другого пользователя. Это приведет к рассинхронизации индекса и файлов на диске. Поэтому серверные репозитории **всегда** должны быть `bare`.
>     
> 
> ---
> 
> **3. В чем разница между** `git clone --depth 1` **и обычным клоном с точки зрения **`--bare`**?**
> 
> - **Ответ:** Вы можете сделать «голый» клон с ограниченной глубиной. Это часто используется в CI/CD пайплайнах, когда нам нужно быстро проанализировать метаданные или историю последних коммитов без развертывания файлов на диске.
>     
> 
> ---
> 
> **4. Если я клонировал репозиторий через** `--mirror`**, смогу ли я в нем работать?**
> 
> - **Ответ:** Нет, так как это `bare` репозиторий. Вам придется клонировать его еще раз (уже нормально) из этой локальной папки, чтобы получить рабочее дерево.
>

# 🪞 git clone --mirror

> [!ABSTRACT] **Техническая суть**
> 
> Опция `--mirror` создает «зеркальный» bare-репозиторий. Главное отличие от `--bare` заключается в том, что зеркало отображает **абсолютно все** ссылки (refs) источника один-в-один, включая заметки (notes), атрибуты и, что самое важное, удаленные ветки других разработчиков.

---

### 📊 Сравнение типов клонирования

| **Характеристика**             | **git clone (Standard)**     | **git clone --bare**   | **git clone --mirror**             |
| ------------------------------ | ---------------------------- | ---------------------- | ---------------------------------- |
| **Рабочая директория**         | ✅ Есть                       | ❌ Нет                  | ❌ Нет                              |
| **Ветки** (`refs/heads/*`)     | ✅ Копирует                   | ✅ Копирует             | ✅ Копирует                         |
| **Теги** (`refs/tags/*`)       | ✅ Копирует                   | ✅ Копирует             | ✅ Копирует                         |
| **Другие ссылки (notes, etc)** | ❌ Нет                        | ❌ Нет                  | ✅ **Копирует всё**                 |
| **Удаленные ветки источника**  | ❌ Превращает в `remotes/`    | ❌ Только локальные     | ✅ **Копирует как есть**            |
| **Логика Fetch**               | Обновляет `remotes/origin/*` | Не настраивает `fetch` | **Настраивает 1:1 зеркалирование** |

---
### ⚙️ Магия конфига: Почему это «Зеркало»?

Секрет `--mirror` кроется в файле `.git/config` (в случае зеркала — это просто файл `config` в корне папки).

#### 1. У обычного репозитория (или bare):
```Ini, TOML
[remote "origin"]
    url = https://github.com/user/repo.git
    fetch = +refs/heads/*:refs/remotes/origin/*
```

_Гит говорит:_ «Возьми ветки из источника и положи их в мой раздел "удаленных" веток».

#### 2. У зеркала (`--mirror`):
```Ini, TOML
[remote "origin"]
    url = https://github.com/user/repo.git
    fetch = +refs/*:refs/*
    mirror = true
```

_Гит говорит:_ «Возьми **вообще всё** (ветки, теги, заметки, скрытые ссылки) и положи это в мой раздел ссылок **точно так же**, без приставки `remotes/origin/`».

> [!IMPORTANT] **Результат**
> 
> Любой запуск `git fetch` в зеркальном репозитории будет принудительно перезаписывать все ваши локальные ссылки на те, что сейчас на сервере. Это и есть эффект зеркала.

---
### 🚀 Главный сценарий: Миграция (Step-by-Step)

Если тебе нужно перенести проект со всеми ветками и тегами из GitLab в GitHub, `clone --mirror` — единственный надежный путь.

1. **Клонируем зеркало из старого места:**
    
    `git clone --mirror https://gitlab.com/old-user/project.git`
    _(Создастся папка `project.git` со всей базой данных)._
    
2. **Заходим в репозиторий:**
    
    `cd project.git`
    
3. **Меняем адрес "выхода" (Push URL):**
    
    `git remote set-url --push origin https://github.com/new-user/project.git`
    
4. **Пушим всё зеркало целиком:**
    
    `git push --mirror`
    _(На новый сервер улетят все ветки, теги и метаданные)._

---

### ❓ Вопросы на собеседовании

> [!QUESTION] **1. В чем главная опасность **`git push --mirror`**?**
> 
> **Ответ:** Эта команда делает целевой репозиторий **точным** соответствием локальному. Если в локальном зеркале нет какой-то ветки, которая есть на сервере — **она будет удалена на сервере**. Это деструктивная операция, которую нужно использовать только при миграции или восстановлении из бэкапа.

> [!QUESTION] **2. Чем отличается** `git push --mirror` **от** `git push --all`**?**
> 
> **Ответ:** `--all` отправляет только **все ветки**. `--mirror` отправляет вообще всё: ветки, теги и любые другие объекты в `refs/`, а также удаляет на сервере то, чего нет локально.

> [!QUESTION] **3. Почему нельзя работать (делать коммиты) в зеркальном репозитории?**
> 
> **Ответ:** Потому что это `bare` репозиторий (нет файлов). Но даже если бы вы смогли, любой `fetch` затрет ваши изменения, так как логика зеркала — всегда соответствовать источнику.

---
### 💡 Резюме для интервьюера

>[!info] Флаг `--mirror` превращает репозиторий в пассивный слепок источника. Технически это достигается за счет изменения `refspec` на `+refs/*:refs/*`. Я использую этот флаг для двух задач:
> 
> 1. Автоматизированные бэкапы репозиториев.
>     
> 2. Бесшовная миграция проектов между хостингами, когда важно сохранить не только код, но и все релизные теги и историю всех веток».

# 🚀 Git Clone --recursive: Всё в одном флаконе

### 📖 Что это такое?

Это «комбо-команда», которая позволяет клонировать основной репозиторий и **сразу** наполнить все вложенные сабмодули. Без этого флага вместо кода библиотек ты получишь просто пустые папки.

### 🛠 Синтаксис

**Классический вариант:**

`git clone --recursive <url>`

**Современный (рекомендуемый) вариант:**

`git clone --recurse-submodules <url>`

_Они идентичны, но второй вариант считается более «говорящим» в свежих версиях Git._

**Для фанатов скорости (DevOps-стиль):**

`git clone --recurse-submodules -j 8 <url>`

_Флаг `-j 8` заставляет Git качать сабмодули в 8 потоков одновременно. На больших проектах ускоряет процесс в разы._

---

### ❓ Зачем это нужно?

В обычном `git clone` объекты сабмодулей **не передаются**. Сервер основного репозитория хранит только ссылки. Если ты забудешь про рекурсию, проект просто не соберется, так как зависимости будут отсутствовать.

### 📅 Когда используется?

1. **Первый запуск проекта:** Когда ты только пришел в компанию и разворачиваешь окружение.
    
2. **CI/CD Пайплайны:** Чтобы сборочный сервер (Runner) сразу получил весь код, необходимый для компиляции.
    
3. **Infrastructure as Code:** Клонирование репозиториев с Terraform-планами, где модули подключены как сабмодули.

### ⚙️ Алгоритм действий Git (Внутренняя кухня)

Когда ты нажимаешь Enter, Git выполняет цепочку действий, эквивалентную ручному труду:

|**Этап**|**Что делает Гит (аналог команды)**|**Результат**|
|---|---|---|
|**1. Корень**|`git clone <url>`|Скачивается основной проект. Появляется `.gitmodules`.|
|**2. Регистрация**|`git submodule init`|Git читает `.gitmodules` и прописывает пути в локальный `.git/config`.|
|**3. Доставка**|`git submodule update`|Git видит, что хэшей нет локально. Он идет по URL сабмодулей, **скачивает объекты** и кладет их в `.git/modules/`.|
|**4. Сборка**|`git checkout <hash>`|В папках сабмодулей появляются файлы, а сами они переходят в **Detached HEAD** на нужные коммиты.|
|**5. Глубина**|`--recursive` (флаг)|Если внутри сабмодуля есть свои сабмодули, Git повторяет шаги 2–4 для них.|

---

> [!TIP] **DevOps-совет для 2026 года**
> 
> Если ты работаешь в GitLab CI, вместо прописывания команд руками в `before_script`, просто добавь переменную окружения:
> 
> `variables: GIT_SUBMODULE_STRATEGY: recursive`.
> 
> Это заставит раннер сам использовать правильные флаги при клонировании.
