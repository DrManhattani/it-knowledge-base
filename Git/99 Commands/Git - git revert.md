# 🔄 git revert

> [!ABSTRACT] **Определение**
> 
> **git revert** — это команда, которая отменяет изменения существующего коммита, создавая **новый коммит** с противоположными изменениями. Она не удаляет коммит из истории, а «вычитает» его влияние из текущего состояния.

---

### 🏗️ Техническая механика (Как это работает)

В отличие от `reset`, который перемещает указатель ветки назад, `revert` всегда идет только вперед.

1. Git вычисляет разницу (diff), внесенную целевым коммитом.
2. Он создает **инвертированный патч** (если в коммите строка была добавлена, revert её удалит).
3. Этот патч накладывается на текущее состояние рабочей директории и индекса.
4. Создается новый коммит.
---

### 🛠️ Таблица флагов и вариантов использования

| **Флаг / Параметр**  | **Описание**                                                                        | **Пример**               |
| -------------------- | ----------------------------------------------------------------------------------- | ------------------------ |
| `<hash>`             | Отменить конкретный коммит в истории.                                               | `git revert a1b2c3d`     |
| `-n` (`--no-commit`) | Применяет инвертированные изменения к индексу и WD, но **не создает** коммит сразу. | `git revert -n HEAD`     |
| `-m` (`--mainline`)  | Необходим для отмены **Merge-коммитов**. Указывает номер родительской ветки.        | `git revert -m 1 <hash>` |
| `-e` (`--edit`)      | Открывает редактор для изменения стандартного сообщения об откате.                  | `git revert -e <hash>`   |

### 🔍 Ответы на технические вопросы

> [!QUESTION] **1. В чем фундаментальная разница между Reset и Revert?**
> 
> - **Reset:** Изменяет указатель ветки, «удаляя» коммиты из видимой истории. Подходит для локальной работы. Требует `force push`.
>     
> - **Revert:** Добавляет новый коммит. История остается линейной и понятной для коллег. Идеально для **публичных веток** (main, develop).
>     

> [!QUESTION] **2. Как отменить сразу несколько коммитов?**
> 
> Есть два способа:
> 
> 1. `git revert A..B` — создаст цепочку отдельных коммитов-откатов. 
>	- **Плюс:** В истории четко видно отмену каждой отдельной правки. 
>	- **Минус:** Засоряет `git log`, если в фиче было 20 коммитов.
>     
> 2. `git revert -n A..B` — применит все инвертированные патчи к **Индексу** и **Рабочей директории**, но **не будет делать коммиты.**
>     

> [!QUESTION] **3. Что такое Reverting a Merge и почему это сложно?**
> 
> Merge-коммит имеет двух родителей. Git не знает, какую сторону слияния считать «главной».
> 
> - **Решение:** Флаг `-m 1`. Это говорит Гиту: «Верни всё к состоянию первой родительской ветки (обычно той, В КОТОРУЮ вливали)».
>     
> - **Последствие:** Если ты позже захочешь снова влить ту же ветку, Git решит, что изменения уже там были (и были отменены), и не добавит их снова. Придется «ревертнуть реверт».
>

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про Revert**
> 
> **1. Когда ты выберешь** `revert` **вместо** `reset`**?**
> 
> - _Ответ:_ Как только коммит попал в удаленный репозиторий (`push`), `reset` становится опасным, так как он ломает историю коллегам. В этом случае только `revert`.
>     
> 
> ---
> 
> **2. Можно ли сделать** `revert` **коммита из середины истории?**
> 
> - _Ответ:_ Да. Git попробует применить обратный патч к текущему состоянию. Если строки, которые менял тот коммит, были затронуты позже, возникнет **конфликт слияния**, который нужно будет решить вручную.
>     
> 
> ---
> 
> **3. Что будет с историей, если я сделаю** `revert` **последнего коммита?**
> 
> - _Ответ:_ В `git log` появится новая запись (например, "Revert 'Fix bug'"). Общее количество коммитов увеличится на один, но состояние файлов будет идентично предпоследнему коммиту.
>     
> 
> ---
> 
> **4. Можно ли отменить** `revert`**?**
> 
> - _Ответ:_ Да, выполнив `git revert` на сам коммит отката. Это часто называют "rolling forward".
>     
> 
> ---
> 
> **5. Повлияет ли** `revert` **на другие ветки?**
> 
> - _Ответ:_ Только если ты вольешь (merge/pull) ветку с ревертом в другие ветки. Сам по себе он локален для текущей ветки.
>     
Разбор команды `git revert` для диапазона коммитов — это «высший пилотаж» в понимании того, как Git раскручивает историю назад. Главная путаница здесь обычно возникает в **порядке действий** и в том, **какие именно коммиты** попадают в выборку.

> [!QUESTION] **1. Что будет, если в середине диапазона** `A..B` **затесался Merge-коммит?**
> 
> **Ответ:** Команда остановится с ошибкой. Реверт мерж-коммита требует флага `-m` (mainline), чтобы Гит знал, какую сторону слияния сохранять. При массовом реверте Гит не знает, какой `-m` применять к каждому встречному мержу, поэтому он потребует ручного вмешательства.

> [!QUESTION] **2. Как включить коммит A в отмену (сделать диапазон инклюзивным)?**
> 
> **Ответ:** Нужно использовать синтаксис `A^..B` (тильда или каретка означает «родитель А»). Тогда отмена начнется с самого коммита A.

> [!QUESTION] **3. Что делать, если на третьем коммите из десяти возник конфликт?**
> 
> **Ответ:** Git остановит процесс. Тебе нужно:
> 
> 1. Разрешить конфликт вручную.
>     
> 2. Сделать `git add <file>`.
>     
> 3. Выполнить `git revert --continue`. Git продолжит отменять оставшиеся коммиты в списке.
>     

> [!QUESTION] **4. Можно ли отменить диапазон, который уже был когда-то ревертнут?**
> 
> **Ответ:** Да, это называется "re-reverting". Технически это просто применение патча. Git всё равно, что именно он отменяет, он просто вычисляет разницу.

### 🏗️ Сценарий: Revert Merge (Technical Breakdown)

Представь ситуацию: ты влил ветку `feature` в `main`, и всё сломалось.

1. Находим хеш мерж-коммита.
2. Выполняем `git revert -m 1 <hash>`.
3. Git смотрит на родителя №1 (старый `main`) и приводит всё к его виду.
4. В истории появляется коммит «отмена слияния».

---
### 💡 Резюме для интервьюера

> «`git revert` — это инструмент профессиональной ответственности. В общих ветках мы никогда не переписываем историю через `reset`, так как это создает хаос. Мы используем `revert`, чтобы прозрачно зафиксировать: "Здесь была ошибка, и вот этот коммит её исправляет". Это сохраняет целостность репозитория и позволяет любому разработчику понять, почему код изменился».
