# 🕵️ git bisect

> [!ABSTRACT] **Определение**
> 
> `git bisect` — это инструмент для поиска коммита, который внес ошибку (баг), с помощью алгоритма бинарного поиска. Команда автоматически переключает состояние репозитория между «хорошим» (где бага нет) и «плохим» (где баг есть) коммитами, пока не вычислит виновника.

---
### 🏗️ Алгоритм работы (Workflow)

Представь, что у тебя 1000 коммитов между последней стабильной версией и текущей, где всё сломалось. Вручную проверять каждый — безумие. `git bisect` сделает это максимум за 10 шагов ($\log_2 1000 \approx 10$).

1. `git bisect start` — запуск процесса.
2. `git bisect bad` — помечаем текущий коммит как «сломанный» (обычно это HEAD).
3. `git bisect good <hash>` — указываем хеш или тег, где всё точно работало.
4. **Процесс:** Git переключит тебя на коммит посередине. Ты проверяешь код (запускаешь тесты или приложение).
    - Если баг есть: пишешь `git bisect bad`.
    - Если бага нет: пишешь `git bisect good`.
5. **Финал:** Git назовет хеш первого «плохого» коммита.
6. `git bisect reset` — возвращение в исходное состояние (на ту ветку, где ты был до начала поиска).

---
### 🛠️ Команды и автоматизация

| **Команда**               | **Описание**                                                                 |
| ------------------------- | ---------------------------------------------------------------------------- |
| `git bisect start`        | Инициализация режима поиска.                                                 |
| `git bisect good/bad`     | Маркировка текущего состояния.                                               |
| `git bisect skip`         | Пропустить коммит (если он не собирается или не относится к делу).           |
| `git bisect visualize`    | Показать оставшиеся подозрительные коммиты в графическом интерфейсе.         |
| `git bisect run <script>` | **Автоматический поиск.** Запускает скрипт на каждом шаге и сам ищет баг.    |
| `git bisect reset`        | возвращение в исходное состояние (на ту ветку, где ты был до начала поиска). |

---
### 🚀 Автоматизация через `git bisect run`

Это уровень Senior. Если у тебя есть автоматический тест (например, `npm test` или python-скрипт), который падает на баге, ты можешь найти виновника, пока пьешь кофе:

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.0
git bisect run pytest tests/test_bug.py
```

Git будет сам переключать коммиты. Если скрипт вернул `0` — коммит «хороший», если от `1` до `127` — «плохой».

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про поиск багов**
> 
> **1. Какова сложность алгоритма** `git bisect`?
> 
> - **Ответ:** $O(\log n)$, где $n$ — количество коммитов в диапазоне. Это классический бинарный поиск.
>     
> 
> ---
> 
> **2. Что делать, если коммит, на который меня переключил** `bisect`**, не компилируется?**
> 
> - **Ответ:** Использовать `git bisect skip`. Git выберет соседний коммит для проверки.
>     
> 
> ---
> 
> **3. Можно ли найти коммит, который наоборот — исправил баг?**
> 
> - **Ответ:** Да. В новых версиях можно использовать термины `old` и `new` вместо `good` и `bad`, чтобы не путаться в логике: `git bisect start --term-old=fixed --term-new=broken`.
>     
> 
> ---
> 
> **4. Что будет, если багов было два, и они внесены в разное время?**
> 
> - **Ответ:** `bisect` найдет **первый** коммит, который приводит к «плохому» состоянию в контексте твоего теста. Для поиска второго бага процедуру придется повторить после исправления первого.
>     
> 
> ---
> 
> **5. Остается ли репозиторий в состоянии «bisecting», если закрыть терминал?**
> 
> - **Ответ:** Да. Состояние хранится в папке `.git`. Пока ты не напишешь `git bisect reset`, ты будешь находиться в режиме поиска (в состоянии Detached HEAD).
>

### 🎙️ Как ответить на собеседовании?

> «Для поиска регрессий я всегда использую `git bisect`. Это экономит часы ручной работы. Самый эффективный способ — написать минимальный скрипт, воспроизводящий баг, и запустить его через `git bisect run <script>`. Это гарантирует математическую точность поиска и исключает человеческий фактор при проверке промежуточных состояний кода».
