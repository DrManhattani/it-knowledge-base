# 🔄 git rebase

> [!ABSTRACT] **Определение (Interview-ready)**
> **git rebase** — один из способов объединить изменения, сделанные в одной ветке, с другой веткой. Это наложение коммитов поверх другого базового коммита. Под базовым понимается тот коммит, к которому применяются коммиты выбранной ветки.
---

> [!SETTINGS] **Синтаксис и структура**
>
> ### 📘 Формальное описание (POSIX/Man-style)
>
> ```text
> git rebase [-i | --interactive] [<options>] [--onto <newbase>] [<upstream> [<branch>]]
> git rebase --continue | --skip | --abort | --edit-todo
> ```
> 
> ### 📋 Детальный разбор параметров
>
> | Элемент | Техническое описание | Роль в операции |
> | :--- | :--- | :--- |
> | `<upstream>` | **Новая база** | Ветка или коммит, на который вы хотите "пересадить" свою работу (например, `main`). |
> | `[<branch>]` | **Целевая ветка** | Ветка, которую нужно переместить. Если не указана, перемещается текущая (HEAD). |
> | `--onto` | **Суржикальная пересадка** | Позволяет перенести диапазон коммитов с одной базы на другую, игнорируя промежуточные звенья. |
> | `-i` | **Интерактивный режим** | Открывает редактор для изменения истории (объединение, переименование, удаление коммитов). |

### 🏷️ Разбор процесса и вывода

#### 📋 Пример интерактивного списка (TODO list)
При запуске `git rebase -i HEAD~3` откроется редактор:

```text
pick a1b2c3d Add initial model logic
pick e5f6g7h Fix small bug in preprocessing
pick i9j0k1l Update README

# Rebase a1b2c3d..i9j0k1l onto z9y8x7w
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# s, squash <commit> = use commit, but meld into previous commit
```

#### 🔍 Статусы во время операции

| **Статус в терминале** | **Техническая интерпретация**                                                   |
| ---------------------- | ------------------------------------------------------------------------------- |
| `Applying: <message>`  | Git успешно создал новый объект коммита с вашими изменениями поверх новой базы. |
| `Stopped at <hash>...` | Конфликт. Git не может автоматически применить патч. Требуется вмешательство.   |
| `Successfully rebased` | Операция завершена. Указатель вашей ветки теперь на новом "кончике" истории.    |

### 🏗️ Внутренняя логика (How it works под капотом)

1. **Isolation:** Git определяет список коммитов, которые есть в текущей ветке, но отсутствуют в `<upstream>`.
2. **Temporary Storage:** Эти коммиты временно сохраняются (аналогично `stash`).
3. **Reset:** Текущая ветка сбрасывается (`reset --hard`) на коммит `<upstream>`.
4. **Re-application:** Git берет каждый сохраненный коммит и по очереди применяет его как новый патч.
5. **New Hashes:** Поскольку база изменилась, каждый коммит получает **новый SHA-1 хеш**. Старые коммиты позже удаляются сборщиком мусора (GC).

### 🛠️ Сценарии и "Золотое правило"

> [!DANGER] **Золотое правило Rebase**
> 
> **Никогда не делай rebase веток, которые уже запушены в общий доступ (public branches).** Это сломает историю всем остальным разработчикам, так как хеши изменятся. Используй rebase только для своих локальных фиче-веток перед мерджем.

> [!EXAMPLE] **Подготовка ветки к Pull Request (Squash)**
> 
> Чтобы превратить 10 "мусорных" коммитов в один красивый:
> 
> 
> ```bash
> git rebase -i main
> # В редакторе заменить 'pick' на 'squash' для всех коммитов, кроме первого.
> ```

> [!EXAMPLE] **Актуализация фичи (Linear update)**
> 
> Чтобы подтянуть новые изменения из main в свою ветку без лишнего merge-коммита:
> 
> ```bash
> git checkout feature
> git rebase main
> ```

# ✂️ git rebase --onto

> [!ABSTRACT] **Определение (Interview-ready)**
> **git rebase --onto** — это команда для «трансплантации» коммитов. Она позволяет взять изменения, которые были сделаны в одной ветке относительно другой, и перенести их на произвольный новый базовый коммит (newbase), полностью исключая влияние промежуточной ветки (upstream). Это основной инструмент для исправления ситуации «фича от фичи».

---

> [!SETTINGS] **Разбор синтаксиса**
>
> ### 📘 Формальное описание
>
> ```text
> git rebase --onto <newbase> <upstream> [<branch>]
> ```
> 
> ### 📋 Разбор аргументов (The Three-Point Logic)
>
> | Аргумент | Роль | Что туда подставлять? |
> | :--- | :--- | :--- |
> | `<newbase>` | **Куда?** | Новая точка назначения (например, `main`). Сюда "приклеятся" коммиты. |
> | `<upstream>` | **Откуда начинаем отрезать?** | Коммит (или ветка), *после* которого Гит начнет забирать изменения. Сама эта ветка в перенос не попадет. |
> | `[<branch>]` | **Что режем?** | Ветка, кончик которой мы переносим. Если не указать — сработает для текущей (HEAD). |

---
### 🏗️ Визуальная логика: Сценарий «Фича от Фичи»

Представь ситуацию: ты начал делать `feature-B`, основываясь на `feature-A`, но потом `feature-A` признали неудачной или она сильно затянулась, а тебе нужно влить `feature-B` напрямую в `main`.

**Схема истории:**
`main` -> `A1` -> `A2` (feature-A) -> `B1` -> `B2` (feature-B)

**Задача:** Перенести `B1` и `B2` сразу на `main`, выкинув `A1` и `A2`.

**Команда:**
```bash
git rebase --onto main feature-A feature-B
```

> [!INFO] **Что сделает Git:**
> 
> 1. Найдет все коммиты, которые есть в `feature-B`, но нет в `feature-A` (это `B1` и `B2`).
>     
> 2. Оторвет их от `A2`.
>     
> 3. Приклеит их сверху на последний коммит ветки `main`.
>     
> 4. Переставит указатель ветки `feature-B` на новый результат.
>     

---
### 🏷️ Разбор процесса (Step-by-Step)

1. **Определение дельты:** Git вычисляет разницу: `upstream..branch`.
2. **Checkout:** Переходит в состояние `detached HEAD` на коммите `<newbase>`.
3. **Application:** По очереди накладывает (cherry-pick) каждый коммит из дельты на новое место.
4. **Finalization:** Указатель `<branch>` обновляется, старые (отрезанные) коммиты остаются в памяти до первой очистки (GC).
---
### 🛠️ Практические примеры

> [!EXAMPLE] **Кейс 1: Линеаризация истории (Surgical Graft)**
> 
> Ты случайно сделал ветку от другой экспериментальной ветки, а хочешь, чтобы она шла от стабильной версии.
> 
> Bash
> 
> ```
> # Пересаживаем текущую ветку с 'experimental' на 'master'
> git rebase --onto master experimental
> ```

> [!EXAMPLE] **Кейс 2: Удаление "плохого" куска из середины истории**
> 
> Допустим, у тебя есть цепочка `C1-C2-C3-C4`. Ты понял, что `C2` и `C3` были ошибкой, и хочешь, чтобы `C4` шел сразу после `C1`.
> 
> Bash
> 
> ```
> # Мы говорим: возьми всё, что идет после C3 (это C4), и посади это на C1.
> git rebase --onto C1 C3 current-branch
> ```

---
### ⚠️ Риски и предостережения

- **Потеря контекста:** Если коммиты в `<branch>` сильно зависели от изменений в `<upstream>`, при ребейзе ты получишь огромное количество конфликтов.  
- **Дублирование:** Если ты перепутаешь аргументы, можно случайно перенести слишком много коммитов или не те, создав дубликаты в истории.
- **Force Push:** Как и любой rebase, если ветка была на сервере, после операции потребуется `git push --force-with-lease`.

# 📖 git rebase -i

Интерактивный ребейз — это инструмент для **переписывания истории коммитов**. В отличие от обычного ребейза, который просто меняет базу ветки, интерактивный режим позволяет модифицировать каждый коммит в цепочке по отдельности.

## 1. Механика работы (Under the Hood)

Когда ты запускаешь `git rebase -i <base>`, Git выполняет следующий алгоритм:

1. **Генерация списка (Todo-list):** Git берет все коммиты в диапазоне `(base..HEAD]` и создает текстовый файл в директории `.git/rebase-merge/git-rebase-todo`.
2. **Приостановка:** Git открывает этот файл в твоем текстовом редакторе и ждет его закрытия.
3. **Исполнение скрипта:** После сохранения файла Git начинает выполнять команды из списка **сверху вниз** (от старых к новым).
4. **Создание объектов:** Для каждой команды `pick`, `reword`, `squash` и т.д. Git создает **новый объект коммита** с новым хешем $SHA-1$, так как меняются метаданные (родитель, дата или содержимое).
5. **Завершение:** Когда список пуст, указатель текущей ветки перемещается на последний созданный коммит.
## 2. Команды Todo-листа (Подробный разбор)

В редакторе ты увидишь список коммитов, перед каждым из которых стоит ключевое слово (по умолчанию `pick`). Хронология в этом списке идет **сверху вниз** — от самого старого коммита к самому новому.

### Сводная таблица команд

> [!TIP] **1. pick (p) — Использовать коммит**
> 
> Это действие по умолчанию.
> 
> - **Что делает:** Гит берет изменения из этого коммита и пытается применить их к текущему `HEAD` (механика аналогична `cherry-pick`).
>     
> - **Результат:** Создается новый коммит. Даже если код идентичен оригиналу, у него будет другой $SHA-1$, так как меняется родитель ($parent$) или метаданные (например, время создания).
>     

> [!NOTE] **2. reword (r) — Изменить описание**
> 
> - **Что делает:** Применяет изменения коммита, но сразу после этого останавливает процесс и открывает текстовый редактор для редактирования сообщения.
>     
> - **Результат:** Содержимое файлов остается прежним, но ты переписываешь `commit message`. Хеш коммита меняется.
>     

> [!IMPORTANT] **3. edit (e) — Остановка для исправления**
> 
> Самый мощный инструмент для «хирургии» кода.
> 
> - **Что делает:** Гит применяет коммит и полностью прерывает ребейз, возвращая управление в терминал.
>     
> - **Твои действия:** На этой паузе ты можешь добавить новые файлы (`git add`), удалить старые или изменить существующие. Можно использовать `git commit --amend`, чтобы докинуть правки в этот же коммит, или «размиксовать» изменения (`git reset HEAD~1`) и разбить один коммит на несколько.
>     
> - **Продолжение:** Чтобы пойти дальше по списку команд, необходимо ввести `git rebase --continue`.
>     

> [!ABSTRACT] **4. squash (s) — Склеить с предыдущим**
> 
> «Схлопывание» коммита в тот, который стоит в списке **выше**.
> 
> - **Что делает:** Гит берет изменения этого коммита и добавляет их в индекс к предыдущему. Затем он открывает редактор, где показаны сообщения **обоих** коммитов.
>     
> - **Результат:** Вместо двух коммитов в истории остается один, объединяющий в себе все правки и оба описания.
>     

> [!SUCCESS] **5. fixup (f) — Склеить и забыть описание**
> 
> Упрощенная версия `squash`.
> 
> - **Что делает:** Механика идентична `squash` (сливает код с предыдущим коммитом), но Гит **автоматически выбрасывает** текущее сообщение.
>     
> - **Применение:** Идеально для коммитов типа «fix typo» или «minor tweak», которые не несут смысловой нагрузки в истории проекта.
>     

> [!WARNING] **6. exec (x) — Запуск команды**
> 
> Инструмент автоматизации проверки истории.
> 
> - **Что делает:** Гит запускает указанную тобой shell-команду (например, `make test` или линтер) сразу после того, как был применен предыдущий коммит в списке.
>     
> - **Результат:** Если команда вернула ошибку (exit code $\neq 0$), ребейз остановится. Это гарантирует, что ты не пропустишь момент, когда один из промежуточных коммитов сломал билд.
>     

> [!DANGER] **7. drop (d) — Удалить коммит**
> 
> Выкидывает изменения из истории.
> 
> - **Что делает:** Гит просто пропускает этот коммит. Его изменения не будут применены, и он исчезнет из истории ветки.
>     
> - **Важно:** То же самое произойдет, если ты просто удалишь строку с этим коммитом в текстовом редакторе Todo-листа.
>     

### 🛠 Механика процесса (Краткий мануал)

1. **Порядок:** В редакторе коммиты идут **от старых к новым** (сверху вниз). Это хронология, в которой Гит будет их «накатывать».
2. **Конфликты:** Если на любом этапе (особенно при перемещении коммитов или `squash`) Гит не может объединить код, он остановится. Тебе нужно будет:
    - Исправить конфликт в файлах.
    - Сделать `git add <file>`.
    - Ввести `git rebase --continue`.
3. **Отмена:** Если ты понял, что всё испортил в процессе редактирования списка — просто удали всё содержимое текстового файла и сохрани его. Гит увидит пустой список и отменит ребейз.
