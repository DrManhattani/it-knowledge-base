# 🔄 git checkout

> [!ABSTRACT] Суть
> Команда для переключения между ветками - изменяет содержимое твоей рабочей директории так, чтобы она соответствовала выбранной ветке или коммиту, и обновляет указатель [[Git - 06 HEAD|HEAD]]. Также может восстанавливать файлы

---

> [!INFO] 🔍 1. Переключение и создание веток
> | № | Команда | Описание |
> | :-- | :--- | :--- |
> | 1 | `git checkout <branch>` | Перейти на существующую ветку. |
> | 2 | `git checkout -b <new>` | **Create & Switch.** Создать новую ветку и сразу прыгнуть на неё. |
> | 3 | `git checkout -` | Вернуться на **предыдущую** ветку (как кнопка "back"). |

> [!TIP] ⚔️ 2. Разрешение конфликтов (Merge Strategy)
> Когда ты находишься в состоянии конфликта слияния, ты можешь быстро выбрать сторону для конкретного файла.
>
> | № | Флаг | Чьи изменения примет? | Контекст |
> | :-- | :--- | :--- | :--- |
> | 1 | `--ours` | **Наши.** Из текущей ветки, где ты находишься. | `git checkout --ours <file>` |
> | 2 | `--theirs` | **Их.** Из ветки, которую ты вливаешь в свою. | `git checkout --theirs <file>` |

> [!DANGER] 📄 3. Работа с файлами (Восстановление)
> | № | Команда | Описание | Опасность |
> | :-- | :--- | :--- | :--- |
> | 1 | `git checkout <hash> <file>` | Вытащить версию файла из конкретного коммита. | Стирает текущие правки в файле! |
> | 2 | `git checkout -- <file>` | Восстановит версию файла в рабочей директории из индекса или из **HEAD**, если нет в индексе. Формально заменяет версию файла в WD и индексе на версию из индекса или HEAD **(без указания источника → по умолчанию индекс имеет приоритет)**  | **Необратимо!** Правки удалятся навсегда. |
> |*2.1*| `git checkout HEAD -- <file>` | Восстановит версию файла в рабочей директории и в индексе до версии HEAD

> [!attention] Нюансы записи `git checkout <file>` (без `--`) 
> Git сначала пытается понять: 
> 1. Это имя ветки/тега/коммита?
> 2. Или это путь к файлу?

---
### 💡 Важные нюансы

> [!IMPORTANT] **Ours vs Theirs: Не перепутай!**
> - Во время **Merge**: `ours` — это ты, `theirs` — то, что вливаешь.
> - Во время **Rebase**: Всё наоборот! `ours` становится той веткой, *куда* ты переезжаешь (база), а `theirs` — твоими патчами. Это часто взрывает мозг новичкам.

> [!NOTE] **Современная альтернатива**
> С версии 2.23 Git разделил `checkout` на две узкоспециализированные команды:
> 1. `git switch` — только для веток (безопаснее, не затрет файлы случайно).
> 2. `git restore` — только для восстановления файлов.
> *Если ты только учишься — лучше сразу привыкать к ним.*

# 🔄 git checkout (File Context)

> [!ABSTRACT] **Суть операции**
> 
> В контексте файлов **git checkout** работает как «телепорт» конкретных версий данных. Она извлекает файлы из базы объектов (или индекса) и принудительно записывает их в рабочую область.
> 
> **Главное отличие от** `restore`: При указании источника (коммита), `checkout` по умолчанию синхронизирует **сразу и Индекс, и Рабочую директорию**, тогда как `restore` требует для этого явных флагов.

---
### 📥 Куда попадают файлы?

Это ключевой момент для понимания. Давай сравним логику «по умолчанию»:

| **Команда**                   | **Источник (Source)** | **Цель (Destination)**          | **Изменится ли Индекс?** |
| ----------------------------- | --------------------- | ------------------------------- | ------------------------ |
| `git checkout -- <file>`      | **Индекс**            | Рабочая директория              | Нет (он и есть источник) |
| `git checkout HEAD -- <file>` | **HEAD (Коммит)**     | **Индекс + Рабочая директория** | **✅ Да**                 |
| `git restore <file>`          | **Индекс**            | Рабочая директория              | ❌ Нет                    |
| `git restore -s HEAD <file>`  | **HEAD (Коммит)**     | Рабочая директория              | ❌ Нет                    |

> [!WARNING] **Технический нюанс**
> 
> Если ты делаешь `git checkout <commit> <file>`, ты фактически делаешь «мгновенный add». Файл в индексе перезаписывается версией из коммита. Если ты хотел просто посмотреть файл, не меняя то, что подготовлено к коммиту — `checkout` тебе не подходит, используй `restore`.

### 🛠️ Детальная таблица сценариев

|**Сценарий**|**Команда**|**Что происходит "под капотом"**|
|---|---|---|
|**Откат правок (Unedit)**|`git checkout -- <file>`|Берет версию из **Индекса** и затирает ею твой файл на диске.|
|**Машина времени**|`git checkout <hash> -- <file>`|Достает блоб из коммита `<hash>`, пишет его в **Индекс**, а затем в **Рабочую директорию**.|
|**Смена стороны (Merge)**|`git checkout --theirs <file>`|Берет версию файла из ветки, которую мы вливаем (stage 3 индекса) и пишет на диск.|
|**Смена стороны (Merge)**|`git checkout --ours <file>`|Берет версию файла из нашей текущей ветки (stage 2 индекса) и пишет на диск.|

### 🏗️ Архитектурная логика (Deep Dive)

Когда ты вызываешь `git checkout <commit> <file>`, Git делает следующее:

1. Ищет дерево (tree) указанного коммита.
2. Находит хеш (SHA-1) нужного файла.
3. Обновляет запись в `.git/index` для этого пути этим хешем.
4. Извлекает содержимое из `.git/objects` и физически перезаписывает файл на диске.

### ❓ Вопросы на собеседовании

> [!QUESTION] **1. Почему** `git checkout -- <file>` **безопаснее, чем** `git checkout HEAD -- <file>`**?**
> 
> **Ответ:** Потому что первая команда берет данные из Индекса. Если ты случайно сделал `git add`, а потом понял, что стер что-то важное, ты сможешь восстановить это из Индекса. Вторая же команда (с `HEAD`) берет данные из последнего коммита, перезаписывая и диск, и индекс — если там были промежуточные правки, они исчезнут.

> [!QUESTION] **2. Что означает** `--` **в команде?**
> 
> **Ответ:** Это разделитель (delimiter). Он говорит Гиту: «Всё, что идет после этого, — это **пути к файлам**, а не имена веток». Это защищает от ситуации, когда у тебя есть и ветка `fix`, и файл `fix`.

> [!QUESTION] **3. Могу ли я сделать** `checkout` **файла из другой ветки, не переходя на неё?**
> 
> **Ответ:** Да. `git checkout other-branch -- path/to/file`. Файл прилетит в твой текущий рабочий каталог и сразу попадет в индекс.

> [!QUESTION] **4. В чем разница между** `checkout` **файла и** `reset` **файла?**
> 
> **Ответ:** `git reset <commit> <file>` меняет **только Индекс**. Файлы на диске не трогаются. `git checkout <commit> <file>` меняет **и Индекс, и Диск**.

### 💡 Резюме для конспекта

> [!SUCCESS] **Золотое правило**
> 
> - Нужно откатить изменения на диске до того, что в индексе? -> `git checkout -- <file>`.
>     
> - Нужно вытащить файл из истории и сразу подготовить его к коммиту? -> `git checkout <hash> <file>`.
>     
> - Нужно вытащить файл из истории, но **не трогать индекс**? -> используй `git restore -s <hash> <file>`.
