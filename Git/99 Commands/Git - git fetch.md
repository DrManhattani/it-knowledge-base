# 🛰️ git fetch

> [!ABSTRACT] **Определение (Professional Context)**
> **git fetch** — загружает новые объекты (коммиты, деревья, блобы) и обновляет указатели удаленных веток (remote-tracking branches) (`refs/remotes/<remote>/...`), отражающие состояние удалённого репозитория, не изменяя текущие локальные ветки и рабочую директорию.  

---

> [!SETTINGS] **Синтаксис и структура команды** `git fetch`
> 
> ### 📘 Формальное описание (POSIX/Man-style)
> 
> 
> ```
> git fetch [<options>] [<repository> [<refspec>...]]
> git fetch [<options>] --all
> ```
> 
> ---
> 
> ### 📋 Детальный разбор параметров
> 
> |**Элемент**|**Техническое описание**|**Роль в операции**|
> |---|---|---|
> |`[<options>]`|**Модификаторы поведения**|Флаги, меняющие логику работы. Например, `--prune` (очистка ссылок), `--depth` (ограничение истории) или `--tags` (загрузка метаданных).|
> |`[<repository>]`|**Идентификатор цели**|Алиас удаленного репозитория (например, `origin`). Если опущен, Git обращается к серверу, прописанному в конфигурации текущей ветки (`branch.<name>.remote`).|
> |`[<refspec>...]`|**Спецификация ссылок**|Строка сопоставления (mapping). Определяет, какую ветку на сервере (`src`) сопоставить с локальной веткой-отслеживанием (`dst`).<br><br><br>_Формат:_ `+<src>:<dst>` (например: `refs/heads/main:refs/remotes/origin/main`).|
> |`--all`|**Флаг пакетной обработки**|Переводит команду в режим итерации по всем секциям `[remote "..."]` в конфиге, игнорируя передачу конкретного `<repository>`.|
> 
> 
> ### 🏗️ Логика вложенности параметров
> 
> 1. `[<repository> [<refspec>...]]`: Квадратные скобки внутри скобок означают, что ты не можешь указать `<refspec>`, не указав сначала конкретный `<repository>`.
>     
> 2. `...` **(Ellipsis)**: Указывает на то, что параметров `<refspec>` может быть несколько. Это позволяет скачать только выбранные ветки за один запрос: `git fetch origin main dev feat/logs`.
>     
> 3. **Взаимное исключение**: Ты используешь либо связку `[<repository> <refspec>]`, чтобы работать точечно, либо флаг `--all`, чтобы синхронизировать всё окружение целиком.
>

### 🏗️ Архитектурная логика (Internals)

На низком уровне команда проходит через следующие стадии:

1. **Negotiation (Переговоры):** Клиент и сервер обмениваются списками последних коммитов (Haves/Wants), чтобы вычислить общую точку расхождения и минимизировать объем передаваемых данных.
2. **Pack-file Transfer:** Сервер генерирует и передает пакетный файл (`.pack`), содержащий только те объекты, которых нет у клиента.
3. **Reference Update:** После верификации целостности данных Git обновляет указатели в пространстве имен `refs/remotes/<remote>/`. 
   *Пример: файл `.git/refs/remotes/origin/main` получает новый SHA-1 хеш.*

### 🚩 Флаги и опции

| Флаг              | Тип         | Назначение                                                                                      |
| :---------------- | :---------- | :---------------------------------------------------------------------------------------------- |
| `-a`, `--all`     | Групповой   | Обновляет все настроенные удаленные репозитории.                                                |
| `-p`, `--prune`   | Гигиена     | Удаляет локальные ссылки на ветки, которые были удалены в удаленном репозитории.                |
| `--dry-run`       | Тестовый    | Симуляция операции без записи данных на диск.                                                   |
| `--tags`          | Метаданные  | Принудительная загрузка всех тегов с сервера (даже тех, что не принадлежат скачиваемым веткам). |
| `--depth <N>`     | Оптимизация | Создает "мелкий" (shallow) клон, ограничивая историю N последними коммитами.                    |
| `-v`, `--verbose` | Логирование | Детальный вывод прогресса и информации об объектах.                                             |

### 🏷️ Разбор вывода команды (Output Properties)

#### 📋 Общий пример вывода в терминале
При запуске `git fetch --prune` ты увидишь примерно следующий блок:

```text
From github.com:user/my-obsidian-vault
   a1b2c3d..e5f6g7h  main         -> origin/main
 * [new branch]      feature-logs -> origin/feature-logs
 + f1a2b3c...d4e5f6g dev          -> origin/dev  (forced update)
 - [deleted]         (none)       -> origin/old-experiment
 ! [rejected]        v1.0         -> v1.0  (already exists)
```
#### 🔍 Частный разбор по статусам

| **Символ** | **Статус**        | **Пример строки**                       | **Техническая интерпретация**                                                                                  |
| ---------- | ----------------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `(пробел)` | **Fast-forward**  | `a1b2c3d..e5f6g7h main -> origin/main`  | **Линейное обновление.** Удаленная ветка просто ушла вперед. Безопасно для слияния.                            |
| `*`        | **New Ref**       | `* [new branch] feat -> origin/feat`    | **Новый объект.** На сервере создана ветка или тег, которых у тебя еще нет.                                    |
| `+`        | **Forced Update** | `+ f1a2b3c...d4e5f6g dev -> origin/dev` | **Перезапись истории.** Кто-то сделал `push --force`. Твои локальные коммиты в этой ветке могут конфликтовать. |
| `-`        | **Pruned**        | `- [deleted] (none) -> origin/old`      | **Очистка.** (Только с `--prune`). Удаленная ветка стерта на сервере, ссылка удалена локально.                 |
| `!`        | **Rejected**      | `! [rejected] v1.0 -> v1.0`             | **Отказ.** Ошибка обновления. Обычно из-за конфликта тегов (нельзя перезаписать тег без `-f`).                 |

---
### 🏗️ Внутренняя логика (Internal Workflow)

1. **Negotiation:** Клиент и сервер сравнивают хеши коммитов, вычисляя разницу (what's missing).
2. **Transfer:** Сервер упаковывает недостающие объекты в `.pack` файл и передает клиенту.
3. **Ref Update:** Атомарное обновление файлов-указателей в `.git/refs/remotes/<remote>/`. Локальный HEAD не меняется.

### 🛠️ Сценарии использования (Middle+ Best Practices)

> [!EXAMPLE] **Анализ входящих изменений (Code Review Workflow)**
> Профессиональный подход исключает слепое использование `pull`. Сначала анализируется "дельта":
> ```bash
> git fetch origin
> # Просмотр коммитов, которые есть в облаке, но нет локально:
> git log main..origin/main --oneline --graph --all
> # Дифф конкретных изменений в коде:
> git diff main origin/main
> ```

> [!EXAMPLE] **Массовая синхронизация инфраструктуры**
> Для проектов с множеством источников (например, Open Source апстрим и собственный форк):
> ```bash
> git fetch --all --prune --tags
> ```

# 🏷️ Теги при команде git fetch
### 1. Можно ли вешать 2 тега на один коммит?

**Да, без проблем.** Вспомни, что такое тег технически — это просто текстовый файл в папке `.git/refs/tags/`, внутри которого записан хеш коммита. Ничто не мешает тебе создать два файла с разными именами, внутри которых будет один и тот же хеш.

**Пример:**
- `v1.0` — официальный тег релиза.
- `stable-gold` — твой внутренний тег для тестов.
    Оба указывают на коммит `abc1234`. В `git log` ты увидишь их оба рядом с этим коммитом.
### 2. Что будет, если прилетит удаленный тег?

Тут есть два сценария, и они принципиально разные:

#### Сценарий А: Имена тегов РАЗНЫЕ (Твой случай)

У тебя стоял локальный тег `my-local-tag`, а с сервера прилетел `v1.0` на тот же самый коммит.

- **Результат:** Они просто будут мирно существовать вдвоем. У коммита теперь два «псевдонима». Никаких конфликтов, Git просто добавит новый файл в `refs/tags/`.

#### Сценарий Б: Имена тегов ОДИНАКОВЫЕ (Конфликт тегов)

А вот это — любимый вопрос на Middle-позиции. Допустим, у тебя есть локальный тег `v1.0`, который указывает на коммит **А**, а на сервере кто-то переставил тег `v1.0` на коммит **В**.

**Что сделает `git fetch`?**

По умолчанию Git **защищает** твои локальные теги. Он увидит, что имя совпадает, а хеши разные, и выдаст ошибку (или предупреждение):

`[tag update] v1.0 -> v1.0 (forced update required)`

**Он НЕ перезапишет твой тег автоматически.** Чтобы принять версию сервера, тебе придется явно написать:

`git fetch --tags -f` (флаг `--force` заставит Git обновить локальные ссылки).

### 3. Как это выглядит в консоли?

Когда ты делаешь `git log --oneline --decorate`, ты увидишь что-то вроде этого:

`abc1234 (HEAD -> main, tag: v1.0, tag: my-local-tag, origin/main) Fix critical bug`

Это абсолютно нормальная ситуация для DevOps-инженера. Например:

1. Тег `v1.2.0` — поставил разработчик.
2. Тег `deployed-to-prod` — поставил автоматический скрипт (CI/CD) после успешного деплоя.
    Оба висят на одном коммите, и это очень удобно для навигации.

### 🎙️ Итог по тегам

1. **Количество тегов на коммит:** Не ограничено.
2. **Конфликты:** Только если **имена** совпадают, но указывают на разные коммиты. В этом случае локальный тег всегда в приоритете, пока ты не скажешь `-f`.
3. **Для чего это нужно:** Разные отделы (разработка, QA, DevOps) могут метить одни и те же вехи своими именами.
