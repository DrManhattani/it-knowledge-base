# 🕵️‍♂️ git blame

> [!ABSTRACT] **Определение**
> 
> `git blame` — это инструмент для аннотирования каждой строки в файле информацией о том, какой коммит и какой автор последними изменили эту строку. Это основной способ понять, _почему_ код выглядит именно так, обратившись к метаданным коммита.

---
### 🛠️ Таблица флагов и операций

| **Команда**                  | **Описание**                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| `git blame <file>`           | Базовый вывод: хеш, автор, дата и содержимое строк.                                 |
| `git blame -L 10,20 <file>`  | Показать аннотации только для строк с 10 по 20.                                     |
| `git blame -e <file>`        | Показать email автора вместо его имени.                                             |
| `git blame -w <file>`        | **Игнорировать пробелы.** Не считать изменением строки только лишь правку отступов. |
| `git blame -M <file>`        | Обнаруживать перемещение строк внутри одного файла.                                 |
| `git blame -C <file>`        | Обнаруживать копирование строк из других файлов в этом же коммите.                  |
| `git blame <hash> -- <file>` | Посмотреть состояние файла на момент определенного коммита                          |

### 🔍 Ответы на технические вопросы

> [!QUESTION] **1. Почему **`git blame` **иногда бесполезен после рефакторинга?**
> 
> Если коллега прогнал весь файл через автоматический форматтер (Prettier/Black), `git blame` укажет на него как на автора всех строк.
> 
> - **Решение:** Настройка файла `.git-blame-ignore-revs`. В него можно записать хеши «мусорных» коммитов, и Гит будет «пропускать» их, показывая настоящего автора логики.
>     

> [!QUESTION] **2. В чем разница между **`git blame` **и** `git log -L`**?**
> 
> - `git blame` показывает текущее состояние файла: кто был **последним**.
>     
> - `git log -L 1,10:file.txt` показывает **всю историю изменений** этого диапазона строк. Это гораздо мощнее, если нужно понять, как эволюционировал конкретный алгоритм.
>     

> [!QUESTION] **3. Как работает обнаружение перемещений (**`-M` **и** `-C`**)?**
> 
> Гит не хранит информацию о том, что строку «передвинули». Он вычисляет это на лету. Флаг `-M` заставляет Гит искать идентичные строки в том же коммите. Это помогает понять, что код не был написан с нуля, а просто переехал из одной функции в другую.

### ❓ Вопросы на собеседовании

> [!IMPORTANT] **Популярные вопросы про поиск авторов**
> 
> **1. Как узнать, когда была удалена строка из файла?**
> 
> - **Ответ:** `git blame` тут не поможет (он видит только живые строки). Нужно использовать `git log -S "текст удаленной строки"` (Pickaxe search) или `git log -G`.
>     
> 
> ---
> 
> **2. Как работает флаг** `--incremental`**?**
> 
> - **Ответ:** Он выводит информацию по мере её получения, не дожидаясь обработки всего файла. Это полезно для инструментов разработки (IDE), чтобы быстрее отрисовывать интерфейс на огромных файлах.
>     
> 
> ---
> 
> **3. Можно ли посмотреть **`blame` **для файла в том состоянии, в котором он был месяц назад?**
> 
> - **Ответ:** Да. Нужно передать хеш коммита перед именем файла: `git blame <hash> -- <file>`.
>     
> 
> ---
> 
> **4. Как игнорировать изменения в** `git blame`**, если автор просто изменил e-mail?**
> 
> - **Ответ:** Для этого используется файл `.mailmap`. В нем можно прописать соответствие разных имен и почт одному и тому же человеку, чтобы Гит считал их одним автором.
>

Затем я делаю `git show <hash>`, читаю описание задачи и понимаю, какие бизнес-требования привели к такому техническому решению. В больших проектах я всегда комбинирую его с `-w` и `-M`, чтобы не отвлекаться на перемещения кода и правки стилистики».
