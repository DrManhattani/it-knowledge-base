# ➕ Git Hooks

### 1. Философия и концепция Shift Left

В DevOps существует принцип **Shift Left** — перенос проверок безопасности и качества кода на как можно более ранние этапы.

- **Без хуков:** Ты узнаешь об ошибке через 10 минут, когда упадет билд в CI/CD.
- **С хуками:** Ты узнаешь об ошибке через 0.1 секунды, еще не успев отправить код в репозиторий.

> [!NOTE] **Определение**
> 
> **Git Hooks** — это скрипты, которые Git автоматически запускает при наступлении определенных событий (коммит, пуш, прием данных сервером). Это «событийная модель» внутри системы контроля версий.

---
### 2. Анатомия и Механика (Как это устроено)

#### Где они живут?

В любом репозитории есть скрытая папка `.git/hooks`.
- Гит автоматически создает там файлы с расширением `.sample` (например, `pre-commit.sample`).
- Эти файлы — просто примеры на Bash.
#### Как активировать хук?

1. Создать файл в `.git/hooks/` с именем хука (например, `pre-commit`) **без расширения**.
2. Сделать его исполняемым: `chmod +x .git/hooks/pre-commit`.
3. Скрипт может быть написан на чем угодно: Bash, Python, Ruby, Go — главное, чтобы в начале был **Shebang** (напр., `#!/bin/bash`).
#### Логика работы

Гит смотрит на **Exit Code** (код возврата) скрипта:
- **0** — Всё хорошо, Гит продолжает операцию.
- **Не 0 (1-255)** — Гит прерывает операцию и выводит сообщение об ошибке из скрипта.

### 3. Классификация хуков

Все хуки делятся на две большие группы: **Клиентские** и **Серверные**.
#### А. Клиентские (Client-side) — работают на твоем ПК

Используются для контроля качества кода и удобства разработки.

| **Хук**              | **Когда запускается**                         | **Типичный сценарий**                                                                                        |
| -------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `pre-commit`         | Сразу после `git commit`, до ввода сообщения. | **Linting, Static Analysis.** Проверка синтаксиса, поиск забытых паролей (secret detection), форматирование. |
| `prepare-commit-msg` | Перед открытием редактора сообщения.          | Автоматическая вставка номера задачи из ветки (напр. `PROJ-123`).                                            |
| `commit-msg`         | После того как ты написал сообщение.          | Проверка формата сообщения (Conventional Commits).                                                           |
| `pre-push`           | Сразу перед `git push`.                       | Запуск Unit-тестов или проверка, что ты не пушишь в `main`.                                                  |

#### Б. Серверные (Server-side) — работают на сервере (GitLab/GitHub)

Используются для принудительного соблюдения политик компании.

| **Хук**        | **Описание**                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `pre-receive`  | Самый важный. Проверяет входящий пуш. Если он выдаст ошибку, пуш будет отклонен для всех. Здесь проверяют права доступа. |
| `post-receive` | После успешного пуша. Используется для уведомлений (Slack/Email) или триггеров деплоя.                                   |

### 4. Главная проблема хуков (The Distribution Gap)

Папка `.git` (и `.git/hooks` внутри неё) **не копируется** при клонировании репозитория.

Это значит, что если ты написал крутой хук, твой коллега его не получит.

**Как это решают профессионалы в 2026 году:**

1. **Framework `pre-commit` (Python-based):** Золотой стандарт. Ты создаешь файл `.pre-commit-config.yaml` в корне проекта. Он версионируется. Коллега пишет `pre-commit install` и вуаля — у него те же хуки.
2. **Husky (JS-based):** Популярно в веб-разработке. Автоматически прописывает хуки через `package.json`.
3. **`core.hooksPath`:** Команда `git config core.hooksPath .githooks` заставляет Гит искать хуки не в `.git/hooks`, а в обычной папке проекта, которую можно пушить в репо.

### 5. Кейсы для DevOps-инженера (Что рассказать на интервью)

> [!IMPORTANT] **Топ-3 "боевых" сценария:**
> 
> 1. **Secret Detection (Gitleaks):** Хук сканирует файлы на наличие API-ключей, AWS секретов или паролей. Если найдено — коммит блокируется.
>     
> 2. **Terraform/Ansible Linting:** Проверка того, что твои конфиги инфраструктуры (IaC) написаны без синтаксических ошибок.
>     
> 3. **Branch Name Validation:** Запрет пуша, если ветка называется не по правилам (например, `feature/name` или `fix/name`).
>     

#### Как обойти хук?

Иногда нужно срочно запушить код, а хук не пускает (например, ложное срабатывание).
Команда: `git commit -m "Emergency" --no-verify` (или `-n`).

_На интервью обязательно упомяни это — это показывает, что ты знаешь, как работает система в экстренных ситуациях._

### 6. Вопросы на собеседовании

**В: Можно ли использовать хуки для развертывания кода (Deployment)?**

_О:_ Да, для этого используется серверный хук `post-receive`. Когда код попадает на сервер, скрипт может скопировать файлы в рабочую директорию веб-сервера или перезапустить контейнер.

**В: В чем разница между `pre-commit` и CI/CD пайплайном?**

_О:_ `pre-commit` — это быстрая обратная связь для разработчика (доля секунды). CI/CD — это финальная инстанция, которая запускает тяжелые тесты и сборку. Одно не заменяет другое, они работают в связке.

**В: Можно ли написать хук на языке Python?**

_О:_ Да. В первой строке файла (`shebang`) нужно указать путь к интерпретатору: `#!/usr/bin/env python3`. Гит запустит его так же, как и Bash-скрипт.
