# Команда git merge

> [!ABSTRACT] **Определение**
> 
> **git merge** — это операция, которая объединяет несколько последовательностей коммитов в одну общую историю. Чаще всего используется для вливания фича-ветки в основную (`main`).

### 🏗️ Два основных сценария слияния

|**Тип слияния**|**Когда происходит?**|**Результат**|
|---|---|---|
|**Fast-Forward**|Если `main` не ушла вперед с момента создания ветки.|Указатель `main` просто «перепрыгивает» на последний коммит фичи. **Нового коммита нет.**|
|**Three-Way (Recursive)**|Если истории разошлись (есть новые коммиты и в `main`, и в фиче).|Создается специальный **Merge Commit** с двумя родителями.|

### 🧐 Вопросы

#### 1. «Что такое Three-way merge и почему он именно "трехсторонний"?»

**Ответ:** Для создания коммита слияния Гит использует три снимка (snapshots):

1. **Край твоей текущей ветки** (`ours`).
2. **Край вливаемой ветки** (`theirs`).
3. **Общий предок** (`merge-base`).
    Гит сравнивает изменения обоих веток относительно общего предка. Если ты изменил строку 10, а коллега — строку 20, Гит поймет, что конфликта нет, и применит оба изменения.

#### 2. «Зачем использовать флаг `--no-ff` (no fast-forward)?»

**Ситуация:** По умолчанию Гит делает Fast-forward, если это возможно.

**Серьезный ответ:** В крупных проектах мы часто запрещаем FF. Флаг `--no-ff` заставляет Гит **всегда** создавать Merge Commit.

**Зачем?** Чтобы в истории остался «пузырек» (группа коммитов), наглядно показывающий, что эта фича была отдельной задачей. Если делать только FF, история превратится в плоскую ленту, где невозможно понять, какие 5 коммитов относились к одной задаче.

#### 3. «Что такое "Стратегия слияния" (Merge Strategy)?»

**Вопрос для профи:** «Какую стратегию Гит использует по умолчанию?»

**Ответ:** Раньше была `recursive`, сейчас (в новых версиях) по умолчанию стоит **`ort`** (Ostensibly Recursive's Twin). Она быстрее и лучше справляется с переименованиями файлов. Если Гит видит, что файл был переименован в одной ветке и изменен в другой, стратегия `ort` это поймет и объединит правки, а не создаст конфликт.

#### 4. «В чем разница между `git merge` и `git merge --squash`?»

**Ответ:** Обычный `merge` тащит за собой все коммиты фича-ветки (со всеми опечатками и промежуточным мусором).

`--squash` берет все изменения из ветки, «схлопывает» их в один большой пакет и кладет его в индекс. Ты делаешь один чистый коммит. **Важно:** при этом Git не создает связи между ветками (у этого коммита будет только один родитель).

### 🧨 Конфликты: Взгляд изнутри

Когда ты видишь в файле эти странные знаки:

Plaintext

```
<<<<<<< HEAD
настройка для Цитадели
=======
настройка для Май
>>>>>>> feature-branch
```

Это не просто текст. Это результат того, что `merge-base` не смог однозначно решить, какой из вариантов правильный.

**Вопрос на засыпку:** «Как Гит понимает, что произошел конфликт?»

**Ответ:** Гит использует так называемые **«стадии» (stages)** в индексе.

- Stage 1: Общий предок.
    
- Stage 2: Твоя версия (`ours`).
    
- Stage 3: Их версия (`theirs`).
    
    Если в файле на стадиях 2 и 3 разные данные в одной строке относительно стадии 1 — бум, конфликт.

### 🎙️ Твой следующий шаг

Мы разобрали два способа объединения: `rebase` (линейная история) и `merge` (честная, ветвистая история). На Западе идет бесконечная война между сторонниками «чистой истории» (`rebase`) и «правдивой истории» (`merge`).
