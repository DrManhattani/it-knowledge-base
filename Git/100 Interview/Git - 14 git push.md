# Команда git push

> [!ABSTRACT] **Определение**
> 
> **git push** — это команда для передачи содержимого твоего локального репозитория в удаленный. Передает локальные объекты - commits, blobs, trees (теги по умолчанию не передаются) в удаленный репозиторий и обновления его указатели (refs).

---
### 🛠️ Полный синтаксис

`git push [<options>] [<repository> [<refspec>...]]`

- **`<repository>`**: Куда пушим (например, `origin`).
- **`<refspec>`**: Что именно и куда (например, `master:master`). Если ветки называются одинаково, пишем просто `master`.

---
### 🚀 Важные флаги

| **Флаг**             | **Полное имя**   | **Что делает**                                                                                                                                    |
| -------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-u`                 | `--set-upstream` | Связывает локальную ветку с удаленной. Нужно нажать **один раз** при первом пуше новой ветки. Дальше можно писать просто `git push`.              |
| `-d`                 | `--delete`       | Удаляет ветку на сервере. Пример: `git push origin -d feature-branch`.                                                                            |
| `-f`                 | `--force`        | **«Ядерная кнопка».** Перезаписывает историю на сервере твоей локальной версией. Игнорирует конфликты.                                            |
| `--force-with-lease` | (то же)          | **Безопасная «сила».** Позволяет перезаписать историю только в том случае, если на сервере нет новых коммитов от коллег, которых ты еще не видел. |
| `--tags`             | `--tags`         | Отправляет все локальные теги из `refs/tags/` на сервер.                                                                                          |
| `--all`              | `--all`          | Отправляет все локальные ветки, для которых настроены соответствия в `.git/config`.                                                               |
### 📦 Что именно и когда летит на сервер?

| **Действие**           | **Что летит по сети?**                              | **Комментарий**                                       |
| ---------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| `git push`             | Коммиты, Деревья, Блобы + ссылки `refs/heads/`      | Теги игнорируются.                                    |
| `git push origin v1.0` | Всё вышеперечисленное + **ссылка **`refs/tags/v1.0` | Если тег аннотированный, летит еще и **объект тега**. |
| `git push --tags`      | Вообще все локальные теги.                          | Массовая отправка всех меток.                         |

### 🧨 Проблема «Non-fast-forward»

Если ты попробуешь сделать `push`, а твой коллега уже успел залить свои изменения в ту же ветку, Git выдаст ошибку **rejected (non-fast-forward)**.

**Почему?** Потому что твоя история и история на сервере разошлись.

- **Как делать нельзя:** Сразу бахнуть `git push --force`. Ты просто сотрешь работу коллеги.
- **Как делать правильно:** Сделать `git pull --rebase`, решить конфликты локально и только потом сделать чистый `git push`.

### 🚫 Что Git НИКОГДА не передает

Это самый частый подвох на собеседованиях. Многие думают, что Git — это полный бэкап папки проекта. Это не так.

**Git НЕ передает:**

- **Конфигурацию (`.git/config`):** Твои локальные настройки, псевдонимы (aliases), почта и имя пользователя остаются только у тебя.
- **Хуки (`.git/hooks`):** Если ты написал скрипт, который проверяет код перед коммитом (pre-commit hook), он не улетит на сервер. Именно поэтому в DevOps используют такие инструменты, как `pre-commit` framework, чтобы синхронизировать эти проверки.
- **Stash (`.git/refs/stash`):** Твои «заначки» (отложенные изменения) — это сугубо локальная вещь.
- **Reflog:** История твоих перемещений по репозиторию локальна. На сервере будет свой рефлог.
- **Игнорируемые файлы:** Всё, что прописано в `.gitignore` и не попало в индекс.

### ❓ Вопросы на собеседовании

> [!question] 1. В чем разница между `--force` и `--force-with-lease`?
> 
> **Ответ:** Это вопрос на "профпригодность". `--force` слепо перезапишет сервер. Если коллега успел что-то залить, его работа пропадет. `--force-with-lease` проверяет: совпадает ли твоё знание об удаленной ветке (`origin/main`) с реальным состоянием на сервере. Если кто-то успел залить новый коммит, Git не даст тебе применить силу и спасет чужой код. **Всегда используй --force-with-lease.**

> [!question] 2. Что делает флаг `-u` (upstream)?
> 
> **Ответ:** Он прописывает связь в `.git/config`. После `git push -u origin main` Git запоминает, что ветка `main` должна всегда отправляться в `origin` и забирать данные оттуда. Это позволяет в будущем использовать просто `git push` и `git pull`.

> [!question] 3. Можно ли запушить локальную ветку `feature` в удаленную ветку под другим именем, например `production`?
> 
> **Ответ:** Да, через полный refspec: `git push origin feature:production`. Но в реальности так делают редко, чтобы не путаться.
