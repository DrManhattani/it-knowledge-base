# Команда git fetch

> [!ABSTRACT] **Определение**
> 
> **git fetch** — это команда связывается с удаленным репозиторием и забирает из него все объекты, которых еще нет в локальном репозитории и обновляет **remote-tracking branches** (указатели удаленных веток `refs/remotes/`), не затрагивая при этом локальные ветки (`refs/heads/`) и рабочую директорию.
> - **Синхронизация объектов:** Гит проверяет хеши коммитов на сервере и у тебя. Всё, чего не хватает в твоем каталоге `.git/objects`, скачивается.
> - **Обновление ссылок:** Гит перезаписывает файлы в `refs/remotes/<remote>/`, чтобы они соответствовали состоянию веток на сервере.
> - **Изоляция (Safety):** команда **никогда** не изменяет состояние указателя `HEAD` и не модифицирует файлы в рабочем каталоге (working directory).

### 🛠️ Популярные флаги и примеры

> [!INFO] **Таблица наиболее используемых флагов**

| **Флаг**    | **Полное имя** | **Описание**                                                                                                                | **Пример команды**    |
| ----------- | -------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **(нет)**   | `git fetch`    | Загружает изменения из удаленной ветки по умолчанию (обычно `origin`).                                                      | `git fetch`           |
| `--all`     | `--all`        | Забирает обновления изо **всех** подключенных удаленных репозиториев сразу.                                                 | `git fetch --all`     |
| `-p`        | `--prune`      | **Чистка.** Удаляет локальные ссылки на ветки, которые уже были удалены в удаленном репозитории. Очень полезно для порядка. | `git fetch -p`        |
| `-t`        | `--tags`       | Загружает все теги (версии) с сервера локально.                                                                             | `git fetch --tags`    |
| `--dry-run` | `--dry-run`    | Тестовый запуск. Показывает, что будет скачано, но ничего не меняет.                                                        | `git fetch --dry-run` |

### ⚙️ Как это работает «под капотом»

На собеседовании в серьезную IT-компанию тебя могут спросить: «А где физически хранятся данные после fetch?».

1. **Удаленные ветки (Remote-tracking branches):** Когда ты делаешь `fetch`, Git обновляет файлы в папке `.git/refs/remotes/origin/`.
2. **Изоляция:** Твои локальные ветки (например, `main`) остаются нетронутыми. Git создает или обновляет ветку `origin/main`. Это всего лишь **указатель** на последний коммит на сервере.
3. **Объекты:** Все новые файлы (блобы) и коммиты скачиваются в твою базу данных `.git/objects`, но они пока «висят» отдельно от твоего рабочего кода.

## 🚩 Вопросы относительно флагов:
### 1. Полный синтаксис git fetch

В самом общем виде команда выглядит так:

`git fetch [<options>] [<repository> [<refspec>...]]`

**Компоненты:**

- **`<options>`**: Флаги (`--all`, `--prune`, `--tags` и т.д.).
- **`<repository>`**: Имя удаленного репозитория (например, `origin` или `upstream`). Если не указать, используется репозиторий «по умолчанию».
- **`<refspec>`**: Описывает, какие именно ссылки (ветки/теги) нужно забрать и куда их положить локально. Формат: `+<src>:<dst>`.
    - _Пример:_ `git fetch origin master:refs/remotes/origin/mymaster` (забрать `master` из `origin` и сохранить его локально как удаленную ветку `mymaster`).

> [!EXAMPLE] **Пример «на максималках»**
> 
> `git fetch -v --prune --tags upstream master`
> 
> _Что произошло:_ Мы максимально подробно (`-v`) забираем ветку `master` из репозитория `upstream`, чистим удаленные ветки (`--prune`) и подтягиваем все теги (`--tags`).
### 2. Удаленный репозиторий по умолчанию

**Как определяется?**

1. **Конфигурация текущей ветки:** Git смотрит в файл `.git/config`. Если у текущей ветки (например, `feature`) настроено отслеживание (tracking), то репозиторий берется оттуда (`branch.feature.remote`).
2. **Запасной вариант:** Если ветка ничего не отслеживает, Git ищет репозиторий с именем `origin`.
3. **Если ничего не найдено:** Команда выдаст ошибку.

**Если репозиториев несколько?**

Если ты просто напишешь `git fetch`, Git отработает только по репозиторию по умолчанию (см. пункт выше). Остальные репозитории он проигнорирует. Чтобы обновить всё — используй `--all`.

### 3. Область действия `--prune`

Флаг `--prune` (или `-p`) работает **в паре с тем, что ты фечишь**.

- Если ты пишешь `git fetch --prune origin`, удалятся только «мертвые» ветки из `origin`.
- Если ты пишешь `git fetch --prune --all`, Git пройдет по **всем** удаленным репозиториям и вычистит ссылки для каждого из них.

> [!TIP] **Совет для профи**
> 
> Можно настроить автоматическую чистку при каждом фече раз и навсегда командой:
> 
> `git config --global fetch.prune true`
### 4. Поведение тегов: `--tags` vs обычный fetch

Здесь есть тонкая механика «автоматического следования» (tag following).

1. **По умолчанию (`git fetch` без флагов):** Git автоматически скачивает только те теги, которые указывают на коммиты, которые ты сейчас загружаешь.
    - _Пример:_ Если ты скачал ветку `main`, и на одном из новых коммитов стоит тег `v1.2`, Git заберет его сам.
2. **С флагом `--tags`:** Git забирает **все** теги из пространства `refs/tags/` удаленного репозитория, даже если они стоят на ветках, которые ты не скачивал.
3. **Специфика:** Флаг `--tags` часто используется при первом клонировании или когда тебе нужно получить полную картину релизов, не скачивая все ветки.

### ❓ Потенциальные вопросы на собеседовании

> [!question] 1. В чем главное отличие `git fetch` от `git pull`?
> 
> **Ответ:** Это фундаментальный вопрос.
> 
> Математически это выглядит так:
> 
> $$git\ pull = git\ fetch + git\ merge$$
> 
> `fetch` — это только скачивание данных. Он безопасен, так как никогда не перезапишет твой локальный код и не создаст конфликтов. `pull` же сразу пытается объединить скачанное с твоей текущей веткой.

> [!question] 2. Зачем использовать `fetch`, если есть `pull`?
> 
> **Ответ:** Чтобы провести **ревью**. Как инженер, ты хочешь сначала увидеть, что изменили коллеги (через `git log main..origin/main` или `git diff main origin/main`), убедиться, что код безопасен, и только потом делать `merge`. В DevOps-пайплайнах это стандарт безопасности.

> [!question] 3. Что произойдет, если коллега удалил ветку на GitHub, а у тебя она всё еще висит в списке удаленных? Как это исправить?
> 
> **Ответ:** Нужно запустить `git fetch --prune`. Она синхронизирует твой список удаленных веток с сервером и удалит те, которых больше нет.

> [!question] 4. Как с помощью `status` увидеть, что ты отстал от сервера?
> 
> **Ответ:** `git status` сам по себе не знает о сервере. Нужно сначала сделать `git fetch`, и тогда статус напишет: _"Your branch is behind 'origin/main' by 3 commits"_.

### 💡 Пример из жизни (Workflow инженера)

Представь, что ты работаешь в «Цитадели» над системой обработки трафика. Прежде чем начать работу, ты делаешь:

1. `git fetch` — узнал, что нового.
2. `git log HEAD..origin/main --oneline` — быстро глянул список новых коммитов.
3. Понял, что всё ок, и сделал `git merge`.
