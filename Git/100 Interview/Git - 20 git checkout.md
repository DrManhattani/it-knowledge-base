# 📖 Руководство: Git Checkout

### 1. Техническое определение

**git checkout** — это команда для переключения состояний. Она обновляет файлы в рабочем дереве, чтобы они соответствовали версии в указанной ветке или коммите, и перемещает указатель `HEAD`, чтобы фиксировать все последующие действия в новом контексте.

---
### 2. Три главных ипостаси checkout

Команда работает в трех разных плоскостях в зависимости от аргументов:

#### А. Работа с ветками (Навигация)

Когда ты пишешь `git checkout <branch_name>`, Гит:
1. Проверяет, нет ли в твоем рабочем дереве незакоммиченных изменений, которые могут быть затерты (защита данных).
2. Перемещает указатель `HEAD` на указанную ветку.
3. Обновляет файлы в папке проекта до состояния этой ветки.

#### Б. Работа с файлами (Восстановление)

Когда ты пишешь `git checkout <commit/branch> -- <file>`, Гит:
1. Не двигает `HEAD`. Ты остаешься на той же ветке.
2. Берет конкретный файл из указанного источника и **перезаписывает** им файл в твоем рабочем каталоге и индексе.

#### В. Создание веток (Дублирование функций `branch`)

Именно здесь `checkout` заменяет `git branch`. Флаг `-b` выполняет две команды разом: `git branch <name>` + `git checkout <name>`.

### 3. Таблица флагов git checkout

| **Флаг (+ полный)**   | **Описание механики и работы "под капотом"**                                                                                                         | **Пример**                   |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `-b`                  | **Создание и переход.** Создает новую ветку от текущего коммита и мгновенно переставляет на нее `HEAD`.                                              | `git checkout -b feature`    |
| `-B`                  | **Принудительный сброс.** Если ветка уже существует, Гит принудительно «перекинет» ее на текущий коммит (как `reset`), прежде чем переключиться.     | `git checkout -B main`       |
| `--`                  | **Разделитель.** Указывает Гиту, что дальше идут пути к файлам, а не имена веток. Защищает от ошибок, если файл называется так же, как ветка.        | `git checkout -- file.txt`   |
| `-f`<br><br>`--force` | **Силовой переход.** Игнорирует локальные изменения и переключает ветку, даже если это приведет к потере незакоммиченного кода.                      | `git checkout -f dev`        |
| `-p`<br><br>`--patch` | **Интерактивный откат.** Позволяет просмотреть изменения в файле по кусочкам (hunks) и выбрать, какие из них вернуть к исходному состоянию.          | `git checkout -p HEAD`       |
| `-m`<br><br>`--merge` | **Попытка слияния.** Если у тебя есть правки, Гит попытается сделать трехстороннее слияние между твоими правками и веткой, на которую ты переходишь. | `git checkout -m main`       |
| `--orphan`            | **Чистый лист.** Создает новую ветку без истории (первый коммит в ней будет корневым), но сохраняет все текущие файлы в индексе.                     | `git checkout --orphan docs` |

### 4. Гранд-сравнение: Checkout vs Reset vs Restore

Это самый важный раздел для понимания «хирургии» Гита.

|**Операция**|**git checkout**|**git reset**|**git restore**|
|---|---|---|---|
|**Цель**|Переключение контекста или откат файла.|Манипуляция историей и указателем ветки.|Специализированный откат файлов (безопаснее).|
|**Влияние на HEAD**|**Перемещает.** Теперь ты на другой ветке.|**Перемещает саму ветку**, на которой стоит HEAD.|**Не перемещает.**|
|**Безопасность**|Безопасна (предупредит о грязных файлах).|Опасна (в режиме `--hard` стирает всё).|Безопасна (четкое разделение индекса и дерева).|
|**Область действия**|Весь проект или файл.|Вся ветка (история).|Конкретные файлы.|

> [!NOTE] **Почему **`restore` **лучше для файлов?**
> 
> В `checkout` легко ошибиться: если ты забудешь имя файла, Гит может решить, что ты переключаешь ветку. `restore` лишен этой двусмысленности.
> 
> - `git checkout HEAD -- file` $\rightarrow$ `git restore --source=HEAD file`
>

### 5. Работа под капотом: Detached HEAD

Когда ты делаешь `git checkout <commit_hash>` (не ветку, а хеш), ты попадаешь в состояние **Detached HEAD**.

1. `HEAD` больше не указывает на ветку (например, `refs/heads/main`).
2. `HEAD` записывает хеш напрямую.
3. **Риск:** Если ты сделаешь коммиты здесь, они не будут принадлежать ни одной ветке. Как только ты переключишься на другую ветку, эти коммиты станут «невидимыми» для обычного `log` и позже будут удалены сборщиком мусора.

### 6. Вопросы с собеседований

#### 🟢 Junior (База)

- **Как отменить изменения в конкретном файле, чтобы он стал как в последнем коммите?**
    
    - _Ответ:_ `git checkout -- <file_path>` (или современный `git restore <file_path>`).
        
- **Что произойдет, если переключить ветку, имея незакоммиченные файлы?**
    
    - _Ответ:_ Если изменения не конфликтуют с целевой веткой, Гит перенесет их с собой. Если конфликтуют — Гит выдаст ошибку и запретит переход, чтобы ты не потерял данные.

#### 🟡 Middle (Инструментарий)

- **Чем `git checkout -b` отличается от `git branch <name>`?**
    
    - _Ответ:_ `git branch` только создает указатель. `git checkout -b` создает указатель и сразу перемещает туда `HEAD`, обновляя рабочую директорию.
        
- **Как вытащить файл из другой ветки, не переключаясь на нее?**
    
    - _Ответ:_ `git checkout <other_branch> -- <file_path>`. Это обновит файл в текущей рабочей директории и сразу добавит его в индекс (staged).

#### 🔴 Senior (Архитектура)

- **В чем разница между `git checkout` и `git reset --hard` применительно к файлам?**
    
    - _Ответ:_ `checkout` более избирателен и безопасен. При переключении веток он сохраняет твои локальные «неконфликтные» правки. `reset --hard` — деструктивная команда, которая приводит всё дерево к состоянию коммита, уничтожая любые локальные изменения без возможности восстановления (кроме тех, что были в индексе).
        
- **Как восстановить файл из `reflog` с помощью checkout?**
    
    - _Ответ:_ Найти хеш состояния до потери через `git reflog`, затем выполнить `git checkout <hash> -- <path>`.
