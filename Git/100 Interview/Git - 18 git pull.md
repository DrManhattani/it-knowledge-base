# 📖 Руководство: Git Pull

### 1. Техническое определение

**git pull** — это высокоуровневая команда («фарфоровая» команда), предназначенная для синхронизации локальной ветки с её удаленной версией.

С технической точки зрения это **комбинированная операция**, которая последовательно запускает две другие команды:

1. **git fetch**: загружает новые коммиты, объекты и ссылки из удаленного репозитория в вашу локальную базу данных (но не меняет ваш код).
    
2. **git merge** (по умолчанию) или **git rebase**: интегрирует скачанные изменения в вашу текущую рабочую ветку.

> [!QUOTE] **Простая аналогия**
> 
> `git fetch` — это как получить уведомление о том, что вышла новая версия программы.
> 
> `git pull` — это нажать кнопку «Скачать и немедленно установить».

---

### 2. Работа «под капотом»: Анатомия процесса

Когда вы вводите `git pull origin main`, происходит следующее:

1. **Сетевой этап (Fetch):** Git связывается с сервером `origin`, проверяет состояние ветки `main` и скачивает все недостающие объекты (коммиты, деревья, файлы).
    
2. **Запись в FETCH_HEAD:** Git записывает хеш последнего скачанного коммита в специальный файл `.git/FETCH_HEAD`. Это временная закладка.
    
3. **Интеграция:** Git смотрит на текущую ветку и на `FETCH_HEAD`.
    
    - Если ваша ветка не менялась, Git просто передвинет указатель вперед (**Fast-forward**).
        
    - Если у вас есть свои коммиты, Git создаст **Merge Commit** (соединит две истории) или выполнит **Rebase** (переклеит ваши коммиты сверху), в зависимости от настроек.

### 3. Таблица флагов git pull

| **Флаг (+ полный)** | **Подробное описание и логика работы**                                                                                                                                                               | **Пример**             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `--rebase`          | **Смена стратегии.** Вместо создания Merge-коммита Git берет ваши локальные изменения и «перекладывает» их поверх пришедших с сервера. Это создает линейную историю без «петель» слияния.            | `git pull --rebase`    |
| `--no-rebase`       | **Принудительный мердж.** Игнорирует глобальные настройки и заставляет Git создать Merge-коммит, даже если можно сделать Fast-forward или настроен ребейз.                                           | `git pull --no-rebase` |
| `--ff-only`         | **Режим безопасности.** Пулл сработает только в том случае, если историю можно просто «прокрутить» вперед. Если есть расхождения (конфликты), команда упадет с ошибкой, ничего не меняя.             | `git pull --ff-only`   |
| `--autostash`       | **Работа с грязным деревом.** Если у вас есть незакоммиченные правки, этот флаг сам сделает `stash`, выполнит пулл и потом сделает `stash pop`. Избавляет от ошибки "Please commit your changes...". | `git pull --autostash` |
| `--prune` (`-p`)    | **Чистка ссылок.** Удаляет локальные «следы» удаленных веток, которые уже были удалены на сервере (origin). Полезно для поддержания чистоты в списке веток.                                          | `git pull -p`          |
| `--tags`            | **Забор меток.** Принудительно скачивает все теги с сервера вместе с коммитами. По умолчанию Git тянет только те теги, что относятся к скачиваемым веткам.                                           | `git pull --tags`      |
| `--no-commit`       | **Пауза перед фиксацией.** Выполняет слияние, но не создает коммит автоматически. Это дает возможность проверить результат и внести правки перед финальным сохранением.                              | `git pull --no-commit` |
| `--depth <n>`       | **Мелкое скачивание.** Обрезает историю до указанного количества коммитов. Используется для экономии трафика и места на диске в огромных репозиториях.                                               | `git pull --depth 1`   |

### 4. Отдельный разбор: git pull --rebase

Это выбор профессионалов для работы в команде.

**Проблема обычного пулла:** Если вы и коллега правили `main`, после `git pull` в истории появится «пузырь» — коммит слияния типа _Merge branch 'main' of..._. Если в команде 10 человек, история превращается в запутанный клубок.

**Решение через `--rebase`:**

1. Git откладывает ваши локальные коммиты «в сторону».
2. Обновляет вашу ветку до состояния сервера.
3. Поочередно применяет ваши коммиты сверху.

**Результат:** Идеально прямая линия истории.

**Риск:** Если в ваших 5 коммитах один и тот же конфликт, вам придется решать его 5 раз (или использовать `git rerere`).

### 5. Вопросы с собеседований

#### 🟢 Junior (База)

- **В чем разница между `git fetch` и `git pull`?**
    
    - _Ответ:_ Fetch только скачивает данные, не меняя ваш код. Pull скачивает и сразу пытается внедрить их в текущую ветку.
        
- **Что произойдет, если во время `git pull` возникнет конфликт?**
    
    - _Ответ:_ Git остановит процесс интеграции, пометит файлы как конфликтующие и попросит вас разрешить их вручную, после чего нужно будет сделать коммит или продолжить ребейз.

#### 🟡 Middle (Инструментарий)

- **Как настроить Git, чтобы `pull` всегда делал `rebase` по умолчанию?**
    
    - _Ответ:_ С помощью команды `git config --global pull.rebase true`.
        
- **Зачем использовать `git pull --ff-only` в CI/CD пайплайнах?**
    
    - _Ответ:_ Чтобы гарантировать, что билд-сервер не создаст случайный Merge-коммит. Если история разошлась, пайплайн должен упасть, а не пытаться «починить» историю автоматически.

#### 🔴 Senior (Архитектура и внутренности)

- **Что такое `FETCH_HEAD` и как он связан с `ORIG_HEAD` при пулле?**
    
    - _Ответ:_ `FETCH_HEAD` хранит хеш последнего скачанного коммита с сервера. `ORIG_HEAD` сохраняет состояние вашей ветки **до** пулла, чтобы вы могли откатиться (`reset --hard ORIG_HEAD`), если слияние прошло неудачно.
        
- **Как работает `git pull` в условиях огромного монорепозитория?**
    
    - _Ответ:_ Здесь обсуждаются проблемы производительности. Можно упомянуть `sparse-checkout` (скачивание только нужных папок) и частичные клоны, так как обычный пулл на 100ГБ репозитории может «положить» сеть.

### 🎙 Инженерный совет (из "Pro Git")

Никогда не делайте `git pull`, если у вас есть незакоммиченные изменения, которые вы цените. Хотя `--autostash` помогает, лучший workflow — это:

1. `git stash`
2. `git pull --rebase`
3. `git stash pop`
