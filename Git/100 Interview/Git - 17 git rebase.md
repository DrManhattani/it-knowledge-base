# 🏗️ git rebase

> [!ABSTRACT] **Определение (Interview-ready)**
> **git rebase** — один из способов объединить изменения, сделанные в одной ветке, с другой веткой. Это наложение коммитов поверх другого базового коммита. Под базовым понимается тот коммит, к которому применяются коммиты выбранной ветки.
> 
> - Главная цель — поддержание **линейной истории** проекта, что критически важно для упрощения навигации по логам и эффективного использования `git bisect`.

### 🛠1. Полный справочник флагов git rebase

#### 1.1 Управление процессом (Flow Control)

Эти флаги используются, когда ребейз уже запущен и требует твоего вмешательства.

| **Флаг**      | **Алиас** | **Описание и технический нюанс**                                                       | **Пример**               |
| ------------- | --------- | -------------------------------------------------------------------------------------- | ------------------------ |
| `--continue`  | `-c`      | Продолжает процесс после исправления конфликтов или остановки по `edit`.               | `git rebase --continue`  |
| `--abort`     |           | Полная отмена. Возвращает `HEAD` на `ORIG_HEAD` и чистит временные файлы.              | `git rebase --abort`     |
| `--skip`      |           | Пропускает текущий коммит. Полезно, если изменения уже есть в целевой ветке.           | `git rebase --skip`      |
| `--quit`      |           | Прекращает ребейз, но **не** возвращает ветку назад. `HEAD` остается там, где застрял. | `git rebase --quit`      |
| `--edit-todo` |           | Позволяет отредактировать список команд прямо во время паузы в интерактивном режиме.   | `git rebase --edit-todo` |

#### 1.2 Режимы и модификаторы поведения

Основные инструменты для изменения того, как именно Гит переносит коммиты.

| **Флаг**          | **Алиас** | **Описание и технический нюанс**                                                     | **Пример**                        |
| ----------------- | --------- | ------------------------------------------------------------------------------------ | --------------------------------- |
| `--interactive`   | `-i`      | Запуск интерактивного режима с Todo-листом в редакторе.                              | `git rebase -i HEAD~10`           |
| `--onto <new>`    |           | «Хирургический» перенос. Позволяет указать новый фундамент в обход старого родителя. | `git rebase --onto main dev feat` |
| `--rebase-merges` | `-r`      | Пытается воссоздать структуру мерджей вместо их линеаризации (схлопывания в линию).  | `git rebase -r master`            |
| `--exec <cmd>`    | `-x`      | Выполняет shell-команду после **каждого** созданного коммита.                        | `git rebase -x "npm test"`        |
| `--root`          |           | Позволяет перебазировать историю, начиная с самого первого (корневого) коммита.      | `git rebase -i --root`            |
| `--merge`         | `-m`      | Использует механику 3-стороннего слияния. Лучше распознает переименования файлов.    | `git rebase -m master`            |

#### 1.3 Автоматизация и удобство

Флаги, которые экономят время на рутинных операциях.

| **Флаг**       | **Алиас** | **Описание и технический нюанс**                                                           | **Пример**                      |
| -------------- | --------- | ------------------------------------------------------------------------------------------ | ------------------------------- |
| `--autostash`  |           | Автоматически делает `stash` перед ребейзом и `apply` после. Спасает от «грязного» дерева. | `git rebase master --autostash` |
| `--autosquash` |           | Авто-сортировка Todo-листа, если были коммиты с пометкой `--fixup` или `--squash`.         | `git rebase -i --autosquash`    |
| `--no-stat`    | `-n`      | Не выводит diffstat (список измененных файлов) после завершения операции.                  | `git rebase -n master`          |
| `--quiet`      | `-q`      | Максимально тихий режим. Полезно для автоматизированных скриптов.                          | `git rebase -q master`          |
| `--verbose     | `-v`      | Наоборот: выводит подробнейший лог всего, что Гит делает под капотом.                      | `git rebase -v master`          |

### 2. Внутренняя механика (Under the Hood)

Когда ты запускаешь `git rebase <newbase>`, Git выполняет следующий алгоритм:

1. **Вычисление разницы (Patch Generation):** Git находит ближайшего общего предка (`merge-base`) между текущей веткой (`HEAD`) и `<newbase>`. Он собирает все коммиты, сделанные в текущей ветке после этого предка, и сохраняет их в виде **временных патчей** (в директории `.git/rebase-apply`).
2. **Сброс состояния (Reset):** Текущая ветка принудительно переставляется (`reset --hard`) на коммит `<newbase>`. В этот момент твои локальные изменения «исчезают» из истории ветки, и она становится идентичной цели ребейза.
3. **Применение (Replay):** Git поочередно берет сохраненные патчи и пытается применить их к новому состоянию.
	* Для каждого патча создается **новый объект коммита**.
	* У этого коммита будет **новый родитель**, новое время создания и, как следствие, **полностью другой SHA-1 хеш**.
4. **Обновление указателей:** После успешного применения последнего патча, указатель ветки (branch ref) обновляется на последний созданный коммит.

---
### 3. Золотое правило Rebase (The Golden Rule)

>[!attention] Никогда не делай rebase для коммитов, которые уже были отправлены (push) в общий репозиторий.
> **Почему?** Поскольку `rebase` меняет хеши, для Git твои переписанные коммиты — это совершенно новые объекты. Если коллега уже скачал твои старые коммиты и начал на них работать, после твоего `push --force` его история разойдется с серверной. Это приведет к «адскому слиянию» и дублированию коммитов в истории.

---
### 4. Интерактивный режим (Interactive Rebase)

Команда `git rebase -i` открывает текстовый файл (TODO-лист), который позволяет манипулировать историей до того, как она будет «зацементирована». Основные операции:

* **pick**: оставить коммит как есть.
* **reword**: изменить только сообщение коммита (не меняя код).
* **edit**: остановиться для редактирования содержимого коммита (можно разбить один коммит на два).
* **squash**: слить коммит с предыдущим, объединив их сообщения.
* **fixup**: слить коммит с предыдущим, выбросив сообщение текущего (идеально для мелких правок опечаток).
* **drop**: полностью удалить коммит из истории.

### 🧪 20 Профессиональных вопросов для собеседования

#### 🟢 Уровень: Junior / Middle

1. **Что произойдет с оригинальными коммитами после успешного ребейза?**
* *Ответ:* Они остаются в базе объектов Git, но на них больше не ссылается ни одна ветка. Со временем их удалит `git gc` (сборщик мусора), если на них нет ссылок в `reflog`.


2. **В чем разница между `merge` и `rebase` при разрешении конфликтов?**
* *Ответ:* В `merge` ты решаешь все конфликты один раз в одном Merge Commit. В `rebase` ты можешь решать конфликты **для каждого коммита в цепочке** отдельно.


3. **Как отменить ребейз, если ты в процессе и всё пошло не так?**
* *Ответ:* `git rebase --abort`.


4. **Что такое `git pull --rebase`?**
* *Ответ:* Это комбинация `fetch` и `rebase` текущей ветки поверх `origin/branch`. Это стандарт для чистой работы в команде.


5. **Как `rebase` влияет на `git bisect`?**
* *Ответ:* Положительно. Линейная история позволяет `bisect` быстро находить коммит, внесший баг, без путаницы с параллельными ветками.


6. **Можно ли сделать rebase на ветку, которая старше текущей?**
* *Ответ:* Да, технически это возможно, но это приведет к «откату» базовой точки.


7. **Что делает флаг `--autosquash`?**
* *Ответ:* Он автоматически подготавливает список для интерактивного ребейза, если ты заранее помечал коммиты как `fixup!` или `squash!`.


8. **Как пропустить коммит во время ребейза, если он вызывает конфликт, который тебе не нужен?**
* *Ответ:* `git rebase --skip`.


9. **Что будет, если сделать rebase ветки на саму себя?**
* *Ответ:* Ничего не произойдет, Git сообщит, что ветка уже актуальна.


10. **Почему после ребейза часто приходится делать `push --force`?**
* *Ответ:* Потому что история локальной ветки теперь фундаментально отличается от удаленной (из-за новых хешей), и Git запрещает обычную перезапись.

#### 🔴 Уровень: Senior / DevOps

11. **Объясни команду `git rebase --onto <newbase> <upstream> <branch>`.**
* *Ответ:* Это «хирургический» ребейз. Позволяет взять изменения из `branch`, которые были сделаны после `upstream`, и пересадить их на `newbase`, даже если `upstream` и `newbase` не связаны.


12. **Как восстановить данные, если ты сделал `rebase -i`, удалил нужные коммиты и сделал `push --force`?**
* *Ответ:* Нужно зайти в `git reflog`, найти хеш ветки до ребейза и сделать `git reset --hard <hash>`. `reflog` хранит историю перемещения `HEAD` даже после изменения истории.


13. **Что такое `git rerere` и как он помогает при ребейзе?**
* *Ответ:* *Reuse Recorded Resolution*. Если ты часто делаешь ребейз и решаешь одни и те же конфликты, `rerere` запоминает твое решение и применяет его автоматически в следующий раз.


14. **Как `rebase` работает с пустыми коммитами (например, если изменения уже влиты в мастер другим путем)?**
* *Ответ:* Git обычно отбрасывает их автоматически. Если нужно оставить — используется флаг `--keep-empty`.


15. **Влияет ли `rebase` на GPG-подписи коммитов?**
* *Ответ:* Да, подписи становятся невалидными, так как хеш и данные коммита меняются. После ребейза коммиты нужно переподписывать.


16. **Можно ли сделать интерактивный ребейз, чтобы изменить порядок коммитов? Какие риски?**
* *Ответ:* Да, в списке `-i` можно просто поменять строки местами. Риск — логические конфликты (например, коммит 2 использует переменную, созданную в коммите 1).


17. **Как выполнить ребейз сразу нескольких веток?**
* *Ответ:* Стандартной команды нет, обычно используется цикл в bash или сторонние инструменты типа `git-town`.


18. **Что такое "functional" vs "procedural" история в контексте спора Merge vs Rebase?**
* *Ответ:* Merge сохраняет процедурную историю (как всё было на самом деле). Rebase создает функциональную историю (как это должно выглядеть для чистоты понимания).


19. **Как настроить Git так, чтобы `pull` всегда делал `rebase` по умолчанию?**
* *Ответ:* `git config --global pull.rebase true`.


20. **Что происходит с `merge commits` при ребейзе?**
* *Ответ:* По умолчанию они «схлопываются» (линеаризуются). Чтобы сохранить структуру слияний, нужно использовать флаг `--rebase-merges`.
