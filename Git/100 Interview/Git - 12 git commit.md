# Команда git commit

> [!ABSTRACT] **Суть команды**
> 
> **git commit** — это операция, которая фиксирует содержимое Индекса (Staging Area) в виде нового «снимка» (snapshot) в локальном репозитории. Каждый коммит — это неизменяемая точка в истории, к которой можно вернуться.

---
### 🔩 Что происходит под капотом (Алгоритм)

Когда ты вводишь `git commit`, Git выполняет следующие действия:

1. **Создание дерева (Tree):** Git упаковывает текущее состояние Индекса в объект типа `tree`.
2. **Создание объекта коммита:** Создается текстовый файл (объект `commit`), который содержит:
    - Хеш корневого `tree`.
    - Хеш **родительского коммита** (то, на что указывал HEAD до этого).
    - Данные автора и коммиттера (имя, email, дата).
    - Текст сообщения.
3. **Хеширование:** Git вычисляет SHA-1 хеш этого нового объекта.
4. **Обновление указателей:** Git перезаписывает хеш в файле текущей ветки (например, `.git/refs/heads/main`) на новый хеш. HEAD автоматически перемещается за веткой.

### 🛠️ Таблица флагов `git commit`

| **Флаг**           | **Описание**                                                                    | **Пример**                     |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------ |
| `-m`               | Задает сообщение коммита прямо в строке. Без него откроется текстовый редактор. | `git commit -m "Fix bug"`      |
| `-a`               | Автоматически делает `add` для всех **уже отслеживаемых** измененных файлов.    | `git commit -am "Update code"` |
| `--amend`          | Позволяет изменить последний коммит (сообщение или добавить забытые файлы).     | `git commit --amend`           |
| `-v` (`--verbose`) | Показывает в редакторе дифф (разницу кода) прямо под местом для сообщения.      | `git commit -v`                |
| `--allow-empty`    | Позволяет создать коммит вообще без изменений кода. Полезно для тестов CI/CD.   | `git commit --allow-empty`     |
| `--no-verify`      | Пропускает выполнение хуков (например, pre-commit тесты или линтеры).           | `git commit -n`                |

### ❓ Потенциальные вопросы на собеседовании

> [!question] 1. В чем разница между `git commit -m` и `git commit -am`?
>- **Ответ:** Флаг `-a` автоматически добавляет изменения в индекс, но только для тех файлов, которые Git уже знает (отслеживает). **Новые (untracked) файлы через** `-a` **не добавятся.** Их всё равно нужно добавлять вручную через `git add`.

>[!question] 2. Как изменить сообщение последнего коммита?
>- **Ответ:** С помощью команды `git commit --amend -m "Новое сообщение"`. Если коммит уже был отправлен в удаленный репозиторий (push), после этого придется делать `push --force`.

>[!question] 3. Что такое "Атомарный коммит" (Atomic Commit)?
>- **Ответ:** Это практика, при которой один коммит содержит изменения только для одной логической задачи (одна фича или один багфикс). Если коммит «ломает» сборку или содержит несвязанные правки — он не атомарен. Это важно для того, чтобы при необходимости можно было легко откатить конкретное изменение.
>- Атомарный коммит — это коммит, представляющий одно логическое изменение, которое можно применить или откатить как единое целое. Это улучшает читаемость истории, упрощает отладку и повышает надёжность системы контроля версий.

>[!question] 4. Зачем Git разделяет "Автора" (Author) и "Коммиттера" (Committer)?
>- **Ответ:** **Автор** — это тот, кто физически написал код. **Коммиттер** — это тот, кто применил этот код в репозиторий. Они могут различаться, например, если вы применили чужой патч или сделали `rebase` чужих коммитов.

>[!question] 5. Что произойдет, если запустить `git commit` без флага `-m`?
>- **Ответ:** Git откроет текстовый редактор, установленный по умолчанию (обычно Vim или Nano), чтобы вы могли написать развернутое сообщение. Если закрыть редактор, не введя текст, коммит будет отменен.

# git commit --amend

> [!ABSTRACT] **Суть команды**
> 
> Команда `--amend` позволяет взять текущее состояние **Индекса** (Staging Area) и объединить его с **последним коммитом**, создав вместо него новый, исправленный коммит.

### 🛠️ Основные сценарии использования

#### 1. Изменение сообщения (самый частый случай)

Если ты просто хочешь переписать текст последнего коммита, не меняя код.
- **Команда:** `git commit --amend -m "Новое правильное сообщение"`

#### 2. Добавление забытых файлов

Если ты сделал коммит, но забыл добавить файл или одну строчку кода.
- **Как делать:**  
    1. Исправь файл или добавь забытый через `git add <file>`.
    2. Выполни `git commit --amend --no-edit`.
- **Результат:** Файл «докинется» в последний коммит, а сообщение останется прежним (благодаря `--no-edit`).

#### 3. Удаление лишних файлов из коммита

Если ты случайно закоммитил лишний конфиг или логи.
- **Как делать:**
    1. Удали файл из индекса: `git rm --cached <file>`.
    2. Выполни `git commit --amend --no-edit`.
- **Результат:** Файл исчезнет из последнего коммита, но останется у тебя в папке.


#### 4. Изменение метаданных (Автор, Дата)

Иногда нужно «подделать» время или автора коммита (например, если коммитил с неправильной почты).
- **Смена автора:** `git commit --amend --author="Name <email@example.com>"`
- **Смена даты на текущую:** `git commit --amend --date="$(date)"`

---

### 🔩 Что происходит под капотом?

Важнейший технический нюанс: **`amend` не редактирует старый коммит**. Он создает **совершенно новый объект коммита** с новым SHA-1 хешем и подменяет им старый.
1. Git берет родителя текущего коммита.
2. Берет текущий Индекс.
3. Создает новый коммит, который ссылается на того же родителя.
4. Указатель ветки перемещается на этот новый коммит.
5. Старый коммит остается «висеть» в базе (его можно найти через `git reflog`), пока его не удалит сборщик мусора.

---

### ⚠️ Золотое правило: Не аменди публичное!

> [!DANGER] **Важное предупреждение**
> 
> Никогда не используй `--amend` для коммитов, которые ты уже **запушил (push)** в общий репозиторий.
> 
> Поскольку хеш коммита меняется, для Git это будет выглядеть так, будто ты удалил старую историю и создал новую. Это вызовет конфликты у всей команды и потребует `push --force`.

---
### ❓ Вопросы на собеседовании по --amend

**1. Меняется ли хеш коммита при использовании `--amend`?**
- **Ответ:** Да, всегда. Даже если ты не менял код, а только сообщение — хеш будет другим, так как данные объекта изменились.

**2. Можно ли с помощью `amend` исправить коммит, который был три шага назад?**
- **Ответ:** Нет, `--amend` работает **только с самым последним** коммитом. Для исправления более старой истории нужно использовать `git rebase -i` (интерактивный ребейс).

**3. Что делать, если я сделал `--amend` и всё испортил? Как вернуть старый коммит?**
- **Ответ:** Нужно использовать `git reflog`. Там можно найти хеш старого коммита (который был до аменда) и откатиться к нему командой `git reset --hard <hash>`.
