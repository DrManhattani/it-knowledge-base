# 🌐 Полный инженерный справочник по IPv6

> [!INFO] **Зачем это DevOps инженеру?**
> 
> В Enterprise-сетях (офисах) IPv6 почти не встречается из-за повсеместного NAT. Однако в BigTech, Cloud-инфраструктуре (Kubernetes Dual-Stack), телекоме (LTE/5G) и IoT — это индустриальный стандарт. Незнание IPv6 ведет к «необъяснимым» падениям контейнеров, ошибкам привязки сокетов в Nginx и проблемам маршрутизации в дата-центрах.

## 1. 🔤 Синтаксис и правила сокращения

IPv6-адрес состоит из **128 бит** (8 групп по 4 шестнадцатеричных символа, разделенных двоеточием).

**Полный адрес:** `2001:0db8:0000:0000:0000:ff00:0042:8329`

> [!TIP] **Правила сжатия (Zero Compression)**
> 
> 1. **Ведущие нули:** В любой группе можно отбросить нули слева. (`0db8` ➡️ `db8`, `0042` ➡️ `42`, `0000` ➡️ `0`).
>     
> 2. **Группы нулей:** Несколько идущих подряд блоков нулей можно заменить на двойное двоеточие `::`.
>     
> 
> ⚠️ **Критическое правило:** Символ `::` можно использовать **только один раз** в адресе! Иначе стек ОС не поймет, сколько нулей восстанавливать.

**Идеально сжатый адрес:** `2001:db8::ff00:42:8329`

## 2. 🧬 Анатомия адреса IPv6 (Global Unicast Address)

Глобальный адрес IPv6 (GUA) — это аналог «белого» публичного IP-адреса в IPv4. Он имеет жестко стандартизированную структуру, которая решает главную проблему старого интернета: фрагментацию таблиц маршрутизации.
По стандарту (RFC 4291) 128 бит адреса делятся на три логические части по правилу **48 + 16 + 64**.

|**Размер блока**|**Название**|**Кто выдает / Чем управляет**|**Суть**|
|---|---|---|---|
|**48 бит**|Global Routing Prefix|IANA ➡️ LIR ➡️ Провайдер (ISP)|Уникальный ID вашей компании в мире.|
|**16 бит**|Subnet ID|Системный администратор / DevOps|65 536 подсетей для внутренних нужд. Каждому VLAN — своя `/64`.|
|**64 бита**|Interface ID|Выдается по SLAAC или DHCPv6|Уникальный ID хоста (часто на основе MAC-адреса).|


> [!ABSTRACT] **Визуальная карта адреса (128 бит)**
> 
> 
> ```Plaintext
> 2001:0db8:ac10 : 0001 : 0000:0000:0000:0055
> |______________| |____| |___________________|
>        |           |              |
>  [1] 48 бит     [2] 16 бит    [3] 64 бита
> Routing Prefix  Subnet ID    Interface ID
> ```

### 2.1🌍 Global Routing Prefix (Первые 48 бит)

Это идентификатор **твоей сети в масштабах всей планеты**. Именно на эти 48 бит смотрят магистральные маршрутизаторы провайдеров (BGP), чтобы доставить пакет до твоего офиса или дата-центра.

- **Как это выдается:**
    1. **IANA** (Корневой регистратор) выдает огромный блок `2000::/3` региональным регистраторам (например, RIPE в Европе).
    2. **RIPE** отпиливает кусок (обычно `/32`) и отдает его крупному провайдеру (ISP).
    3. **Провайдер** отпиливает кусок `/48` и отдает его конечной компании (тебе).

> [!INFO] **Математика** `2000::/3`
> 
> Почему все глобальные адреса начинаются на **2** или **3**?
> 
> Маска `/3` означает, что первые 3 бита жестко зафиксированы как `001`.
> 
> Четвертый бит может быть `0` (получается `0010`, то есть **2** в шестнадцатеричной системе) или `1` (получается `0011`, то есть **3**). Остальные варианты (4, 5, A, F) аппаратно не попадают в этот блок.

### 2.2 🏢 Subnet ID (Следующие 16 бит)

Это зона ответственности **системного администратора / DevOps-инженера**. Провайдер доставил трафик до твоего пограничного роутера (на основе первых 48 бит). Дальше ты сам решаешь, как делить сеть.

- **Масштаб возможностей:** 16 бит дают тебе **$2^{16} = 65 536$** подсетей.
- **Новая парадигма:** В IPv4 инженеры постоянно занимались _субнеттингом_ (высчитывали маски `/26`, `/29`, чтобы сэкономить адреса для P2P линков или маленьких отделов). В IPv6 это считается дурным тоном.
- **Золотое правило IPv6:** Одному VLAN / одному Docker-мосту / одному физическому линку всегда выделяется ровно одна подсеть `/64`. Экономить не нужно.

### 2.3 💻 Interface ID (Последние 64 бита)

Это идентификатор конкретного хоста (ПК, сервера, телефона) внутри подсети. 64 бита — это **$2^{64}$** (более 18 квинтиллионов) адресов в _каждой_ подсети.
Существует два основных способа, как операционная система генерирует себе этот «хвост»:

#### 2.3.1 Метод А: EUI-64 (На основе MAC-адреса)

Это классический аппаратный метод. ОС берет физический MAC-адрес (48 бит) и математически растягивает его до 64 бит.

**Алгоритм EUI-64 (Частый вопрос на собеседованиях):**

1. Берем MAC-адрес: `00:11:22:33:44:55`.
2. Разрезаем его ровно пополам: `00:11:22` и `33:44:55`.
3. Вставляем в середину зарезервированные 16 бит **`FF:FE`**.
    - Получается: `00:11:22:FF:FE:33:44:55`.
4. **Инвертируем 7-й бит** (Универсальный/Локальный бит) в первом байте.
    - Первый байт `00` (в бинаре `0000 0000`) превращается в `02` (`0000 0010`).
    - **Финальный Interface ID:** `0211:22FF:FE33:4455`.

#### 2.3.2 Метод Б: Privacy Extensions (RFC 4941)

> [!WARNING] **Проблема приватности EUI-64**
> 
> Если Interface ID жестко привязан к MAC-адресу твоего ноутбука, то куда бы ты ни пришел (в кафе, домой, в офис), вторая половина твоего IPv6-адреса будет **одинаковой**. Корпорации и рекламные сети могли бы отслеживать перемещение твоего устройства по всему миру.

Чтобы этого избежать, современные ОС (Windows, macOS, Linux, iOS, Android) по умолчанию используют **Privacy Extensions**.
- Система генерирует случайный 64-битный Interface ID.
- Каждые несколько часов или при переподключении к сети этот хвост меняется.
- MAC-адрес больше не светится в интернете. EUI-64 сегодня используется в основном только на серверах и маршрутизаторах, где важен статичный предсказуемый адрес.

#### 2.3.3 ⚠️ Реалии провайдеров (DevOps Грабли)

Стандарт RFC 3177 предписывает всем провайдерам выдавать конечным клиентам блок `/48`. Но в реальности провайдеры часто жадничают.
Если ты будешь настраивать корпоративную сеть, внимательно смотри, какой префикс отдал провайдер:

- **Выдали `/48`:** Идеально. У тебя честные 65 536 подсетей (16 бит для Subnet ID).
- **Выдали `/56`:** Провайдер забрал 8 бит себе. У тебя осталось только 8 бит для подсетей (всего 256 VLAN-ов). Для среднего офиса хватит, но архитектуру придется планировать внимательнее.
- **Выдали `/64`:** Провайдер повел себя непрофессионально. Твой роутер не сможет создать ни одной внутренней подсети (Subnet ID равен 0 бит). Вся твоя компания/квартира будет вынуждена работать в одном плоском L2-домене.

## 3. 📚 Классификация адресов (IPv4 vs IPv6)

> [!WARNING] **Главный сдвиг парадигмы (DevOps Alert)**
> 
> В IPv4 правило звучит так: _«Один интерфейс = Один IP-адрес»_ (обычно).
> 
> В IPv6 правило звучит так: _«Один интерфейс = **Множество** IP-адресов»_.
> 
> У любого активного устройства всегда есть как минимум один локальный адрес (::fe80::), и к нему могут добавляться глобальные (::2000::) или корпоративные (::fd00::).

Ниже представлен полный разбор типов адресов с прямой привязкой к их аналогам из старого мира IPv4.

### 3.1 🗺 Сводная таблица трансляции (Cheat Sheet)

Эта таблица — твой главный справочник при чтении сетевых дампов или логов Nginx.

| **Концепт в IPv4**    | **Аналог в IPv6** | **Название в IPv6** | **Описание и область действия**                      |
| --------------------- | ----------------- | ------------------- | ---------------------------------------------------- |
| **Белые IP**          | `2000::/3`        | Global Unicast      | Публичный интернет. Маршрутизируется везде.          |
| `10.x.x.x`        | `fd00::/8`        | ULA (Unique Local)  | Корпоративные серые сети. В интернет не выходят.     |
| `169.254.x.x`     | `fe80::/10`       | Link-Local          | Служебные адреса провода. Маршрутизация запрещена.   |
| `224.x.x.x`       | `ff00::/8`        | Multicast           | Групповая рассылка. Полностью заменяет Broadcast.    |
| `255.255.255.255` | `ff02::1`         | All-Nodes Multicast | Рассылка всем узлам в локальном сегменте.            |
| `0.0.0.0/0`       | `::/0`            | Default Route       | Маршрут по умолчанию (шлюз последней надежды).       |
| `0.0.0.0/32`      | `::/128`          | Unspecified         | Для сокетов (слушать все интерфейсы) / DAD.          |
| `127.0.0.1`       | `::1/128`         | Loopback            | Петля для обращения локальных сервисов к самим себе. |

### 3.2 🌍 Global Unicast (GUA) — Глобальные адреса

**Блок: `2000::/3` (Адреса начинаются на `2` или `3`)**
Это основа современного интернета. Адреса, которые IANA выдает провайдерам, а те — дата-центрам и мобильным телефонам.
- **Структура:** Строго подчиняются правилу маршрутизации **48 + 16 + 64** (Routing Prefix + Subnet + Interface ID).
- **Применение:** Доступ к публичным веб-серверам, API, маршрутизация трафика между континентами.

### 3.3 🏢 Unique Local (ULA) — Корпоративные адреса

**Блок:** `fc00::/7` (::На практике всегда fd00::/8)

Аналог "серых" сетей (RFC 1918) из IPv4 (`10.0.0.0/8`, `192.168.0.0/16`).
- **Почему FD, а не FC?** Восьмой бит (L-бит) определяет статус адреса. `0` (FC) планировался для централизованной раздачи, но от этого отказались. `1` (FD) означает, что адрес сгенерирован администратором локально. Поэтому рабочие конфиги всегда начинаются с `fd`.
- **Применение:** Закрытые сети дата-центров, внутренние кластеры Kubernetes, базы данных, не имеющие (и не долженствующие иметь) выхода в глобальный интернет.

> [!note] А как на практике?
> - На практике используется `fd00::/8`
> - **40 бит** выделяется на *глобальный префикс*, который определяется правилами RFC 4193.
> - **16 бит** выделяется на *подсеть*
> - **64 бита** выделяется на *идентификатор интерфейса* (адрес хоста)

### 3.4 🔌 Link-Local (LLA) — Локальные адреса канала

Самый важный служебный блок IPv6. В отличие от APIPA в IPv4 (который появляется только при аварии DHCP), Link-Local создается **сразу и навсегда** при поднятии сетевого интерфейса. Предназначен исключительно для связи в пределах одного физического или логического сегмента (L2-домена / VLAN).

> [!note] 3.4.1 🧮 ДИАПАЗОН `FE80` ... `FEBF`
> Разгадка кроется в строгих правилах формирования (RFC 4291):
> 1. Первые 10 бит фиксированы: `1111 1110 10` (что дает блок от `FE80` до `FEBF`).
> 2. **Следующие 54 бита строго обязаны быть нулями** (`0`).**
> 3. Оставшиеся 64 бита выделяются под идентификатор интерфейса (Interface ID).
> Из-за жесткого требования заполнять середину адреса нулями, первая группа шестнадцатеричных символов **всегда** будет схлопываться именно в `fe80`.
> Значения `fe81`, `fe8a`, `fe90` или `febf` технически входят в подсеть `/10`, но **никогда не используются** в реальных операционных системах, так как это нарушит структуру адреса. На практике этот блок ведет себя как `fe80::/64`.

> [!abstract] 3.4.2 🧱 ЛОГИКА МАРШРУТИЗАТОРА (DROP RULE)
> - **Правило L3:** Роутеры аппаратно отбрасывают (Drop) любые пакеты с адресом источника или назначения `fe80::`.
> - Что значит «роутер аппаратно отбрасывает пакет»? Чтобы это понять, нужно разделить две функции маршрутизатора: **обработку** трафика (Control Plane) и **пересылку** трафика (Data Plane).
> 1. **Когда роутер ОТБРАСЫВАЕТ (Drop) пакет:**
>     Если на роутер (например, на порт `eth0`) прилетает пакет, у которого _Source IP_ или _Destination IP_ начинается с `fe80::`, и таблица маршрутизации говорит, что этот пакет нужно переслать в другую сеть (например, в порт `eth1`), роутер его **уничтожает**.
>     _Почему?_ Потому что зона действия (Scope) адреса `fe80::` ограничена одним проводом. Выпускать его за пределы свитча — нарушение стандарта. Роутер выступает «стеной» для таких пакетов.
> 2. **Когда роутер НЕ ОТБРАСЫВАЕТ пакет:**
>     Если пакет с адресом `fe80::` предназначен **самому роутеру** (его интерфейсу `eth0`). Например, компьютер шлет роутеру запрос «Дай мне глобальный префикс». Роутер примет этот пакет, обработает его процессором и ответит. Он не пересылает его дальше, он выступает конечной точкой.

> [!info] 3.4.3 ⚙️ КАК ЭТО РАБОТАЕТ В СЕТИ
> Зачем генерировать этот адрес, если устройства в итоге общаются по глобальным IP? Вот две главные задачи, где `fe80::` является фундаментом.
>> [!summary] 3.4.3.1📡 Замена ARP (Протокол NDP)
>> В IPv4, чтобы узнать MAC-адрес соседа, компьютер кричит на всю сеть (Broadcast). В IPv6 он отправляет точечный мультикаст-запрос (Neighbor Solicitation).
>> **Проблема:** Чтобы отправить IP-пакет (даже мультикаст), у компьютера **уже должен быть** IP-адрес отправителя (Source IP). А глобальный IP он еще не успел получить от роутера!
>> **Решение:** Компьютер использует свой Link-Local адрес.
>> - **Логика:** «Я отправляю запрос со своего `fe80::A`, ищу MAC-адрес владельца `fe80::B`».
>>     Поскольку `fe80::` есть у всех с первой секунды загрузки ОС, компьютеры могут находить MAC-адреса и общаться друг с другом напрямую через свитч, даже если интернет-кабель вообще отрезан.
>
>> [!summary] 3.4.3.2 🗺️ Next-Hop в таблицах маршрутизации
>> Это самая неочевидная для новичков фича IPv6, которая сильно упрощает жизнь DevOps и сетевикам.
>> В классическом IPv4 таблица маршрутизации (OSPF, BGP) выглядит так:
>> - _Маршрут до Гугла -> переслать на IP соседа `192.168.1.1`_
>>     Если админ решит поменять IP-адрес на роутере-соседе, маршрут сломается, сеть упадет.
>> В IPv6 маршрутизация отделена от глобальной адресации:
>> - _Маршрут до Гугла -> переслать на IP соседа `fe80::1111:2222:3333:4444`_
>>     **Преимущество:** Link-Local адрес привязан к MAC-адресу железяки (роутера) и **никогда не меняется**. Вы можете менять глобальные IPv6-адреса на портах маршрутизаторов каждый день, но таблица OSPF не упадет, потому что роутеры перекидывают транзитный трафик друг другу, ориентируясь исключительно на неизменные `fe80::` адреса.

В IPv4 APIPA (`169.254.x.x`) — это костыль при сбое DHCP. В IPv6 Link-Local (`::fe80::`) — это **фундамент работы протокола**. Сетевая карта генерирует его мгновенно при включении.

> [!IMPORTANT] **Зачем нужен **`fe80::`?
> 
> 1. **Стабильность маршрутизации:** В таблицах маршрутизации (OSPFv3, BGP) Next-Hop **всегда** указывает на `fe80::` адрес соседнего роутера. Смена белых IP на интерфейсах не ломает сеть.
>     
> 2. **Замена ARP (Протокол NDP):** Для поиска MAC-адресов соседей устройства используют системные сообщения ICMPv6, отправляемые со своих Link-Local адресов.
>     
> 3. **Не маршрутизируется:** Пакет с `fe80::` никогда не пройдет через роутер. Его жизнь ограничена одним L2-доменом (VLAN/Свитч).
>     

## 4. 📡 Multicast — Групповая рассылка

**Блок: `ff00::/8` (Всегда начинается с `FF`)**

В IPv6 нет бродкаста (широковещания). Любое обращение к группе узлов идет через мультикаст. Структура мультикаст-адреса включает в себя флаги и "Scope" (радиус действия — локально, в пределах офиса, в пределах интернета).

> [!ABSTRACT] **Критически важные Multicast-группы:**
> 
> - `ff02::1` **(All-Nodes):** Все IPv6-узлы в локальной сети. Роутер пишет сюда свои анонсы (Router Advertisement).
>     
> - `ff02::2` **(All-Routers):** Все маршрутизаторы в локальной сети. Хосты пишут сюда запросы (Router Solicitation), чтобы получить IP.
>     
> - `ff02::1:ffXX:XXXX` **(Solicited-Node):** Точечный мультикаст для замены протокола ARP. Каждое устройство слушает свой персональный суффикс, не отвлекая процессор на чужие запросы.
>     

### 4.1 🎯 Убийца Бродкаста: Solicited-Node Multicast

IPv6 полностью отказался от широковещания (Broadcast), чтобы не тратить процессорное время (CPU) всех устройств в сети на мусорные ARP-запросы. Вместо этого используется **аппаратный мультикаст**.
#### 4.1.1 Как ПК узнает MAC-адрес соседа (без Broadcast):

1. **[L3] Формирование Target IP:** К префиксу `FF02::1:FF` приклеиваются последние 24 бита искомого IPv6-адреса. Получается Solicited-Node IP (например, `FF02::1:FF33:4444`).
2. **[L2] Трансляция в MAC:** Любой IPv6-мультикаст в сетях Ethernet обязан начинаться с MAC-префикса `33:33`. К нему приклеиваются последние 32 бита из IP. Получается целевой MAC `33:33:ff:33:44:44`.
3. **[Аппаратный фильтр]:** Сетевые карты аппаратно игнорируют чужие MAC-адреса. Пакет обрабатывает только тот ПК, чьи 24 бита совпали. ОС остальных устройств даже не просыпается.

> [!ABSTRACT] **Диаграмма трансляции (L3 ➡️ L2)**
> 
> ```Plaintext
> [Искомый IPv6]    fe80::1111:2222: [3333:4444]  <-- Берем последние 24 бита
>                                         |
> [L3 Multicast]    FF02::1:FF[00:00]  +  V
> [IP Packet DST] = FF02:0000:0000:0000:0000:0001: [FF33:4444] <-- Берем 32 бита
>                                                      |
> [L2 MAC Prefix]   33:33: [00:00:00:00]  +            V
> [Ethernet DST]  = 33:33:  FF:33:44:44
> ```

## 5. 👻 Anycast — Невидимый тип (Произвольная рассылка)

Это не отдельный диапазон адресов, а **способ их использования**.

Anycast-адрес внешне выглядит как обычный Global Unicast, но он назначается **одновременно нескольким серверам** в разных частях земного шара.

- **Как работает:** Пакет доставляется **только одному** серверу — тому, к которому ближе метрика маршрутизации (самый короткий путь по BGP).
- **Применение (DevOps):** Так работают DNS-серверы Google (`8.8.8.8` или `2001:4860:4860::8888`) и балансировщики Cloudflare. Ты обращаешься к одному IP-адресу, но в Европе тебе отвечает сервер из Франкфурта, а в Азии — сервер из Токио.
