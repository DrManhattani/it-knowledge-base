# 🕵️‍♂️ Полный инженерный справочник по ARP

> [!INFO] **Зачем это DevOps инженеру?**
> 
> Если ты настраиваешь отказоустойчивые кластеры (Keepalived, VRRP, HAProxy), переносишь IP-адреса между серверами (Floating IP) или ищешь причину «потери» пакетов внутри одного свитча — ты неизбежно столкнешься с кэшами ARP и необходимостью принудительно их обновлять.

## 1. 🧠 Фундаментальная концепция

> [!info] **ARP (Address Resolution Protocol)** — это протокол разрешения адресов. 
> Он нужен для того, чтобы по известному IP-адресу узнать MAC-адрес устройства в пределах одной локальной сети.  Когда операционной системе нужно отправить IP-пакет в локальную сеть, она обязана инкапсулировать его в Ethernet-кадр, для чего строго необходим MAC-адрес получателя. Для поиска отправляется широковещательный ARP-запрос на MAC-адрес `FF:FF:FF:FF:FF:FF`. Устройство с искомым IP-адресом присылает Unicast-ответ со своим аппаратным адресом. Чтобы не спамить сеть широковещанием перед отправкой каждого пакета, полученная связка IP-MAC сохраняется в локальный ARP-кэш устройства на определенное время.»
> - **Проблема:** Коммутаторы (L2) пересылают кадры только по MAC-адресам. Они ничего не знают про IP. Операционная система знает целевой IP-адрес, но не может отправить данные, пока не «завернет» их в Ethernet-кадр с правильным MAC-адресом получателя.
> - **Решение:** Протокол ARP, который позволяет компьютеру «крикнуть» в сеть IP-адрес и получить в ответ MAC-адрес владельца.

> [!WARNING] **Особенность инкапсуляции (Частый вопрос)**
> 
> Пакет ARP **не имеет IP-заголовка**. Он не маршрутизируется. Он упаковывается напрямую в Ethernet-кадр (EtherType `0x0806`). Поэтому ARP-запросы физически не могут преодолеть маршрутизатор и живут только в пределах одного L2-домена (VLAN/Свитч).

## 2. ⚙️ Механика работы (Пошаговый процесс)

Допустим, Компьютер А (`192.168.1.10`) хочет отправить пинг Компьютеру Б (`192.168.1.20`).

### 2.1 Шаг 1: Проверка локального кэша

Компьютер А заглядывает в свою локальную таблицу (ARP Cache).
- Если MAC-адрес для `192.168.1.20` найден — пакет мгновенно отправляется.
- Если записи нет (или она устарела) — генерация запроса.

### 2.2 Шаг 2: ARP Request (Широковещательный запрос)

Компьютер А формирует кадр ARP Request.
- **Source MAC:** `MAC Компьютера А`
- **Destination MAC:** `FF:FF:FF:FF:FF:FF` (Broadcast — слушают все сетевые карты).
- **Payload (Суть):** _"Кто имеет 192.168.1.20? Ответьте 192.168.1.10 (моему MAC)"_.
    Коммутатор получает этот кадр и рассылает его **во все порты** (кроме порта отправителя). Процессоры всех устройств в сети отвлекаются на обработку этого пакета.

### 2.3 Шаг 3: ARP Reply (Точечный ответ)

Все устройства, чей IP не совпадает, отбрасывают запрос. Компьютер Б узнает свой IP.
Он формирует кадр ARP Reply.
- **Source MAC:** `MAC Компьютера Б`
- **Destination MAC:** `MAC Компьютера А` (Unicast — летит точно отправителю).
- **Payload (Суть):** _"Я 192.168.1.20, мой MAC-адрес — BB:BB:BB:BB:BB:BB"_.

### 2.4 Шаг 4: Обновление кэша

Компьютер А получает ответ, записывает связку `IP <-> MAC` в свой ARP-кэш на несколько минут (обычно от 1 до 20 минут в зависимости от ОС) и наконец-то отправляет задержанный IP-пакет (ping).

## 3. 🛡 Важные виды ARP
Помимо стандартного запроса, есть специализированные типы ARP, на которых строится вся магия отказоустойчивости.

### 3.1 🌟 Gratuitous ARP (GARP) — «Беспричинный» ARP

Это ARP Reply (или Request), о котором **никто не просил**. Устройство отправляет его по своей инициативе на широковещательный MAC `FF:FF:FF:FF:FF:FF`.
**Зачем он нужен:**
1. **Обнаружение конфликтов IP (DAD):** Когда ОС загружается, она шлет GARP со своим собственным IP. Если кто-то отвечает — значит в сети дубль, и Windows выдает ошибку: _"Этот IP-адрес уже используется"_.
2. **Failover кластеры (Keepalived / VRRP / HAProxy):** * У тебя есть два балансировщика (Master и Backup) и один "плавающий" IP (`10.0.0.100`).
    - Master умирает. Backup забирает IP `10.0.0.100` себе.
    - **Проблема:** Коммутатор и все клиенты всё еще думают (их ARP-кэш), что этот IP привязан к MAC-адресу мертвого Master'а. Трафик летит в черную дыру.
    - **Решение:** Новый Backup мгновенно рассылает GARP: _"Всем обновить кэши! Теперь IP 10.0.0.100 находится на моем MAC-адресе!"_. Сеть перестраивается за долю секунды.

### 🎭 3.2 Proxy ARP

> [!tip] Ситуация, когда маршрутизатор отвечает на ARP-запрос **вместо** целевого устройства.
> - Используется в старых или криво настроенных сетях (например, когда маска подсети на ПК настроена шире, чем на роутере).
> - ПК думает, что целевой сервер в его локалке, и шлет ARP-запрос. Роутер понимает, что ПК ошибается, но чтобы трафик не пропал, роутер отвечает: _"Это я, шли пакеты мне (на мой MAC)"_, а затем сам маршрутизирует их серверу.
> - _Best Practice:_ Сейчас Proxy ARP рекомендуется отключать из-за проблем с безопасностью.

Представь классическую ситуацию с ошибкой конфигурации (Misconfiguration):
- **Компьютер (PC1):** IP `192.168.1.10`, маска **`/16`** `(255.255.0.0)`.
- **Роутер (R1, порт eth0 - смотрит к PC1):** IP `192.168.1.1`, маска **`/24`**.
- **Роутер (R1, порт eth1 - смотрит к Серверу):** IP `192.168.2.1`, маска **`/24`**.
- **Сервер (SRV):** IP `192.168.2.20`, маска **`/24`**.
PC1 хочет отправить пинг на Сервер (`192.168.2.20`).
#### 3.2.1 Шаг 1: Ошибка компьютера (Почему он шлет ARP)

Операционная система PC1 берет свой IP и накладывает свою (ошибочно широкую) маску `/16`.
Она видит, что целевой IP `192.168.2.20` входит в её локальную подсеть (`192.168.0.0/16`).
Так как ПК думает, что сервер находится с ним в одном проводе (L2-домене), он **не отправляет пакет на шлюз по умолчанию**. Вместо этого он генерирует широковещательный ARP-запрос:
> _"У кого IP 192.168.2.20? Скажите мне ваш MAC!"_
#### 3.2.2 Шаг 2: Железная логика роутера (Алгоритм Proxy ARP)

Широковещательный запрос прилетает на интерфейс `eth0` роутера.
В норме роутер отбрасывает ARP-запросы, адресованные не ему. Но если на интерфейсе **включена функция Proxy ARP**, ядро роутера выполняет следующие 3 проверки:
1. **Целевой IP мне принадлежит?**
    Роутер видит, что ищут `192.168.2.20`. Это не его IP.
2. **Я знаю, где этот IP?**
    Роутер заглядывает в свою таблицу маршрутизации. Он видит маршрут: _"Подсеть 192.168.2.0/24 доступна через интерфейс `eth1`"_. (Да, знаю!).
3. **ГЛАВНОЕ УСЛОВИЕ:** Находится ли этот IP **за другим интерфейсом** (не за тем, откуда прилетел ARP)?
    ARP прилетел из `eth0`. А целевой IP находится за `eth1`. Условие выполнено!
#### 3.2.3 Шаг 3: Вывод роутера и «Ложь во спасение»

Роутер сопоставляет факты:
- _"Компьютер из порта `eth0` пытается найти MAC-адрес узла 192.168.2.20 с помощью ARP."_
- _"Но ARP работает только в локальной сети, а узел 192.168.2.20 физически находится за моим портом `eth1` (в другой сети)."_
- _"Вывод: Компьютер ошибается и думает, что это одна L2-сеть. Если я промолчу, пакет просто сгорит, потому что настоящий сервер за портом `eth1` никогда не услышит этот ARP-запрос (я же не пропускаю бродкасты)."_
Чтобы спасти трафик, роутер генерирует **ARP Reply** от своего имени:
> _"Эй, PC1! IP 192.168.2.20 находится на МОЁМ MAC-адресе (MAC порта eth0)."_
#### 3.2.4 Шаг 4: Развязка

PC1 радостно записывает в свой кэш: `192.168.2.20 = MAC-адрес роутера`.
PC1 формирует IP-пакет (где назначения IP сервера) и запаковывает его в кадр с MAC-адресом роутера. Пакет прилетает на роутер. Роутер распаковывает его, видит IP назначения, маршрутизирует его в порт `eth1` и доставляет серверу.

> [!ABSTRACT] **Резюме для справочника**
> 
> Роутер не анализирует маску отправителя. **Proxy ARP — это просто условный рефлекс маршрутизатора:**
> 
> _"Если кто-то в порту А по ARP спрашивает IP-адрес, который по моей таблице маршрутизации находится в порту Б, я совру и отвечу своим MAC-адресом, чтобы перехватить этот трафик и смаршрутизировать его."_

## 4. ☠️ Уязвимости (ARP Spoofing / Poisoning)

Протокол ARP был придуман в 80-х годах, когда сети были доверенными. В нем **нет никакой аутентификации** и он **Stateless** (не отслеживает состояние).

> [!WARNING] **Атака Man-in-the-Middle (MITM)**
> 
> Хакер в локальной сети постоянно шлет поддельные Gratuitous ARP ответы всем компьютерам: _"IP роутера (192.168.1.1) — это мой MAC"_, а роутеру: _"IP компьютеров — это мой MAC"_.
> 
> ОС слепо верят этим пакетам и обновляют кэши. Весь трафик в офисе начинает идти через ноутбук хакера.

**Защита (Инфраструктурная):**

На управляемых коммутаторах (Cisco, Juniper, MikroTik) настраивается **DAI (Dynamic ARP Inspection)**. Коммутатор сверяет все пролетающие ARP-пакеты со своей базой DHCP-Snooping (он точно знает, какому порту какой IP он выдал). Если хакер пытается представиться чужим IP — порт блокируется аппаратно.

## 5. 💻 Практика: CLI и Диагностика (POSIX-style)

Современный стандарт в Linux — утилита `ip` (из пакета `iproute2`). Старая утилита `arp` считается устаревшей (deprecated).

```bASH
# 1. ПОСМОТРЕТЬ ARP-КЭШ (ТАБЛИЦУ СОСЕДЕЙ)
$ ip neigh show
192.168.1.1 dev eth0 lladdr a1:b2:c3:d4:e5:f6 REACHABLE
192.168.1.50 dev eth0 lladdr 11:22:33:44:55:66 STALE

# Статусы:
# REACHABLE — Запись свежая, всё работает.
# STALE — Запись устарела, при следующей отправке пакета будет послан новый запрос.
# INCOMPLETE — Мы послали ARP Request, но никто не отвечает (устройство мертво/не существует).

# 2. ОЧИСТИТЬ ARP-КЭШ (Если перенесли IP на другой сервер, а кэш залип)
$ ip neigh flush all
# или удалить конкретный
$ ip neigh del 192.168.1.50 dev eth0

# 3. ОТПРАВИТЬ GARP ВРУЧНУЮ (Утилита arping)
# Полезно при дебаге Keepalived/Свитчей (-U = Unsolicited/Gratuitous)
$ arping -U -c 3 -I eth0 192.168.1.100

# 4. ТРАБЛШУТИНГ ЧЕРЕЗ TCPDUMP
# Отлавливаем только ARP пакеты
$ tcpdump -i eth0 -n arp
14:22:01.001 ARP, Request who-has 192.168.1.20 tell 192.168.1.10, length 28
14:22:01.002 ARP, Reply 192.168.1.20 is-at bb:bb:bb:bb:bb:bb, length 28
```

## 6. ⚖️ Сравнение: IPv4 ARP vs IPv6 NDP

Чтобы закрепить логику перехода к современным сетям, давай сравним их лоб в лоб.

|**Характеристика**|**ARP (IPv4)**|**NDP (IPv6)**|**Почему это лучше?**|
|---|---|---|---|
|**Уровень OSI**|L2 (EtherType `0x0806`)|L3 (ICMPv6 внутри IPv6)|NDP маршрутизируем, работает поверх IPsec (можно шифровать), подчиняется правилам Firewall.|
|**Тип рассылки**|**Broadcast** (`FF:FF...`)|**Multicast** (`33:33:FF...`)|ARP будит CPU всех устройств. NDP отфильтровывается аппаратно на сетевых картах (NIC).|
|**Интеграция**|Отдельный костыльный протокол|Часть ядра ICMPv6|Сокращает зоопарк протоколов. NDP выполняет роли ARP, DHCP (SLAAC) и ICMP-Redirect одновременно.|
