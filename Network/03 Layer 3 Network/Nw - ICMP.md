# 🏓 ICMP: Инженерный конспект и Траблшутинг

## 📑 NAME

**ICMP** — протокол межсетевых управляющих сообщений. Это главный диагностический инструмент стека TCP/IP. В отличие от протоколов пользовательского трафика (TCP/UDP), ICMP не передает данные приложений, а сообщает о проблемах доставки пакетов и состоянии сети.

![[ICMP - общая информация.png]]
## ⚙️ ARCHITECTURE & PROTOCOL SPECS

- **OSI Layer:** L3 (Сетевой уровень). ICMP работает на одном уровне с IP, но технически инкапсулируется _внутрь_ IP-пакета.
- **Транспорт:** Не использует TCP или UDP. В заголовке IPv4 поле `Protocol` для ICMP всегда равно **1**.
- **Порты:** У ICMP **НЕТ ПОРТОВ**. Вы не можете "открыть порт ICMP" на файрволе, вы можете разрешить только определенные типы сообщений (Types и Codes).

## 📩 MESSAGE TYPES & CODES (Типы и Коды)

Структура ICMP-пакета опирается на два главных поля: **Type** (Категория сообщения) и **Code** (Конкретизация проблемы).

Знание этой таблицы — база для настройки сетевых экранов (iptables/nftables/UFW).

| **Type** | **Code** | **Имя (Функция)**        | **Описание для инженера**                                                                                                         |
| -------- | -------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **8**    | 0        | **Echo Request**         | Запрос эха. То, что отправляет утилита `ping`.                                                                                    |
| **0**    | 0        | **Echo Reply**           | Ответ на эхо. Успешный ответ на ваш `ping`.                                                                                       |
| **11**   | 0        | **Time Exceeded**        | Время жизни (TTL) пакета истекло. Пакет убит роутером, чтобы не летать вечно в петле маршрутизации. _(Основа работы traceroute)._ |
| **3**    | 0        | **Net Unreachable**      | Роутер не знает маршрута к целевой подсети.                                                                                       |
| **3**    | 1        | **Host Unreachable**     | Подсеть найдена, но конечный компьютер выключен или не отвечает на ARP.                                                           |
| **3**    | 3        | **Port Unreachable**     | Компьютер работает, но нужная служба (демон) не слушает указанный UDP-порт.                                                       |
| **3**    | 4        | **Fragmentation Needed** | ⚠️ **Критично для DevOps.** Пакет слишком большой (превышает MTU), но установлен флаг DF (Don't Fragment).                        |

## 🛠️ КАК РАБОТАЮТ УТИЛИТЫ (Under the Hood)

Инженера часто просят объяснить на собеседовании, как именно работают базовые утилиты.

### 1. Утилита `ping`

Работает тривиально:

1. ОС генерирует ICMP Type 8 (Echo Request) и отправляет его целевому IP.
2. В пакет зашивается таймстемп (время отправки) и Sequence Number (порядковый номер).
3. Целевой хост получает Type 8, меняет Type на 0 (Echo Reply), перекладывает Payload и отправляет обратно.
4. Ваша ОС получает Type 0, сравнивает таймстемп и вычисляет RTT (Round-Trip Time — пинг).

![[ICMP - ping.png]]
### 2. Утилита `traceroute` / `tracert` (Магия TTL)

Traceroute эксплуатирует механизм уничтожения пакетов через поле TTL (Time To Live).

1. Ваш ПК отправляет пакет к цели, но умышленно ставит **TTL = 1**.
2. Первый же роутер (шлюз) получает пакет, уменьшает TTL до 0. Пакет уничтожается, а вам отправляется ICMP **Type 11** (Time Exceeded). Теперь вы знаете IP первого роутера.
3. Ваш ПК отправляет пакет с **TTL = 2**. Он проходит первый роутер, умирает на втором. Второй роутер шлет вам Type 11. Вы знаете IP второго роутера.
4. Процесс повторяется, пока пакет не достигнет цели.

> [!INFO] **Разница Linux и Windows**
> 
> - **Windows **(`tracert`): Отправляет классические ICMP Echo Request (Type 8).
>     
> - **Linux **(`traceroute`): По умолчанию отправляет **UDP-пакеты** на случайные высокие порты (33434+). Цель в конце концов получает UDP-пакет, понимает, что такой порт закрыт, и отправляет вам ICMP **Type 3 Code 3** (Port Unreachable). Это сигнал окончания трассировки.
>

## 🛑 DEVSEC SECRETS: Миф "Блокируй весь ICMP"

Многие Junior-администраторы настраивают Linux-серверы так: `iptables -A INPUT -p icmp -j DROP`, думая, что если сервер не пингуется, то он в безопасности от хакеров.

**Это фатальная архитектурная ошибка (Black Hole Router).**

Если вы заблокируете **весь** ICMP, вы сломаете механизм **PMTUD (Path MTU Discovery)**.

1. Ваш сервер пытается отправить клиенту большой пакет (1500 байт) с установленным флагом DF (не фрагментировать).
2. Где-то по пути провайдер использует GRE-туннель с MTU 1476.
3. Провайдерский роутер не может пропихнуть пакет 1500 в дыру 1476. Он убивает пакет и отправляет вашему серверу ICMP **Type 3 Code 4** (_Fragmentation Needed_).
4. Если ваш файрвол блокирует ICMP, сервер **не получит** это сообщение.
5. **Симптом:** TCP-рукопожатие (мелкие пакеты) проходит успешно. Но как только начинается скачивание файла или загрузка тяжелой веб-страницы — соединение виснет намертво.

> [!TIP] **Best Practice для Firewall**
> 
> Никогда не блокируйте ICMP целиком. Минимально необходимый набор, который **обязан** проходить через файрвол:
> 
> - Type 0 (Echo Reply)
>     
> - Type 3 (Destination Unreachable) — _Особенно Code 4!_
>     
> - Type 11 (Time Exceeded)
>

## 💻 EXAMPLES: POSIX-style CLI Diagnostic

```bash
# 1. Пинг с указанием конкретного интерфейса или source-IP (полезно при наличии нескольких VLAN)
1. $ ping -I eth1 8.8.8.8

# 2. Linux Traceroute: Форсированное использование ICMP (как в Windows), а не UDP
2. $ traceroute -I 8.8.8.8

# 3. Проверка PMTUD: Отправка большого пакета с запретом фрагментации
# Если вернется "Frag needed and DF set", значит MTU по пути меньше 1500.
3. $ ping -M do -s 1472 8.8.8.8

# 4. Настройка Iptables (разрешаем жизненно важный Type 3 Code 4)
4. # iptables -A INPUT -p icmp --icmp-type fragmentation-needed -j ACCEPT
```
