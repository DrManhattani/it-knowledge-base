# 🚇 СТАНДАРТ: GRE (Generic Routing Encapsulation)

> [!INFO] **Архитектурная ценность**
> 
> В чистом виде GRE в современном интернете — это моветон и дыра в безопасности. Однако связка **GRE over IPsec** — это абсолютный индустриальный стандарт (Legacy Enterprise) для построения корпоративных сетей (Site-to-Site VPN). Понимание GRE — это ключ к пониманию того, как работают инкапсуляция, оверхед заголовков и проблемы с фрагментацией (MTU).

## 📄 NAME

**GRE** — протокол туннелирования, разработанный Cisco Systems, предназначенный для инкапсуляции пакетов сетевого уровня (пассажира) внутри других пакетов сетевого уровня (транспорта).

## 🎯 SYNOPSIS

Протокол создает виртуальный (логический) P2P-линк между двумя маршрутизаторами (`rtr`), позволяя передавать через публичный интернет нестандартный или немаршрутизируемый трафик:

- Протоколы динамической маршрутизации (OSPF, EIGRP, BGP), которые требуют Multicast.
- Широковещательный трафик (Broadcast).
- Не-IP протоколы (IPX, AppleTalk — исторически) или IPv6 поверх старой IPv4-инфраструктуры.

## 🧠 DESCRIPTION: Архитектура и Инкапсуляция

Главная суперсила GRE — его «всеядность». IPsec параноидален и не пропускает Multicast, поэтому роутеры не могут установить соседство по OSPF через чистый IPsec-туннель. GRE выступает в роли «глупого конверта», который берет любой пакет, прячет его и отправляет получателю.

### 📦 Анатомия GRE-пакета

Когда маршрутизатор упаковывает данные в GRE, он формирует структуру "Матрешки":

|**Delivery Header (Транспорт)**|**GRE Header**|**Passenger Packet (Пассажир)**|
|---|---|---|
|**Новый IPv4 заголовок**<br><br>  <br><br>Source: 8.8.8.8 (Белый IP)<br><br>  <br><br>Dest: 9.9.9.9 (Белый IP)<br><br>  <br><br>Protocol: 47|**Заголовок GRE**<br><br>  <br><br>Указывает тип протокола внутри (EtherType), флаги контрольной суммы и ключи.|**Оригинальный IP Пакет**<br><br>  <br><br>Source: 192.168.1.10 (Серый IP)<br><br>  <br><br>Dest: 192.168.2.20 (Серый IP)<br><br>  <br><br>Payload: ICMP/TCP/UDP|
|_20 Bytes_|_4 Bytes (минимум)_|_Оригинальный размер пакета_|

> [!WARNING] **Протокол 47 (Не порт!)**
> 
> GRE — это протокол сетевого уровня. Он не использует порты TCP или UDP (L4). В заголовке наружного IPv4-пакета в поле `Protocol` жестко прописан номер **47**. Если на пути стоит Firewall или NAT-устройство, оно обязано уметь пропускать `IP Protocol 47`, иначе туннель не поднимется.

## ✂️ CAVEATS: MTU и TCP MSS (DevOps Грабли)

Это самая частая причина, почему "пинги ходят, а сайты не открываются" через туннели.

1. **Проблема MTU:** Стандартный размер кадра Ethernet (MTU) — 1500 байт. GRE добавляет 24 байта сверху (20 байт внешний IP + 4 байта GRE). Если в туннель попытаться засунуть стандартный пакет 1500 байт, он раздуется до 1524 байт, не влезет в провайдерский кабель и будет фрагментирован (или уничтожен аппаратно).
2. **Решение (Снижение MTU):** На логическом интерфейсе `Tunnel` необходимо жестко ограничить MTU: $1500 - 24 = 1476$ байт.
3. **Проблема TCP MSS:** Чтобы компьютеры за `rtr` даже не пытались формировать пакеты большего размера, маршрутизатор должен перехватывать процесс TCP Handshake и подменять в нем значение **MSS (Maximum Segment Size)**.
    - $MSS = MTU (1476) - 20 (IP Header) - 20 (TCP Header) = 1436$ байт.

## 🔒 GRE over IPsec (Индустриальный стандарт)

Сам по себе GRE **не имеет шифрования** (весь трафик летит в открытом виде) и **не имеет аутентификации** (любой может закинуть пакет в туннель).
Поэтому на практике настраивается двухслойная инкапсуляция:

1. `rtr` берет Multicast OSPF-пакет и запаковывает его в **GRE** (чтобы маршрутизация заработала).
2. `rtr` берет получившийся GRE-пакет и шифрует его с помощью **IPsec** (ESP, Protocol 50).
3. Зашифрованный "куб" отправляется через интернет.

## 💻 EXAMPLES: Конфигурация P2P GRE Tunnel (Cisco IOS)

Развертывание статического P2P туннеля между Главным офисом (rtr-HQ) и Филиалом (rtr-BR).

**Дано (rtr-HQ):**
- Белый IP (WAN): `203.0.113.1`
- Серый IP (Туннель): `10.255.255.1/30`

**Дано (rtr-BR):**
- Белый IP (WAN): `198.51.100.2`
- Серый IP (Туннель): `10.255.255.2/30`

### Шаг 1: Настройка rtr-HQ

```bash
1. Priv # configure terminal
# Создаем логический интерфейс туннеля
2. Priv # interface Tunnel0
# Назначаем "внутренний" серый IP-адрес для маршрутизации
3. Priv # ip address 10.255.255.1 255.255.255.252
# Указываем свой физический внешний интерфейс (источник)
4. Priv # tunnel source GigabitEthernet0/0
# Указываем белый IP-адрес удаленного роутера
5. Priv # tunnel destination 198.51.100.2
# Оптимизация фрагментации (ОБЯЗАТЕЛЬНО для продакшена)
6. Priv # ip mtu 1476
7. Priv # ip tcp adjust-mss 1436
8. Priv # exit
```

### Шаг 2: Настройка маршрутизации (Проброс LAN)

Чтобы компьютеры из офиса А увидели офис Б, нужно завернуть их подсети в этот туннель:

```bash
# Статический маршрут: "Всю сеть 192.168.20.0/24 отправлять в Tunnel0"
9. Priv # ip route 192.168.20.0 255.255.255.0 Tunnel0
```

### Шаг 3: Верификация

```bash
# Проверка поднятия интерфейса (Protocol должен быть UP)
10. Priv # show ip interface brief | include Tunnel
Tunnel0                    10.255.255.1    YES manual up                    up

# Проверка параметров инкапсуляции
11. Priv # show interfaces Tunnel0
# Ожидаемый вывод:
# Tunnel0 is up, line protocol is up
#   Tunnel source 203.0.113.1, destination 198.51.100.2
#   Tunnel protocol/transport GRE/IP
```

> [!TIP] **Keepalive Timer**
> 
> По умолчанию GRE — это протокол без состояния (Stateless). Интерфейс `Tunnel0` будет светиться как `UP`, даже если на другом конце выключили свет. Чтобы `rtr` мог отследить падение туннеля и перестроить маршруты, необходимо включить генерацию тестовых пакетов командой:
> 
> `keepalive 10 3` (Отправлять пакет каждые 10 секунд, считать туннель мертвым после 3 пропусков).
